CURRICULUM PHILOSOPHY PORTABLE MEMORY v3.11 BASE CLEAN
======================================================
STATUS: CURRENT UNIVERSAL TEACHING / LEARNING PHILOSOPHY
PURPOSE: Preserve the universal educational beliefs that should shape every course without relying on stored
memory, prior chats, or course-specific habits.

================================================================
READ THIS FIRST / SOURCE OF TRUTH
================================================================

This Philosophy PM is the BASE layer. It owns universal beliefs about learning, instruction, evidence,
teacher choice, useful abundance, representations, resource purpose, and quality.

It does NOT define a course's exact I-can statements, response format, recurring-practice pattern, resource
counts, Summative format, representation system, source library, or deployed paths. Those course-specific
choices belong in the CURRENT course Framework and its embedded course profile.

It does NOT override the ORIGINAL current Unit Assessment Plan on what students must learn/evidence.
It does NOT override the Base Bank PM on universal Bank construction/package mechanics.
It does NOT override the Base Notes PM on universal Notes construction/package mechanics.
It does NOT override the Base Practice PM on universal Practice rendering/package mechanics.
It does NOT override the Base Activities PM on universal Activities selection/transformation/package mechanics.
It does NOT override the Base Recurring + Assessment Resources PM on universal downstream shell/rendering/package mechanics for Warm-Ups, Exit Tickets, Progress Trackers, Reviews, or Summative Assessments.
Explicit current teacher instructions override this PM.

Use the architecture in this order:
  BANK:  PHILOSOPHY -> BASE BANK PM -> CURRENT COURSE FRAMEWORK -> COMPLETE BANK BUILD
  NOTES: PHILOSOPHY -> BASE NOTES PM -> CURRENT COURSE FRAMEWORK -> FINALIZED UNIT BANK -> COMPLETE UNIT NOTES
  PRACTICE: PHILOSOPHY -> BASE PRACTICE PM -> CURRENT COURSE FRAMEWORK -> FINALIZED UNIT BANK -> COMPLETE PRACTICE SETS
  ACTIVITIES: PHILOSOPHY -> BASE ACTIVITIES PM -> CURRENT COURSE FRAMEWORK -> FINALIZED UNIT BANK -> COMPLETE UNIT ACTIVITIES
  RECURRING/ASSESSMENT: PHILOSOPHY -> BASE RECURRING + ASSESSMENT PM -> CURRENT COURSE FRAMEWORK -> FINALIZED UNIT BANK -> COMPLETE REQUESTED RESOURCE
  MAINTENANCE: DEPLOYED COURSE/RESOURCE -> TARGETED MAINTENANCE PM -> CURRENT AUTHORITIES -> SURGICALLY UPDATED RESOURCE IN THE SAME DEPLOYED STRUCTURE

Do not blend this PM with remembered older philosophy. Read it near the beginning, then REREAD it after the
exact I-can/evidence/representation maps are built and immediately before canonical item authoring.

CORE SENTENCE
Instruction creates opportunities to learn; assessment collects evidence; the portfolio organizes that
evidence over time; and the grade communicates the best current professional judgment of what the student
actually understands.

================================================================
1. BUILD FROM LEARNING ARCHITECTURE, NOT RANDOM INVENTORY
================================================================

Do not start by writing questions.

Correct sequence:
  current Framework + ORIGINAL Unit Assessment Plan
    -> exact I-can / learning-target map
    -> course-specific learning lifecycle / recurring-practice routing
    -> resource-purpose map
    -> learning progression
    -> evidence map
    -> representation plan
    -> item requirements
    -> approved question structure
    -> actual authored question
    -> independent verification

For any build that spans multiple items, sections, or resource instances, turn the learning/evidence/representation
architecture into an explicit PRE-AUTHORING MAP across the full requested scope before writing the final student
materials. The map is a thinking tool, not a quota sheet. Use it to see coverage, missing opportunities, repeated
structures, representation use, evidence routes, and the actual jobs students will do before template momentum
starts driving the build. QA and revise the map before rendering when the pattern does not match the intended
learning work.

Predictable routine is desirable. Mad-Libs for WHERE resources go can be good. Mad-Libs for QUESTION THINKING
is bad.

The exact I-can statements are the instructional spine. Section readings, explanations, Notes anchors,
Examples/YTIs, Practice, evidence, and later downstream resources should revolve around those exact learning
jobs rather than a generic textbook chapter template. If the learning architecture changes, downstream
resources should be intentionally reconciled rather than quietly preserving an obsolete order.

================================================================
1A. CANONICAL LEARNING-LIFECYCLE VOCABULARY
================================================================

Use three distinct internal learning stages:

  CURRENT LEARNING = the content being newly taught in the current Unit.
  RETRIEVAL = purposeful return to recently learned content for spacing, connection, and retention.
  MASTERY = the durable learning currently being gathered as formal portfolio / Summative evidence.

The older labels `Intro` and `Review` may appear in finalized legacy Banks. Treat them only as compatibility aliases:
  Intro = Current Learning
  Review = Retrieval
Do not rebuild an otherwise correct finalized Bank only to rename those metadata values.

RESOURCE-NAME RULE — HARD:
The student-facing `Unit Review` is NOT the RETRIEVAL stage. It is the current Unit's MASTERY-preparation resource and prepares students for the same Mastery evidence represented by the Progress Tracker and Summative.

Historical/source Unit identity remains internal to the Assessment Plan/source map and is not student-facing in the Unit Review family.

OWNERSHIP BOUNDARY — HARD:
This Philosophy owns only that universal PURPOSE/IDENTITY distinction. It does NOT own Review HTML structure, navigation, CSS classes, visible section sequence, focus-heading style, Review Practice layout, or package mechanics. Those belong to the current Base Recurring + Assessment Review renderer, with course-specific content requirements supplied by the current Framework.

Therefore:
  RETRIEVAL = an internal spiral stage.
  UNIT REVIEW = a student-facing Mastery-preparation resource.

================================================================
2. RICH MENU / USEFUL ABUNDANCE / TEACHER CHOICE
================================================================

The course is a rich menu of high-quality options, not a minimum viable packet or fixed calendar.
The teacher may skip, shorten, substitute, combine, reorder, or spend longer on resources.

MORE CAN BE BETTER when additional material is genuinely useful. Unused high-quality material gives teacher
choice, differentiation, reassessment options, alternate representations, repetition, and flexibility.

Underbuilding often forces the teacher to invent curriculum during class. Therefore do not stop simply
because the smallest acceptable amount has been reached. The guardrail is PURPOSE, not minimalism.
Do not add purposeless filler, but do not remove useful material merely because not all of it will be used.

DOWNSTREAM FULLNESS PRINCIPLE:
When a finalized canonical source route is already appropriately classroom-sized and a downstream wrapper can support the full route, preserve the full useful set by default. Do not discard canonical opportunities merely to match an older page count or legacy template. Intentional thinning is allowed only when it serves a clear resource purpose.

ABUNDANCE IS COURSE-RESPONSIVE.
Different courses and topics need different kinds and amounts of repetition. A course that depends heavily on
procedural fluency may intentionally devote several nearby questions to the same high-value family. Another
course may gain more from changing representation, phenomenon, model, or reasoning demand. The Framework
should state the course-specific expression of this philosophy.

The rich digital Bank is allowed to contain more options than a teacher will use in one lesson or printout.
A future print/export workflow may select or condense the menu; the canonical Bank should not be made sparse
merely because every available question will not be assigned.

================================================================
3. REPETITION IS OFTEN HOW LEARNING DEVELOPS
================================================================

Repetition is not automatically a defect. Repeated execution/retrieval can build fluency, accuracy,
notation/control, discrimination, conceptual strength, and confidence.

Several direct solve/evaluate/simplify/graph/classify/calculate/formula questions may be better than forcing
every question into a different context or reasoning wrapper. A useful family may legitimately appear several
times with closely related values/structures when that is the learning work students need.

Even an exact duplicate is not automatically a curriculum failure in a rich teacher Bank. It may be harmless
or intentionally reusable. Do not launch an anti-clone rewrite merely because prompts repeat. Teacher judgment
can later decide which instances to keep, replace, remap, or allow as multiples.

Repeated questions should still read like ordinary student questions. Do not expose generator iteration labels
such as “second pass” or append one generic explanation/checking suffix across a whole Practice form.
Explanation, verification, representation, units, or reasonableness language should be item-specific when it
adds learning value.

MAP-FIRST REPETITION DISCIPLINE:
A pre-authoring map helps distinguish PURPOSEFUL REPETITION from ACCIDENTAL REPETITION. Repetition that serves
a mapped learning job — fluency, retrieval, repeated evidence, consistency across forms, repeated use of an
important representation, or deliberate return to a high-value structure — may be exactly right and should not
be removed merely to create surface variety.

The map should, however, expose repetition caused mainly by template convenience: the same question shell,
experience sequence, representation choice, reasoning suffix, or student action repeated because it was easy
to render rather than because the learning architecture called for it. When a suspicious cluster appears, ask
what learning/evidence purpose the repetition serves. If the purpose is real, keep it. If the repetition is only
a byproduct of the template, revise the PLAN before authoring the final resource.

Do not use anti-repetition quotas such as “no structure more than twice.” Good repetition may legitimately cluster.
The goal of map-first planning is not maximum variety; it is INTENTIONALITY.

Variety should broaden thinking where useful; it should not crowd out needed repetitions.

================================================================
4. HIGHEST-STAKES BANK AREAS
================================================================

1. Exact I-can / learning-target mapping.
2. Strong WTC / section-opening experience.
3. Strong Notes Example/YTI anchors.
4. Strong Exit Tickets with explicit evidence maps.
5. Honest distribution of opportunities across the exact I-can statements.

Inventory completeness does not rescue weakness in these areas. Equal distribution is not required, but an
explicit I-can should not accidentally receive almost no meaningful instructional/evidence opportunity unless
the current Framework/Assessment Plan intentionally treats it as supporting or subsumed.

================================================================
5. REPRESENTATIONS ARE INSTRUCTIONAL CONTENT
================================================================

The course Framework defines the representation system that matters for that discipline and Unit. Possible
representations include graphs, equations, tables, contexts, diagrams, phenomena/images, data, formulas,
models, units, experimental setups, number lines, geometric objects, code, or other course-specific forms.

Plan and actually USE the applicable forms; do not satisfy representation philosophy by merely mentioning
that they were considered. Connect/translate among forms where meaningful. This is not an equal-percentage
quota. A representation-heavy target with almost no real representation work is philosophically underbuilt
even if its symbolic/text questions are correct.

A representation counts only when students actually read, build, use, compare, translate, annotate, or
interpret it. Decorative images and metadata labels do not count as representation reasoning.

Use the Framework's authoritative graph/figure/data tool whenever its supported type represents the intended
content cleanly DURING AUTHORING or canonical figure production. Preserve editable figure source with production
Banks. Downstream renderers such as Practice Sets should reuse the finalized canonical representation bytes rather
than regenerate or redesign them.

================================================================
6. PRACTICE CREATES LEARNING; DO NOT UNDERBUILD
================================================================

Practice exists primarily to CREATE LEARNING, not to generate grades.
The Base Bank PM may provide an inventory template and the Framework may specify course-specific counts,
repetition patterns, or routing. Those are implementation rules, not the philosophical reason Practice exists.

A good Practice resource provides substantial productive work for the intended learner, with useful extra
material allowed because the teacher can skip/select.

Practice may contain direct/repeated work, representations, conceptual/diagnostic work, and a smaller or larger
number of deeper/integrated/transfer items depending on the course and target. Parallel forms preserve learning
coverage/opportunity; they do not need to maximize sentence-shell variety.

================================================================
7. NOTES / EXAMPLE-YTI / WTC
================================================================

Notes are the main guided instructional pathway but not a script that must be completed top-to-bottom.
Exact I-can mapping comes first; readings, explanatory notes, representations, Examples/YTIs, and teacher
discussion should revolve around those learning jobs.

Notes sections should be deliberately compartmentalized around the current Framework/Assessment Plan structure.
Formatting/order can improve over time, but do not blur exact I-cans into a generic undifferentiated chapter.

Instructional reading should be substantial enough to teach the idea, not a thin bridge inserted only to reach the
next problem. The current Framework owns the course-specific reading benchmark, density, language, and source
style. After a substantial reading, students should immediately process meaning through a short discussion /
sense-making task before the next major application. Discussion questions should be specific to the reading and
representations rather than stock comprehension prompts.

Vocabulary should develop in context. When a course Notes profile uses a vocabulary preview, the first meaningful
introduction or definition of a target vocabulary/notation term in instructional prose may be visually emphasized
so students can connect the previewed word to its meaning; do not turn every later recurrence into bold clutter.

Math Notes / Model Notes are reference tools, not decoration. Useful abundance applies here too: a rich Notes
resource may contain more high-value reference blocks, worked representations, connections, or models than a
teacher uses in one lesson. The teacher can skip. Do not underbuild a durable reference merely to make the Notes
shorter, but every block still needs a real instructional purpose.

WTC is a coherent section-opening FRQ-like experience built around one shared situation/object/graph/table/
data set/diagram/model. Its connected parts preview intellectual territory without testing untaught procedures.
It is not a bundle of unrelated preview questions, and it should become more meaningful after instruction.

Example/YTI pairs are instructional anchors tied to mapped targets. Reading/visuals/discussion should revolve
around conceptual learning behind the Example, not simply reveal its exact procedure immediately beforehand.
A target may legitimately receive several pairs. The teacher may skip anchors or use them differently.

Notes should not contain a fake closing Exit Check simply for symmetry.

================================================================
7A. ACTIVITIES / INTERACTIVE PRACTICE
================================================================

Activities create learning by changing the participation structure around worthwhile mathematical/scientific work.
Movement, collaboration, station rotation, projected team work, peer checking, and structured conversation can make
retrieval, representation use, comparison, explanation, and practice more visible and social. The activity structure
serves the learning job; novelty is not the goal.

Activities are OPTIONAL instructional routes. Required core instruction or required portfolio/evidence opportunities
must not disappear if an Activity is skipped. A good Activity can deepen, rehearse, connect, or make visible work that
is already supported by the Framework/Bank/Notes architecture.

When an Activities workflow is built from a finalized Bank, the Bank is the canonical mathematical content source.
The activity builder may SELECT, GROUP, ORDER, and WRAP canonical Bank questions inside an approved participation
structure, and may author directions, timing, roles, movement, checking routines, and teacher-use instructions. It must
not casually rewrite the mathematics, values, representations, or answers merely to make the activity look different.
If a new mathematical task is truly needed, that is upstream authoring work and should be handled intentionally rather
than smuggled into a renderer.

Choose an activity format because it fits the learning work. Short independent items may fit a social/find-someone-who
structure; a varied representation set may fit stations; richer questions or teacher-controlled reveals may fit a
projected format. Do not force every section into the same activity shell and do not choose a format only for surface fun.

Activity closure is formative unless the current Framework explicitly says otherwise. Do not silently reuse secure
Summatives or official Exit Ticket evidence as ordinary activity material. Teacher-live improvements to an Activity
should be preserved during later course upgrades unless explicitly replaced.

================================================================
7B. RECURRING / ASSESSMENT SHELL RESOURCES
================================================================

Some downstream resources are intentionally Mad-Lib-like shells rather than new curriculum-authoring systems.
When the Framework/Assessment Plan/Bank already owns the learning content, the downstream builder should extract the
authoritative fields or canonical questions and place them into the approved resource structure instead of quietly
creating a second content system. Light synthesis is appropriate only where the resource purpose genuinely requires it.

USAGE MODE IS PART OF RESOURCE DESIGN. A projector resource should be designed around a viewport; a Notability-first
resource around the tested handwriting/import geometry; a printed resource around physical page flow; and a screen study
guide around navigation/readability. The Base resource PM owns universal shell/rendering mechanics; the current Framework
owns which usage mode, stylesheet/profile, counts, paths, filenames, and course-specific routing apply.

Student-facing versions should show the learning task, not internal authoring metadata. Preserve useful hidden traceability
when the workflow needs it, but do not print DOK labels, Bank IDs, internal route names, or similar implementation labels
unless the teacher explicitly wants them visible.

================================================================
8. WARM-UPS
================================================================

Warm-Ups create a predictable instructional opening routine. Map their actual learning/retrieval job before
writing them. Spiraling/recurring practice is purposeful, not random. Repeated direct skills are valid.

The course Framework owns any course-specific recurring routine, stage routing, or special question type.
A Warm-Up SET may contain different learning jobs. Those jobs should normally remain separate numbered
questions rather than unrelated clauses bundled into one canonical item.

================================================================
9. EXIT TICKETS / EVIDENCE
================================================================

Exit Tickets are one of the highest-stakes Bank components. Build an explicit evidence map BEFORE questions.
They are quick evidence pulses, not extra Practice. The Bank creates a useful evidence menu even if only one
ticket is used.

Do not fake Mastery Goal mappings. Evidence should be interpretable and aligned with the Assessment Plan.

Quick Check = later deeper evidence. Performance Task = later richer evidence route.


PARALLEL DELIVERY / EQUIVALENT-FORM PRINCIPLE
------------------------------------------------
Short assessments may use parallel delivery formats when classroom use requires them. A projector/display form and a
collected print form may present the same evidence job differently without creating a different assessment target.
Likewise, multiple classroom versions may use a shared calibration anchor plus tightly parallel/varied items when that
helps reduce direct copying and normalize portfolio comparison.

Equivalent forms must preserve the evidence target, representation demand, reasoning load, and usable difficulty.
Delivery-format differences are not permission to change what is being assessed.

When a response requires a coordinate plane, number line, unit circle, table/grid, diagram, or other response surface,
provide an appropriate blank scaffold unless constructing that scaffold is itself part of the evidence. Information-bearing
figures belong wherever the student must read them; work-only response accessories may be print-only.

================================================================
10. ASSESSMENT / GRADING / PORTFOLIO
================================================================

Assessment determines what students currently understand/can do independently and what should happen next.
Practice creates learning; assessment gathers evidence. Grades communicate demonstrated proficiency, not
compliance or accumulated points.

Proficiency is professional judgment from a BODY OF EVIDENCE considering quality, consistency, independence,
reasoning, representation use, recency, and broader pattern over time.

Do not use simple averaging, “latest score wins,” or one weak event as the sole proficiency rule.
Not Yet means insufficient evidence, not permanent failure.

Evidence may come from Exit Tickets, Quick Checks, Performance Tasks, investigations/labs, quizzes, written
explanations, modeling, Summatives, and other valid opportunities. The same Mastery Goal may receive multiple
independent evidence points across time, representations, and contexts.

Progress labels such as Not Yet / Approaching / Meeting / Exceeding describe the quality/body of evidence,
not four item-difficulty tiers. DOK is descriptive metadata, not the assessment-design engine. A student Progress Tracker
should help learners connect exact learning goals to portfolio evidence, current evidence status, and a next move; it should
not turn DOK or a Learning Ladder into a student proficiency score.

The current Framework's course Bank profile owns course-specific response-format and Summative-format choices.
Older Assessment Plan response-format examples do not override a newer explicit course profile, while the
Assessment Plan remains authoritative for what evidence/learning must be assessed.

================================================================
11. QUESTION STRUCTURE / STARTER TOOLKIT
================================================================

The Toolkit supports authoring; it does not control curriculum coverage, item counts, DOK quotas, or teaching
sequence.

Use it especially for conceptual reasoning, representation connections, misconception diagnosis, modeling,
comparison, argument/evidence, transfer, coherent multipart tasks, and unfamiliar applications.

Simple direct questions should remain simple when that is the right task. Do not wrap routine work in stock
reasoning language merely to look rigorous. Values should be pedagogically natural for the target and intended
representation; random-looking numbers do not create useful variety.

Every item has a specific instructional/evidence target. Multi-concept items require a coherent bridge.
Context must affect the mathematics/science/interpretation rather than act as decorative nouns.
Representations must be real when representation reasoning is claimed. Internal authoring labels such as
“Example anchor,” “YTI anchor,” or structure IDs belong in metadata, not student-facing prompt text.

The approved structure library can grow as new resource types are built, but the current build should use the
current approved library rather than inventing a separate hidden architecture.

The project-level `3b_Question_Structure_and_Visual_Toolkit` is a SHARED AUTHORING / VISUAL SUPPORT LIBRARY,
not a separate curriculum product the teacher must manually route every time. A resource-family PM may carry an
embedded copy for portability. When the executable PM already embeds the current Toolkit, that embedded copy
satisfies the workflow and the control panel should not force a redundant second upload. When another workflow
needs the Toolkit but does not embed it, the control panel may add the current canonical Toolkit from `memories/`
automatically.

This shared role is especially important for Physics Notes. The Toolkit's Conceptual Physics source-image catalog
may supply relevant textbook visuals for explanation, discussion, modeling, comparison, and conceptual sense-making.
Use those source visuals generously when they materially improve learning and fit the current Unit/section; do not add
images merely to decorate pages. Preserve source/provenance/licensing requirements and keep the current Framework /
Notes PM in control of final instructional purpose, placement, layout, and deployed path rules.

================================================================
12. OPTIONAL LATER RESOURCES
================================================================

Demonstrations, Investigations, Performance Tasks, and Quick Checks are designed later from Framework/maps unless the
current workflow explicitly includes them. Activities use the dedicated Base Activities workflow. Reviews, Warm-Ups,
Exit Tickets, Progress Trackers, and Summative renderings may use the dedicated Base Recurring + Assessment workflow.
Optional instructional routes must not carry required core instruction that disappears if skipped.

Teacher-live improvements should be preserved during later updates unless explicitly replaced.

================================================================
13. VISUAL / WORKSPACE PHILOSOPHY
================================================================

Visuals are instructional content, not decoration. Source visuals are candidates, not automatically approved.
Workspace, scale, layout, and readability should fit how the teacher/students actually use the resource.
The current course Framework/Notes workflow may define more specific device/print/workspace conventions.

STUDENT-FACING REPRESENTATION CAPTION RULE — UNIVERSAL / LOCKED:
Do not place descriptive captions, titles, source labels, representation labels, or figure-name text beneath a
student-facing graph, table, diagram, diamond, image, or other representation. The prompt introduces the
representation; the representation then stands alone. Do not emit visible `<figcaption>` text such as
"Diamond problem," "Graph of ...," "Figure ...," or similar descriptive labels beneath the representation.
Preserve mathematically/scientifically necessary labels INSIDE the representation itself: axes, tick values,
units, legends when mathematically necessary, point/function labels, force labels, values, and comparable data.
If explanatory wording is necessary for the task, place it in the prompt BEFORE the representation rather than
as a caption beneath it. A course/resource layer may control representation size or placement, but it may not
re-enable descriptive student-facing captions unless the teacher explicitly requests an exception.

================================================================
14. FINAL-BYTE PHILOSOPHY / HUMAN-IN-THE-LOOP
================================================================

Correct curriculum content is not enough if rendering corrupts it.

The authoring chat may deliver an authoring-complete Bank ZIP before local deterministic finalization. The
teacher can inspect readable HTML immediately. The included local finalizer then regenerates figures, fixes
MathJax/final-byte issues, runs deterministic checks, and creates the final deployable ZIP.

Final DEPLOYABLE bytes must pass the local finalizer's hard computer checks. Deterministic tooling should not
silently rewrite curriculum or declare repeated question families bad. Semantic curriculum judgment remains a
teacher/AI review job outside mechanical finalization.

================================================================
15. CANONICAL TASK GRANULARITY
================================================================

A resource set may contain several different questions. A single canonical question should contain one
coherent job unless its parts share a real stimulus, dependency, representation connection, or compare/contrast
bridge. Do not compress independent questions by joining them with “and,” “then,” or “also.”

================================================================
16. BASE / COURSE-SPECIFIC INHERITANCE PRINCIPLE
================================================================

Treat the curriculum memories like layered style rules:

  BASE PHILOSOPHY
    universal beliefs that should survive across courses

  BASE BANK PM
    universal mechanics for constructing/packaging a Bank

  BASE NOTES PM
    universal mechanics for constructing/packaging Notes

  BASE PRACTICE PM
    universal mechanics for rendering/packaging Practice Sets from the finalized Bank

  BASE ACTIVITIES PM
    universal mechanics for selecting/grouping canonical Bank work into approved interactive activity structures

  BASE RECURRING + ASSESSMENT RESOURCES PM
    universal mechanics for rendering/packaging Warm-Ups, Exit Tickets, Progress Trackers, Reviews, and Summatives

  CURRENT COURSE FRAMEWORK
    the course-specific philosophy, exact Assessment Plans/I-cans, response mode, recurring routines,
    abundance pattern, representations, source intelligence, path contracts, and tools

Course-specific rules should live in the Framework instead of accumulating as exceptions inside the Base
Philosophy, Base Bank PM, Base Notes PM, Base Practice PM, Base Activities PM, or Base Recurring + Assessment Resources PM. When a course rule changes, reconcile the Framework and downstream assumptions;
do not add a new override while leaving a contradictory old rule active.


================================================================
17. CANONICAL PROJECT MEMORY ROOT / CONTROL-PANEL RESOLUTION
================================================================

The current project-level authority library lives in one canonical root-level directory named `memories/`,
as a SIBLING of deployed course-site directories rather than inside any one course. For example:

  project root/
    memories/
      _Curriculum_Philosophy_PM.zip
      2_Framework_Algebra_1.zip
      2_Framework_Physics.zip
      2_Framework_CALC.zip
      3a_Base_Bank_PM.zip
      ... current PMs / toolkits / helper tools ...
      curriculum_control_panel_pilot.html
      requests/
        ... generated request ZIPs only ...
    algebra/
      banks/unit1/ ... banks/unitN/
      ... deployed Algebra course site ...
    physics/
      ... deployed Physics course site ...
    calculus/
      ... deployed Calculus course site ...

The root `memories/` directory is the CURRENT AUTHORITY SHELF for build/upgrade/maintenance orchestration.
It is not a student-facing course folder and is not part of any course's deployed path contract. Moving this
authority shelf out of a course directory does not authorize changes to course resource paths, CSS, navigation,
or artifact structure.

Use STABLE CANONICAL FILENAMES in `memories/` for current authorities. When a PM/Framework/tool is upgraded,
replace the canonical file in place rather than keeping several numbered/current-looking copies in the authority
shelf. Version information may live inside the ZIP/text, while the outer canonical filename remains stable.
Archived versions belong outside the current authority shelf.

A local Curriculum Control Panel may live inside `memories/`. Its job is orchestration, not curriculum judgment.
After the teacher grants browser access to the PROJECT ROOT, the panel may resolve the current Framework/PM from
`memories/` by stable filename and may also resolve an unambiguous current Unit Bank from the deployed course path
(e.g. `algebra/banks/unit6/`). When a workflow needs that Bank, the panel may package the Bank folder itself as a
clean temporary ZIP for the request rather than forcing the teacher to manually zip it. Request packaging must not
modify the deployed course and should exclude operating-system junk such as `__MACOSX`, `.DS_Store`, AppleDouble
`._*`, `__pycache__`, and `.pyc` files.

The dedicated `memories/requests/` directory is a STAGING/OUTPUT location for generated request ZIPs. It is NOT part
of the current authority shelf. Generated requests must never be mistaken for PMs, Frameworks, or canonical source
artifacts. A control panel with write permission may save request ZIPs directly there; otherwise it may fall back to
the browser's normal download behavior.

The panel should state the exact required user input in concrete terms such as `Unit 6 Bank ZIP` or `current Algebra
course-site ZIP`, not vague phrases like "source files as needed." When the exact required input already exists at a
known canonical project path and is unambiguous, automatic resolution is preferred. When it cannot be resolved, the
panel should identify exactly what the teacher must select.

For a normal Unit Bank build, if the current Base Bank PM already contains the approved Question Structure + Visual
Toolkit and the current Framework contains the Unit learning/evidence architecture, the Unit selector is sufficient to
identify the Bank target. Do not force a vague mandatory "source/reference files" upload. Additional source files are
OPTIONAL and should be requested only when the teacher is intentionally adding new material not already represented
in the current Framework/Toolkit.

For final build delivery, prefer replacement-ready ZIPs that match the teacher's actual Finder drag/drop workflow.
For Practice-to-Summative all-together delivery, use one Unit root containing the deployed COURSE-PARENT folders
`practice_sets/`, `activities/`, `warmups/`, `exit/`, `progress/`, `reviews/`, and `assessments_zxrtjp/`. Put the
new Unit resources at their canonical relative paths beneath those parents. This lets the teacher place the output
beside the course root and drag the matching parent folders across. Do not nest child ZIP files inside the master.
Offer individual resource ZIPs separately when useful. Exclude `__MACOSX`, `.DS_Store`, AppleDouble `._*`,
`__pycache__`, and `.pyc` from generated packages.

Keep teacher-facing Control Panel output descriptions SHORT. Detailed path/packaging mechanics belong in the request
manifest and executable PM, not in a paragraph the teacher must reread for every run.

A request package should carry its own explicit manifest and execution instruction so the teacher does not have to
retype a conventional chat prompt. A typed external prompt may remain blank when the surrounding platform permits
an attachment-only request.

The panel must never silently substitute a missing authority, infer an older PM copy from a course folder, or override
the selected executable PM. If a required canonical authority or exact input is missing or ambiguous, it should fail
closed and identify the missing item.

The control-panel principle is:
  ONE CURRENT AUTHORITY SHELF -> AUTO-RESOLVE SAFE CANONICAL INPUTS -> EXPLICIT REQUEST MANIFEST -> CORRECT EXECUTABLE PM -> MINIMUM MANUAL UPLOADS.

This structure exists partly to reduce human upload/version mistakes. It does not change the authority hierarchy:
current explicit teacher instruction, current executable PM, current Framework/Assessment Plan, and canonical
Bank/source artifacts still retain their established roles.

================================================================
18. BUILD STAGE VS CURRICULUM MAINTENANCE
================================================================

The initial curriculum BUILD and the long-term maintenance of a deployed course are related but distinct jobs.
Once a course is substantially built, a separate project called CURRICULUM MAINTENANCE should oversee targeted
updating, repairing, polishing, and upgrading of the live course without reopening the whole build architecture
every time a teacher notices a local problem.

Maintenance should default to SURGICAL SCOPE. A maintenance PM may take an existing deployed resource folder or
ZIP, correct the specific requested defect, and return the corrected resource in the SAME folder/file structure so
it can be dropped back into the course safely. For example, an Activities maintenance PM may accept one existing
Activity folder, repair a Find Someone Who worksheet, and return that Activity folder with all unrelated files,
paths, filenames, canonical questions, and approved presentation preserved.

The maintenance principle is:
  FIX THE SMALLEST CORRECT LAYER; PRESERVE EVERYTHING OUTSIDE THAT SCOPE.

A local repair is not permission to redesign the resource, rebuild the Unit, rewrite unrelated questions, update
shared CSS, alter navigation, or change other course folders. Preserve unaffected bytes when practical and make the
changed scope easy to audit. If the requested fix can be completed entirely inside the deployed artifact, do that.

Maintenance must still respect authority boundaries. If a teacher-live defect reveals that the underlying canonical
Bank, Framework, Base PM, shared tool, or Philosophy is actually wrong, distinguish the immediate artifact repair
from the upstream system lesson. Repair the classroom-facing artifact now when appropriate, then deliberately
promote/reconcile the improvement upstream rather than silently causing a broad rebuild.


SYSTEMIC BOTTLENECK / PM IMPROVEMENT LOOP
-----------------------------------------
A real build or maintenance run is also controlled regression testing of the workflow. If execution exposes a
REPEATABLE/SYSTEMIC bottleneck, contradiction, ambiguous ownership rule, missing shell contract, or other PM-level
weakness, do not silently improvise around it and do not silently rewrite current authorities during the run.

First distinguish the owning layer:
- artifact-specific defect -> repair/rebuild the artifact; no PM upgrade proposal is required;
- PM-owned workflow defect -> report it and may return a candidate PM upgrade;
- Framework-owned course rule -> report the Framework conflict instead of patching the PM around it;
- Bank-owned content/mapping defect -> preserve the Bank during downstream work and route the issue to Bank upgrade;
- Philosophy/tool/shared-CSS defect -> report that owning layer explicitly.

When a SYSTEMIC issue is found, return a concise `PM_IMPROVEMENT_REPORT.txt` containing:
1. Problem encountered.
2. Evidence that it is systemic/repeatable rather than artifact-specific.
3. Owning layer.
4. Exact proposed rule/change.
5. Expected benefit / bottleneck removed.
6. Possible collateral impact.
7. Recommendation: ACCEPT ALL / ACCEPT PART / REJECT.

If the active PM itself owns the defect and a safe candidate can be authored, the run MAY also return a clearly labeled
`*_PROPOSED.zip` upgraded PM. A proposed PM is NON-AUTHORITATIVE and must never overwrite the canonical authority
shelf automatically. The teacher reviews the report and accepts all, part, or none of the proposal. Only an approved
revision becomes the new canonical PM.

After an approved PM change, validation is REQUIRED:
1. rerun the exact case that exposed the weakness;
2. audit the revised PM against the current Framework;
3. when Bank-driven, audit the output/routing against the finalized current Bank;
4. regression-check protected resource families, paths, CSS/shells, and authority boundaries;
5. accept the revision only when the original bottleneck is removed without collateral drift.

Do not generate PM-upgrade proposals merely because a single artifact is unusual. The purpose is to promote genuine
system lessons upstream while keeping local exceptions local.

This creates a long-term lifecycle:

  BUILD -> UPGRADE -> DEPLOY/TEACH -> OBSERVE -> TARGETED MAINTENANCE -> PROMOTE UPSTREAM WHEN WARRANTED

Teacher-live improvements are valuable evidence about the curriculum. The goal of Curriculum Maintenance is not to
freeze the course forever; it is to let the course improve continuously while controlling blast radius, preserving
working material, and keeping replacements easy for the teacher to understand and deploy.

19. FINAL OPERATING PRINCIPLES
================================================================

1. PURPOSE BEFORE INVENTORY.
2. EXACT I-CAN / TARGET MAP BEFORE QUESTIONS.
3. EVIDENCE MAP BEFORE EVIDENCE ITEMS.
4. FOR MULTI-ITEM / MULTI-SECTION BUILDS, MAP THE FULL REQUESTED SCOPE BEFORE AUTHORING AND USE THE MAP TO DISTINGUISH PURPOSEFUL REPETITION FROM TEMPLATE-DRIVEN CLONING.
5. THE FRAMEWORK DEFINES COURSE-SPECIFIC EXPRESSION OF THE BASE PHILOSOPHY.
6. REPRESENTATIONS ARE INSTRUCTIONAL CONTENT; PLAN AND ACTUALLY USE APPLICABLE FORMS.
7. USE THE FRAMEWORK GRAPH/FIGURE TOOL WHEN AUTHORING CANONICAL VISUALS; DOWNSTREAM RENDERERS REUSE CANONICAL BYTES.
8. PREDICTABLE ROUTINE IS GOOD.
9. PURPOSEFUL REPETITION IS GOOD.
10. USEFUL ABUNDANCE IS GOOD; THE TEACHER CAN SKIP.
11. ABUNDANCE SHOULD BE COURSE-RESPONSIVE, NOT UNIVERSALLY EVEN.
12. UNDERBUILDING IS A REAL DEFECT.
13. PURPOSELESS FILLER IS BAD.
14. FAKE VARIETY IS BAD.
15. DIRECT QUESTIONS MAY REMAIN DIRECT.
16. MULTIPART REQUIRES A REAL CONNECTION.
17. OPTIONAL LATER RESOURCES MUST NOT CARRY REQUIRED CORE INSTRUCTION.
18. THE BANK IS A MACHINE-READABLE CONTENT FACTORY AND RICH TEACHER MENU.
19. THE LOCAL FINALIZER HANDLES MECHANICAL FINAL BYTES; THE TEACHER JUDGES SEMANTIC QUALITY.
20. STUDENT-FACING QUESTIONS USE NATURAL VALUES/LANGUAGE; INTERNAL AUTHORING LABELS STAY INTERNAL.
21. SUBSTANTIAL NOTES READING SHOULD BE FOLLOWED BY IMMEDIATE SENSE-MAKING / DISCUSSION.
22. USEFUL MATH/MODEL NOTES ABUNDANCE IS GOOD; THE TEACHER CAN SKIP.
23. ACTIVITIES SHOULD CHANGE PARTICIPATION STRUCTURE WITHOUT CASUALLY REWRITING CANONICAL MATHEMATICS.
24. OPTIONAL ACTIVITIES MUST NOT CARRY REQUIRED CORE INSTRUCTION OR SECURE EVIDENCE.
25. DOWNSTREAM MAD-LIB SHELLS SHOULD POPULATE AUTHORITATIVE CONTENT RATHER THAN RE-AUTHOR IT.
26. RESOURCE USAGE MODE (PROJECTOR / NOTABILITY / PRINT / SCREEN) IS PART OF THE DESIGN CONTRACT.
27. TEACHER PROFESSIONAL JUDGMENT REMAINS FINAL.
28. BUILD AND MAINTENANCE ARE DISTINCT PHASES; A MATURE DEPLOYED COURSE SHOULD SUPPORT TARGETED MAINTENANCE WITHOUT FORCING A WHOLE-COURSE REBUILD.
29. MAINTENANCE FIXES THE SMALLEST CORRECT LAYER AND RETURNS REPLACEMENT ARTIFACTS IN THE SAME DEPLOYED STRUCTURE WHEN PRACTICAL.
30. TEACHER-LIVE IMPROVEMENTS MAY BE PATCHED LOCALLY FIRST, THEN DELIBERATELY PROMOTED UPSTREAM WHEN THEY REVEAL A CANONICAL OR SYSTEM-LEVEL LESSON.

31. ONE ROOT-LEVEL `memories/` DIRECTORY IS THE CURRENT PROJECT AUTHORITY SHELF; DEPLOYED COURSE FOLDERS SHOULD NOT CARRY COMPETING AUTHORITATIVE PM COPIES.
32. CONTROL-PANEL AUTOMATION MAY RESOLVE CURRENT AUTHORITIES BY STABLE FILENAME, BUT MUST FAIL CLOSED WHEN A REQUIRED AUTHORITY IS MISSING OR AMBIGUOUS.
33. STABLE OUTER FILENAMES SHOULD POINT TO THE CURRENT PM/FRAMEWORK/TOOL; ARCHIVED VERSIONS BELONG OUTSIDE THE CURRENT AUTHORITY SHELF.
34. `memories/requests/` IS A REQUEST-STAGING FOLDER, NOT AN AUTHORITY SOURCE; GENERATED REQUEST ZIPS MUST NOT BE SCANNED AS CURRENT PMs OR FRAMEWORKS.
35. WHEN A REQUIRED UNIT BANK EXISTS AT AN UNAMBIGUOUS CANONICAL COURSE PATH, THE CONTROL PANEL MAY PACKAGE IT CLEANLY AND AUTOMATICALLY RATHER THAN REQUIRE MANUAL ZIPPING.
36. CONTROL-PANEL REQUEST PACKAGING MUST NOT MODIFY DEPLOYED COURSE FILES AND SHOULD EXCLUDE OPERATING-SYSTEM/PYTHON JUNK FROM TEMPORARY ZIPS.
37. CONTROL-PANEL UI SHOULD NAME THE EXACT REQUIRED INPUT; AUTOMATE SAFE INPUT RESOLUTION WHEN POSSIBLE AND FAIL CLOSED WHEN NOT.
38. A SELF-DESCRIBING REQUEST PACKAGE MAY ELIMINATE THE NEED FOR A REPEATED EXTERNAL CHAT PROMPT.
39. THE QUESTION STRUCTURE + VISUAL TOOLKIT IS SHARED AUTHORING SUPPORT; EMBEDDED COPIES SATISFY WORKFLOWS THAT ALREADY CARRY IT, WHILE OTHER WORKFLOWS MAY RECEIVE THE CURRENT ROOT TOOLKIT AUTOMATICALLY.
40. PHYSICS NOTES SHOULD USE RELEVANT CONCEPTUAL PHYSICS SOURCE VISUALS GENEROUSLY WHEN THEY ADVANCE LEARNING, NOT AS DECORATION.
41. PRACTICE-TO-SUMMATIVE MASTER ZIPS SHOULD USE ONE CLEAN UNIT ROOT WITH THE DEPLOYED COURSE-PARENT FOLDERS (`practice_sets/`, `activities/`, `warmups/`, `exit/`, `progress/`, `reviews/`, `assessments_zxrtjp/`) DIRECTLY INSIDE SO THE TEACHER CAN DRAG/DROP THEM AGAINST THE COURSE ROOT; OFFER CHILD ZIPS SEPARATELY RATHER THAN NESTING THEM INSIDE THE MASTER.
42. CONTROL-PANEL TEACHER-FACING OUTPUT LABELS SHOULD BE SHORT; DETAILED PACKAGING CONTRACTS BELONG IN THE MANIFEST/EXECUTABLE PM.
43. SYSTEMIC RUN-TIME BOTTLENECKS SHOULD PRODUCE A CONCISE PM IMPROVEMENT REPORT INSTEAD OF SILENT WORKAROUNDS.
44. A CANDIDATE SELF-UPGRADED PM IS A NON-AUTHORITATIVE PROPOSAL UNTIL THE TEACHER ACCEPTS ALL OR PART OF IT.
45. AFTER AN APPROVED PM CHANGE, RERUN THE EXPOSING CASE AND AUDIT AGAINST THE CURRENT FRAMEWORK, FINALIZED BANK WHEN APPLICABLE, AND PROTECTED REGRESSION BOUNDARIES.
46. PARALLEL ASSESSMENT DELIVERY FORMS MAY DIFFER IN WORKSPACE/ORDER/VERSIONING WHILE PRESERVING THE SAME EVIDENCE TARGET.
47. PROVIDE THE RESPONSE SURFACE A TASK REQUIRES UNLESS BUILDING THAT SURFACE IS ITSELF PART OF THE EVIDENCE.
