BUILD FIRST 4 DAYS — PORTABLE MEMORY v1.5
=========================================
STATUS: UNIVERSAL BUILD ORCHESTRATOR FOR SPECIAL OPENING-OF-SCHOOL SEQUENCES

PURPOSE
-------
Build a course's special First 4 Days / opening sequence without inventing a fake Unit 0 and without requiring a permanent Unit Bank.

This PM is intended to work with Algebra, Physics, Calculus, and later courses. The CURRENT course Framework supplies course-specific learning architecture, language/tone, paths, representations, tools, and deployed CSS. This PM supplies the universal First 4 Days workflow and carries reference family shells/CSS so the builder does not reconstruct resource architecture from memory.

This is a BUILD PM, not a maintenance/repair PM.

AUTHORITY
---------
1. Current explicit teacher instruction.
2. Current self-contained Course Framework + REQUIRED course-specific First 4 Days opening plan. The opening plan may be supplied as a teacher-authored source file OR generated by the Control Panel from structured teacher inputs. It must establish the requested sequence, resource types/counts, opening learning targets/I-can statements, and course-specific content direction. Supplemental assets may be attached separately. A runnable request with neither a complete structured opening plan nor an authoritative supplied opening-plan source MUST fail closed unless the current Framework explicitly contains an authoritative First 4 Days plan.
3. This Build First 4 Days PM.
4. Bundled current Curriculum Philosophy.
5. Reference shells/CSS inside this PM.
6. Older First 4 Days artifacts only as non-authoritative visual/path examples unless explicitly promoted.

Do not use a stale course Framework frozen inside this universal PM. The request/controller should package the CURRENT Framework with the run. This PM may carry renderer references, but course-specific authority remains the current Framework.

CORE ARCHITECTURE — MAP BEFORE DOCUMENTS
----------------------------------------
Do NOT start by writing questions or HTML.

Before authoring any student artifact, construct a PRIVATE machine-readable pre-authoring JSON map for the COMPLETE requested First 4 Days scope. This is the same thinking discipline used before Bank authoring.

Treat the private map as a TEMPORARY INTERNAL MICRO-BANK:
- exact learning targets / I-can statements first;
- resource-purpose and evidence jobs next;
- representations / participation / portfolio routes next;
- canonical local question instances next;
- render documents only after the map is coherent.

The micro-bank is a build-time thinking/source object, NOT a deployed Bank and NOT a Unit 0 Bank. Do not expose it to students or install it in the normal course banks/ tree unless the teacher explicitly changes the architecture.

PRIVATE PRE-AUTHORING MAP — HARD GATE
-------------------------------------
The map must include at minimum:

course
sequence label / dates if supplied
not_a_unit = true
source learning targets / exact I-can statements
baseline/familiar-skill jobs when the opening sequence intentionally samples prior knowledge
artifact plan
for EACH requested artifact:
  - purpose
  - exact I-can(s) / learning job(s) served
  - baseline skill jobs if any
  - evidence role (instruction / practice / formative / portfolio evidence / orientation)
  - item count or requested structure
  - representation plan
  - participation/use mode
  - question structures
  - accessibility/response-surface needs
  - source/lineage IDs for locally authored canonical items
freshness / cross-resource reuse plan
portfolio routing plan when applicable
CSS / shell ownership
path / filename plan

QA the map BEFORE authoring:
- every requested I-can has an intentional route;
- no artifact exists only because a template usually has it;
- counts match the explicit First 4 Days plan, not normal Unit defaults;
- evidence artifacts are not accidental copies of Practice;
- representation/participation choices fit the learning job;
- exact same instantiated questions do not drift across unrelated resources except where reuse is intentionally part of the approved architecture (for example the common Exit anchor across versions);
- no current learning target is displaced by future-preview material.

A reference schema is bundled at templates/PREAUTHORING_MAP_SCHEMA.json.


STRUCTURED OPENING PLAN — CONTROL PANEL CONTRACT
--------------------------------------------------
The Control Panel should gather course-specific First 4 Days intent BEFORE creating the request ZIP. The PM profile exposes plan_fields so the controller can render these prompts dynamically rather than hard-code this one workflow.

The structured opening plan should ask for, at minimum:
- exact resources / counts to build;
- Warm-Up topics / skill jobs by day;
- Notes learning targets / I-can statements and any special Notes/WTC direction;
- Practice / Extra Practice focus when requested;
- Activity idea / participation goal when requested;
- Investigation / Demo idea, materials, and intended student actions when requested;
- Exit Ticket / portfolio-baseline intent when requested;
- any overview, survey, welcome, naming, scheduling, or other opening details.

The controller packages the completed answers as `inputs/FIRST_4_DAYS_OPENING_PLAN.json`. That JSON is an authority for the run because it is the teacher's current explicit build plan. Uploaded source files/images remain supplemental inputs and may elaborate the structured plan; they do not replace required plan decisions unless they explicitly contain them.

Do not require the teacher to author a separate planning document merely to run this PM when the Control Panel can capture the plan directly.

RESOURCE-PLAN-DRIVEN — HARD

INPUT GATE — HARD
A First 4 Days build requires a course-specific opening plan. Do not infer a default four-day sequence from this PM, from another course, or from normal Unit architecture. The preferred Control Panel path is to ASK the teacher for the plan in structured fields and package those answers as FIRST_4_DAYS_OPENING_PLAN.json. Supplemental source files/assets are optional unless the teacher's plan depends on them. If the structured plan is incomplete and no supplied source or current Framework fills the missing authority, FAIL CLOSED and request only the missing plan information.
---------------------------
Build only resources the teacher requests for this First 4 Days sequence.

Do NOT force normal Unit inventories, section counts, Bank counts, Practice counts, Warm-Up counts, Activity counts, or Summative architecture.

The teacher may specify a plan such as:

- short Notes

FIRST 4 DAYS IS NOT UNIT 0
--------------------------
Never label the sequence Unit 0 unless the teacher explicitly requests that architecture.

Use the course's chosen opening labels such as 0.1 / 0.2 only as section/resource names when supplied. They do not create a hidden spiral unit, Mastery Goal unit, or fake Assessment Plan.

PATCH / RETURN CONTRACT
-----------------------
When returning production files to the teacher, preserve deployability rather than returning an incomplete handful of sibling files.

- If a requested/changed resource family is normally a folder (for example an Activity folder), and the teacher is replacing that family, return the COMPLETE deployable folder with all files that belong in it, including unchanged siblings and required local figures.
- If exactly one file is the complete repair target and no sibling files are needed to deploy it safely, returning that single file is correct. State its exact repository-relative destination path.
- If multiple unrelated First 4 Days files changed, return one course-root-relative patch ZIP containing only the changed complete files/folders needed for drag-and-drop replacement.
- Do not make the teacher reconstruct a deployable family by combining files from several earlier downloads.

CSS / RENDERER OWNERSHIP
------------------------
Reuse CURRENT canonical course resource shells and CSS where they already exist.

Normal deployed course CSS remains the live authority:
- Notes -> current course base.css + notes.css
- Practice -> current course base.css + practice_set.css
- Warm-Ups -> current course base.css + warmup.css
- Exit Tickets -> current canonical exit.css
- Activities -> current course Activity CSS for the selected structure

Reference copies included in this PM are REFERENCE-ONLY. Do not create a second live exit.css, warmup.css, practice_set.css, or other competing course stylesheet inside the First 4 Days branch.

A small misc/first_4_days/first_4_days.css is allowed for genuinely special opening-only artifacts such as the First 4 Days index, course-systems organizer, survey, or custom investigation wrappers. It must not reimplement or override the stable canonical family shells.

NOTES
-----
Opening Notes can be deliberately shorter than a normal instructional section when part of the learning job is learning the device/file/class routine.

Still map Notes BEFORE writing them.

Use only as many Example/YTI pairs as the explicit plan needs. There is no universal First 4 Days pair count. Every Example must be followed by its You Try It; do not replace the YTI with discussion.

A What's To Come (WTC) may be included as a coherent FRQ-like long-range preview. DEFAULT: WTC stays INSIDE the Notes document using the current canonical Notes WTC section/shell; its teacher guidance stays inside the Notes teacher version. Do not create a separate wtc/ branch unless explicit current teacher instruction specifically requests a standalone resource. It may intentionally look difficult. For a future-function preview, an equation alone may be the stimulus; do not provide a graph merely to make the task easier when the teacher wants students to confront function notation and future vocabulary. WTC material may sample extrema, domain/range, intercepts, increasing/decreasing intervals, function notation, modeling features, or other course-appropriate ideas, but it is not current evidence and must not displace the current opening learning targets. Teacher support should facilitate noticing, interpretation, discourse, and questions rather than teach the future procedure.

When supplied learning targets emphasize Notability/device/file routines, pair familiar content with the routine so technology—not new mathematics/science—is the main new difficulty.

PRACTICE + EXTRA PRACTICE
-------------------------
Practice creates learning and gives students a safe place to learn the course routine.

Author the planned Practice inventory from the private map. If Extra Practice is requested, route it over the SAME mapped I-can / baseline-skill jobs with fresh instances. Do not copy the entire Practice set and rename it.

FIRST-4-DAYS PRACTICE RENDERING:
- preserve the canonical Practice shell/CSS;
- when the teacher supplies a canonical blank coordinate-plane image such as misc/printables/plane.png, reuse those exact bytes for ordinary blank graphing surfaces instead of authoring giant inline SVG grids;
- ordinary blank coordinate planes should normally render compactly (about 60% of a full-width oversized grid unless the task needs more);
- when a supported visual such as a Diamond is required, use the current Framework-authoritative graph/figure tool rather than hand-drawing an imitation; across a set, vary which Diamond cells are given when that produces useful completion forms (for example product+sum -> factors, factors -> product+sum, or one factor plus product/sum -> remaining cells) instead of mechanically repeating the same blank-cell pattern;
- opening Practice may need more writing room while students learn the digital workflow; if the teacher requests triple default workspace, use approximately 3x the normal ws-25 default (ws-80 is the canonical practical utility) across Practice and Extra Practice.

INVESTIGATIONS / DEMOS
----------------------
Use the current Framework/family purpose: students should do, observe, measure, build, represent, test, explain, or revise—not merely complete a worksheet with an investigation title.

Opening investigations may be shorter while students are learning tools such as Notability, lab procedures, calculators, or physical manipulatives.

If the teacher supplies a physical-material design (for example cm cubes), preserve the material and stage architecture. Representations such as model -> table -> graph -> verbal/informal rule -> prediction should be mapped intentionally rather than appended as generic requirements.

ACTIVITIES
----------
Select the participation structure AFTER the learning/question map exists.

Activity structure serves the learning job. For an opening sequence, a social structure such as Find Someone Who may be useful when it simultaneously supports worthwhile practice and getting acquainted; do not choose it merely because it is the first week.

When the teacher asks for the NORMAL Activity family, do not return one isolated worksheet. Build the normal deployable Activity branch:

ACTIVITY SHELL / CSS ROUTING — HARD:
- Activity Options hub -> current course `css/activities.css`. The hub is NOT merely a menu of links. Its first screen/page may present the Activity Options, but AFTER that it must contain the normal projectable teacher directions for EVERY activity structure listed on the hub. Each projectable directions section/page should preserve the current course Activity look and include, as appropriate: activity name/title, learning/topic label, STRUCTURE, SETUP, DIRECTIONS, GOAL or participation purpose, links to the relevant question/station/handout file, and paired green `Looks Like Success` / red `Doesn’t Look Like` expectation boxes. Keep a clear `Activity Options` return/navigation link on the projectable directions pages. These directions are classroom-display/teacher-use material, not extra student worksheets.
- Projected question/solution sets -> current course `css/activities.css` AND canonical markup: `page question-page` / `page solution-page`, `prob-head`, `prob-num`, `prob-q`, `work`, `solution`. Do not invent substitute classes such as `activity-question-page` / `activity-solution-page` when the live CSS expects the canonical classes. The canonical question header is green; the solution header is red.
- Stations -> current course `css/activities/activity_stations.css`; preserve the approved landscape 2x2 station grid and duplex page sequence. Do not point Stations at the generic activities.css.
- Find Someone Who -> current course `css/activities/activity_find_someone_who.css` when that stylesheet exists in the current course.
- Use the current deployed course subfamily CSS paths; bundled copies are reference-only.

  activities/0_1_act1/
    0_1_act1.html                     Activity Options hub
    0_1_set1_questions_solutions.html
    0_1_set2_questions_solutions.html
    0_1_set1_stations.html
    0_1_set2_stations.html
    0_1_find_someone_who.html         when requested
    0_1_activity_teacher_guide.html
    figures/                           only when needed

The two full question sets are mapped local canonical pools. Projection/whiteboard participation structures reuse those sets. Stations reuse the same set mathematics in the approved duplex print architecture: each station question page is followed by an empty page; solution material follows with two pages reserved per station so duplex printing remains aligned even when a solution fits on one page. Find Someone Who may intentionally be a shorter social handout rather than another full 24-question set when the teacher requests that form.

When no permanent Bank exists, direct-author the Activity question pools from the same private map and give every local question a stable internal lineage ID for QA.

Teacher guide/discourse is required for the Activity family. It should explain which participation structure serves which classroom/learning need and include contextual Teacher/Student moves rather than generic repeated bullets.

WARM-UPS
--------
Build the exact number and content jobs requested. Opening Warm-Ups may intentionally sample familiar prerequisite skills while students learn the opening routine.

Unless explicit current instruction says otherwise, package ALL First 4 Days Warm-Ups in ONE HTML file, following the normal Unit warm-up pattern rather than one HTML per day. Individual day/page sections live inside that combined document and the First 4 Days index links to the combined Warm-Up file.

Use the current canonical warmup.css. Reuse canonical blank printables such as plane.png for ordinary blank coordinate grids. Use the Framework-authoritative graph tool for supported generated visuals such as Diamond problems.

Do not automatically route opening Warm-Ups through normal Unit retrieval/spiral assumptions when the sequence is explicitly outside normal Units.

EXIT TICKETS / PORTFOLIO BASELINE
---------------------------------
When the teacher designates opening Exit Tickets as portfolio baseline evidence, treat them as evidence—not extra Practice.

Each opening Exit Ticket uses the CURRENT approved canonical Exit architecture unless explicit current instruction changes it:
A. Project/display Version 1: four questions visible 2 x 2.
B. Print/collect: four student versions, two portrait pages per version, two questions per page, appropriate response room/accessories.

Because First 4 Days may have no Bank:
- author four Version 1 questions from the private map;
- treat those four V1 questions as the LOCAL canonical source set for that ticket;
- derive V2-V4 downstream.

Evidence roles:
- Anchor = local V1 Q1; exact same question across all four versions.
- Parallel A = local V1 Q2; V2-V4 direct number/value/context-detail parallels preserving evidence.
- Parallel B = local V1 Q3; V2-V4 direct number/value/context-detail parallels preserving evidence.
- Variation = local V1 Q4; V2-V4 comparable evidence-aligned variation.

Balanced four-version scramble whenever possible:
V1: Anchor, Parallel A, Parallel B, Variation
V2: Parallel A, Parallel B, Variation, Anchor
V3: Parallel B, Variation, Anchor, Parallel A
V4: Variation, Anchor, Parallel A, Parallel B

Renumber displayed questions after scrambling. Preserve evidence role/source lineage in non-visible metadata.

Response accessories are evidence-driven. Supply a coordinate plane, unit circle, number line, table/grid, diagram, etc. only when needed to express the intended evidence and constructing the scaffold is not itself the target. When the current course supplies the approved reusable blank surface (for example `misc/printables/plane.png`), reuse those canonical bytes and the canonical Exit image class instead of hand-authoring a giant inline SVG coordinate plane. This applies to both Project and Print versions and prevents response accessories from escaping the Exit size contract.

Do not rewrite the global live exit.css inside this branch.

COURSE SYSTEMS / OVERVIEW / SURVEY
----------------------------------
Opening sequences may include course-system artifacts that normal Units do not.

Overview/organizer:
- use exact supplied course-system facts when available;
- if the teacher has not supplied exact grading, policy, portfolio, or procedural details, make a guided organizer/workspace rather than inventing policy.

Survey:
- keep it brief and useful for instruction;
- ask about learning habits, confidence, goals, course tools, and support preferences when useful;
- do not require sensitive personal information.

PORTFOLIO PRINCIPLE
-------------------
Follow the current Philosophy and Framework. Instruction creates opportunities to learn; assessment collects evidence; the portfolio organizes evidence over time; the grade communicates the best current professional judgment of understanding.

Do not make the teacher restate settled portfolio architecture when the current Philosophy/Framework already contains it.

TEACHER GUIDES / DISCOURSE
--------------------------
Where the current teacher-guide architecture calls for discourse support, include concise, contextual Teacher and Student Moves tied to that exact phase/I-can. Do not paste an identical generic discourse box everywhere.

For an Investigation, teacher moves may include anticipate/monitor/select/sequence/connect where they actually help. For an opening social Activity, emphasize explanation/listening/compare rather than speed. A WTC requires teacher guidance in the Notes teacher version by default: protect productive confusion, ask students to interpret familiar words/notation, revoice partial ideas, and avoid turning the preview into premature direct instruction. Only create a separate WTC teacher guide when a standalone WTC was explicitly requested.

Teacher Notes do not need to preserve student Notability writing geometry rigidly; teacher-only guidance may expand as needed. Student files must preserve their actual usage-mode geometry.

FRESHNESS / INDEPENDENCE
------------------------
The private micro-bank is not permission to repeat one exact item everywhere.

Use common learning jobs across resources while authoring fresh instances appropriate to each resource. Exact reuse is allowed only when purposeful and explicitly part of the architecture, such as an Exit anchor across its four versions or a teacher key reproducing its matching student question.

INDEX
-----
Every completed First 4 Days branch gets a clear index.html.

The index should organize resources by day/section when the plan supplies a day sequence and should distinguish student vs teacher resources. Links must be relative and path-checked.

PM SELF-IMPROVEMENT / BOTTLENECK REPORT
---------------------------------------
Real First 4 Days builds are also controlled PM testing.

If this PM encounters a repeatable/systemic bottleneck, conflict, ambiguity, shell ownership issue, or missing renderer contract:
- finish safely if possible;
- do NOT silently rewrite this PM;
- return a short PM IMPROVEMENT REPORT containing:
  Problem encountered
  Owning layer
  Proposed change
  Why
  Possible collateral impact
  Recommended action: ACCEPT ALL / ACCEPT PART / REJECT

After teacher approval, update only the smallest owning layer, rerun the exact artifact that exposed the problem, audit against Framework and other current authorities, regression-check protected artifacts/layout/paths, and only then call the new PM version good.

Artifact-specific oddity -> repair the artifact; do not grow the PM unless the issue is genuinely repeatable/systemic.

CROSS-COURSE REUSE
------------------
This PM is deliberately universal.

Algebra, Physics, and Calculus may have different opening content, artifacts, response surfaces, representations, tools, and CSS. Do not copy Algebra-specific counts/content into another course. The shared architecture is:

  current Framework + REQUIRED explicit opening plan/sources
    -> private exact-I-can JSON map / temporary micro-bank
    -> mapped local canonical content
    -> canonical family rendering + special opening artifacts
    -> First 4 Days index
    -> deployment patch
