THIS IS AN ORCHESTRATOR ONLY.

CORE RULE — HARD
----------------
DO NOT embed, restate, summarize, reconstruct, or reinterpret child PM logic here.

The CURRENT registered child PM is the sole procedural authority for its artifact.
If this orchestrator and a child PM appear to disagree about that child's content,
rendering, shell, security, QA, path, or source rules:

  THE CHILD PM WINS.

This PM exists so the teacher can run the existing PM stack with one Control Panel request
without maintaining a second duplicate implementation.

============================================================================
4A. CHILD PASS ACCEPTANCE / SHELL-CONFORMANCE GATE — ABSOLUTE HARD
============================================================================

A child's own statement of PASS is NECESSARY but NOT SUFFICIENT for Step 12 to accept it.

Before freezing the child, perform a STATIC conformance check of the child's emitted deployable
files against the CURRENT child PM and the exact live/deployed shell exemplar(s) that child PM
required. This check does NOT rewrite the child and is NOT a second authoring/render pass.

Derive the conformance checks from the active child PM; do not hardcode a substitute shell here.
At minimum, verify every deterministic shell rule the child PM declares, including as applicable:
- exact stylesheet hrefs and order;
- required outer/body wrapper topology;
- required structural class names and IDs;
- required title/header structure;
- deterministic page/section counts and ordering;
- question/solution page alternation when declared;
- workspace/response-surface placement when declared;
- table hooks when declared;
- figure/graph/diagram wrapper classes when declared;
- student-facing caption prohibitions when declared;
- MathJax head contract when declared;
- prohibited inline CSS / extra stylesheet / invented wrapper behavior;
- required hidden traceability metadata when declared;
- required representation presence and relative asset references.

LIVE-SHELL PARITY — HARD
When the child PM names the current deployed HTML/CSS as implementation authority, compare the
new artifact's shell fingerprint against the applicable exemplar. The fingerprint is structural,
not curricular. It includes only shell behavior such as:
- stylesheet sequence;
- top-level DOM hierarchy;
- required recurring class/ID hooks;
- declared page topology/order;
- representation wrappers;
- print/page shell hooks.

Do NOT compare or copy old curricular text.

PASS REJECTION — HARD
If any emitted file violates a deterministic HARD shell/render rule from the child PM:
1. reject that child's claimed PASS;
2. do NOT freeze the child;
3. return control to the SAME child PM with the exact violated rule/path;
4. allow the child to correct its own output under its own PM;
5. rerun that child's own QA and this acceptance gate;
6. only then accept/freeze the child.

The orchestrator itself must not patch the HTML.

If the child cannot satisfy its own shell after correction:
  STOP and report the child's own failure classification.

Examples of things that MUST NOT be accepted merely because files open successfully:
- replacing a required deployed wrapper/class topology with generic `<main>/<section>` markup;
- emitting a simplified hub instead of the declared live hub shell;
- omitting declared figure/graph wrappers;
- adding visible metadata/title blocks the PM forbids;
- substituting generic workspace blocks for a declared response surface;
- dropping a required representation while keeping only its prompt text.
