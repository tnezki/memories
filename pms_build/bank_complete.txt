BUILD COMPLETE BANK — STEP 3B / EXECUTE ACCEPTED MAP
====================================================

STATUS: CURRENT
STEP: 3b
JOB: bank_complete
ROLE: Build or repair one complete canonical Unit Bank by executing one accepted Step 3a Bank Map.

CORE PRINCIPLE
Assessment Plan -> accepted Bank Map -> Complete Bank -> downstream artifacts.
Step 3b AUTHORS the accepted design. It does not redesign Step 3a.

AUDITED-MAP HANDOFF — HARD
A deployed Step 3a map with MAP_MANIFEST.status = PASS and a completed Audit + Rebuild PASS is the accepted executable design contract for Step 3b.
Step 3b does NOT proactively re-audit the 208 design slots, re-derive curriculum routing, or reopen passed Question Structure decisions.
A newer repository/PM commit, provenance date, retrieval-pointer cleanup, source-policy cleanup, delivery/checkpoint change, or other non-design maintenance change does NOT invalidate the accepted map.

Reopen Step 3a only when:
- the accepted map fails its own manifest/hash/fingerprint entry gate; OR
- the current request explicitly identifies a material design-authority change; OR
- authoring exposes one specific concrete contradiction between the accepted map and a current HARD authority.

Otherwise: TRUST THE ACCEPTED MAP AND AUTHOR.

GOOD-ENOUGH EXECUTION — HARD
Follow the Curriculum Philosophy good-enough rule. Finish the declared complete Bank, run the required deterministic QA once in batches, repair concrete failures, rerun only affected checks, and STOP when the HARD contract passes.
Do not spend build time chasing optional polish, rereading passed authorities for reassurance, or improving valid questions merely because another version could be prettier or more novel.

================================================================
0. SOURCE BOUNDARY — HARD
================================================================

For a Curriculum Control Panel job, use ONLY:
- current request/current explicit teacher instruction;
- request-provided files;
- exact pinned canonical project GitHub sources declared by the request/system.

Do NOT use:
- prior chats or remembered project facts;
- ChatGPT File Library recovery;
- stale uploads/old request packages unless the CURRENT request explicitly identifies one as input;
- public web search/fetch or outside curriculum sources.

Direct pinned project GitHub reads are allowed because they are the declared canonical project source. Open-ended web research is not.

A PM may narrow sources further. It may NOT broaden a source boundary prohibited by the current request/runtime.
If a required canonical project dependency cannot be read, FAIL CLOSED as BANK_REQUIRED_PROJECT_SOURCE_MISSING with exact repo + commit + path.

Pin system/course commits once. No mixed commits.

================================================================
1. AUTHORITY ORDER
================================================================

1. current explicit teacher instruction / current request
2. current Curriculum Philosophy
3. current universal Question Structure
4. current Course Framework + exact Unit Assessment Plan + declared operational maps
5. current Framework Bank profile
6. accepted Step 3a Bank Map (PASS)
7. this PM
8. registered tools/render contracts

The accepted Step 3a map is executable design authority.
An existing Bank may be an authored starting artifact in REPAIR mode; it is never curriculum authority.

EXECUTION-ONLY READ RULE — HARD
After the accepted audited map passes the entry gate, do not reread the full Unit Assessment Plan or operational maps to reconstruct fields already carried by the map.
For normal BUILD, read only what is needed to EXECUTE mapped records:
- Curriculum Philosophy good-enough/source boundary;
- current Question Structure definitions actually referenced by mapped records, only as needed to author their behavior;
- Framework Bank/representation rules and current Bank profile;
- registered tool/render/CSS contracts actually used.
If a required target/evidence/identity field is missing from the accepted map, treat that as BANK_MAP_NOT_ACCEPTED rather than rebuilding the missing design inside Step 3b.

================================================================
2. DO THESE STEPS IN ORDER
================================================================

1. Pin current system/course snapshots.
2. Read the accepted deployed source_map/ and this PM's required execution authorities ONCE.
3. Verify accepted map PASS, required slices, declared hashes/fingerprint, and audit PASS when recorded.
4. Select BUILD or REPAIR.
5. Build one expected-record table directly from the accepted map.
6. Author/repair all canonical destinations. For Algebra author in this order: Exit -> Summative V1 -> V2-V4 -> V5-V6 -> Practice 1 -> WTC -> Seeds.
7. Generate all required representations/assets with registered tools/routes.
8. Build ITEM_INDEX + PROVENANCE + byte-faithful source_map snapshot.
9. Run representation/graph/prompt/security/viewer checks as BATCH QA, not repeated per-record rediscovery.
10. Generate MAP_FIDELITY_REPORT.json + RENDER_QA_REPORT.json.
11. Build/update teacher inspection viewer from canonical root CSS.
12. Repair only concrete QA failures and rerun only affected QA plus required final checks.
13. Run universal finalization.
14. Produce the complete canonical Bank tree, wrap/transfer per current runtime, STOP.

DO NOT:
- redo Step 3a design work;
- re-derive I Can/evidence routing already encoded in the accepted map;
- re-audit every Question Structure mapping that already passed Step 3a + Audit/Rebuild;
- compare old/retired Bank architectures;
- reread unchanged authorities for reassurance;
- search File Library, public web, old chats, or historical packages;
- voluntarily stop to create a checkpoint while production can continue.

================================================================
3. ENTRY GATE — ACCEPT THE AUDITED MAP
================================================================

REQUIRE
- MAP_MANIFEST.status = PASS
- question_design.status = PASS when present
- map qa.status = PASS when present
- every slice declared by MAP_MANIFEST readable
- required MAP_REPORT semantic audit present/PASS
- declared map file hashes/fingerprint verify
- current Audit + Rebuild PASS when the map records a later audit snapshot

If the map fails its own gate: BANK_MAP_NOT_ACCEPTED.

TRUST BOUNDARY — HARD
Passing Step 3a + Audit/Rebuild means design work is DONE for Step 3b.

Do not proactively compare the full current Philosophy, Question Structure, Framework, Assessment Plan, operational maps, or Bank profile against old generation pins simply because the repository commit changed.

Treat changed repository SHA, PM version, audit date, retrieval pointer, packaging rule, source-policy wording, finalization mechanics, or viewer procedure as non-design drift unless the current request explicitly says the design authority changed.

If authoring exposes a SPECIFIC concrete contradiction that makes a mapped record impossible or invalid:
- name the exact map record + exact current HARD authority conflict;
- stop as BANK_MAP_AUTHORITY_CHANGED or BANK_MAP_SEMANTIC_MISMATCH;
- return Step 3a for targeted repair.

Do not turn one concrete contradiction into a full speculative re-audit of all design slots.

================================================================
4. BUILD VS REPAIR
================================================================

BUILD when:
- no usable current Bank exists;
- accepted map fingerprint/record identity changed;
- semantic design changed;
- existing Bank is too incomplete/contaminated to repair safely.

REPAIR when:
- current deployed Bank exists at the pinned course commit;
- accepted_map_fingerprint matches;
- canonical record IDs reconcile;
- defects are localized to authored wording/values, representations, rendering, viewer behavior, metadata, QA, or packaging within accepted variation contracts.

In REPAIR:
- current Bank is the authored starting artifact only;
- read/materialize it from the declared pinned course repository or current request input;
- do not search File Library or public web for a previous package;
- preserve untouched records byte-for-byte when practical;
- identify touched records/surfaces explicitly;
- rerun MAP_FIDELITY + RENDER_QA across the COMPLETE final Bank.

If required current Bank bytes/assets cannot be materialized through allowed project sources/current request, FAIL CLOSED as BANK_CURRENT_ARTIFACT_UNAVAILABLE rather than searching elsewhere.
If repair reveals widespread semantic drift, switch to BUILD.

================================================================
8. QUESTION / MATH QUALITY
================================================================

Every finished question must materially execute its mapped Question Structure. Metadata label alone is not enough.

Purposeful repetition is allowed. Mechanical finished-prompt cloning is not the default.
Across the whole Unit, vary allowed stem/values/representation/context/comparison/misconception as useful without fake noun swaps or arbitrary difficulty inflation.

Selected matching/classification order may not leak answers.

ALGEBRA MATHJAX
Use \( ... \) and \[ ... \] when useful.
Do not use `$...$` as inline MathJax because currency must remain normal text.
Avoid needless duplicate display of the same equation while still satisfying required equation representation.

================================================================
9. REPRESENTATION CONTRACT — HARD
================================================================

representation_mode describes what students can actually see/use.
QA must inspect finished student_html, not trust metadata labels.

Examples:
- mixed_graph_table => visible graph + visible table
- mixed_table_equation => visible table + visible equation
- mixed_graph_equation => visible graph + visible equation
- mixed_graph_table_equation => all three
- student_constructed_* => visible answer-neutral construction surface

Missing required visible component = REPRESENTATION_COMPONENT_MISSING.

TABLES
Use semantic HTML table when mapped. For Algebra small value tables use `<table class="values">` and canonical root CSS.

GRAPHS
When accepted route names registered graph tool:
- execute registered tool unchanged as instructed;
- save generated asset;
- reference it in student_html;
- preserve render_trace/tool identity/hash/dimensions as available.

Do not claim registered-tool provenance while using hand-built coordinate/function SVG.

Graph semantics:
- discrete = points only unless map explicitly connects;
- continuous = continuous relationship;
- no answer-revealing special marker/callout;
- every prompt-required graph feature/value must be visible inside bounds with usable margin;
- preserve native/square aspect as required.

Out-of-view required evidence = GRAPH_REQUIRED_EVIDENCE_OUT_OF_VIEW.

GOOD-ENOUGH STOP
When every HARD check above passes, MAP_FIDELITY mismatch_count = 0, RENDER_QA issue_count = 0, BANK_MANIFEST is COMPLETE/PASS, and FINALIZATION_QA passes:
  STOP AND DELIVER.
Do not start another optional polish cycle.

================================================================
14. WORK CHECKPOINT / CONTINUATION — EMERGENCY ONLY
================================================================

A fresh BUILD must attempt to finish the complete Bank in the CURRENT run.

Checkpointing is NOT a planned build phase and is NOT a normal stopping point.
Do not voluntarily stop after a destination, time estimate, or arbitrary amount of work just to return a checkpoint.

A staging checkpoint may be maintained silently while working, but return a continuation package only when execution is actually forced to stop by runtime/tool limits and the complete Bank cannot be finished in the current run.

If forced continuation is necessary:
- package CURRENT staging work only;
- record completed destinations/assets/QA and exact next phase;
- on `cont`, resume immediately from that checkpoint;
- do not restart authority discovery;
- do not search File Library, old chats, or old packages;
- do not return repeated checkpoints while productive execution can continue.

The target behavior for a normal fresh Unit Bank BUILD is:
  one request -> one production run -> one complete transfer ZIP.
