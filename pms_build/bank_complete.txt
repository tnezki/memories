BUILD COMPLETE BANK — STEP 3B / EXECUTE ACCEPTED MAP
====================================================

STATUS: CURRENT
STEP: 3b
JOB: bank_complete
ROLE: Build or repair one complete canonical Unit Bank by executing one accepted Step 3a Bank Map.

CORE PRINCIPLE
Assessment Plan -> accepted Bank Map -> Complete Bank -> downstream artifacts.
Step 3b AUTHORS the accepted design. It does not redesign Step 3a.

================================================================
0. SOURCE BOUNDARY — HARD
================================================================

For a Curriculum Control Panel job, use ONLY:
- current request/current explicit teacher instruction;
- request-provided files;
- exact pinned canonical project GitHub sources declared by the request/system.

Do NOT use:
- prior chats or remembered project facts;
- ChatGPT File Library recovery;
- stale uploads/old request packages unless the CURRENT request explicitly identifies one as input;
- public web search/fetch or outside curriculum sources.

Direct pinned project GitHub reads are allowed because they are the declared canonical project source. Open-ended web research is not.

A PM may narrow sources further. It may NOT broaden a source boundary prohibited by the current request/runtime.
If a required canonical project dependency cannot be read, FAIL CLOSED as BANK_REQUIRED_PROJECT_SOURCE_MISSING with exact repo + commit + path.

Pin system/course commits once. No mixed commits.

================================================================
1. AUTHORITY ORDER
================================================================

1. current explicit teacher instruction / current request
2. current Curriculum Philosophy
3. current universal Question Structure
4. current Course Framework + exact Unit Assessment Plan + declared operational maps
5. current Framework Bank profile
6. accepted Step 3a Bank Map (PASS)
7. this PM
8. registered tools/render contracts

The accepted Step 3a map is executable design authority.
An existing Bank may be an authored starting artifact in REPAIR mode; it is never curriculum authority.

================================================================
2. DO THESE STEPS IN ORDER
================================================================

1. Pin current system/course snapshots.
2. Read accepted map + required current authorities ONCE.
3. Verify map status, required slices, hashes/fingerprint, and targeted authority compatibility.
4. Select BUILD or REPAIR.
5. Build expected-record table from accepted map.
6. Author/repair every canonical destination exactly to mapped identity/behavior.
7. Generate required representations/assets with registered tools/routes.
8. Build ITEM_INDEX + PROVENANCE + source_map snapshot.
9. Run representation/graph/prompt/security/viewer scans.
10. Generate MAP_FIDELITY_REPORT.json.
11. Generate RENDER_QA_REPORT.json.
12. Build/update teacher inspection viewer from canonical root CSS.
13. Run final canonical QA + universal finalization.
14. Produce the complete canonical Bank tree, wrap/transfer per current runtime, STOP.

Do not re-run Step 3a design work when the accepted map already passes and no concrete map defect is found.
Do not reread unchanged authorities for reassurance.
Do not inspect historical Banks/retired templates unless a current hard dependency requires it.

================================================================
3. ENTRY GATE / COMPATIBILITY
================================================================

REQUIRE
- MAP_MANIFEST.status = PASS
- question_design.status = PASS when present
- map qa.status = PASS when present
- every slice declared by MAP_MANIFEST readable
- required MAP_REPORT semantic audit present/PASS
- declared map file hashes/fingerprint verify

If not: BANK_MAP_NOT_ACCEPTED.

PIN COMPATIBILITY — HARD
A repository HEAD SHA change alone does NOT invalidate an accepted map.

When current request pins are newer than map generation pins:
1. preserve the accepted map snapshot/fingerprint;
2. compare only relevant higher-authority content that could change design meaning:
   - Philosophy
   - Question Structure
   - Framework
   - exact Unit Assessment Plan
   - operational maps actually used
   - Bank profile
   - registered executable tools/routes when relevant;
3. harmless unrelated changes = COMPATIBLE_DRIFT;
4. a material higher-authority change that changes accepted design meaning = BANK_MAP_AUTHORITY_CHANGED and Step 3a must be repaired first.

Do NOT rerun Step 3a merely because this PM, viewers, unrelated Units, agendas, or repository SHA changed.

TARGETED SEMANTIC RECHECK
Trust the accepted PASS map/report as starting evidence.
Reopen mapped structure/route definitions only when a concrete ambiguity or conflict exists.
A real map structure/action/response/representation conflict = BANK_MAP_SEMANTIC_MISMATCH.

================================================================
4. BUILD VS REPAIR
================================================================

BUILD when:
- no usable current Bank exists;
- accepted map fingerprint/record identity changed;
- semantic design changed;
- existing Bank is too incomplete/contaminated to repair safely.

REPAIR when:
- current deployed Bank exists at the pinned course commit;
- accepted_map_fingerprint matches;
- canonical record IDs reconcile;
- defects are localized to authored wording/values, representations, rendering, viewer behavior, metadata, QA, or packaging within accepted variation contracts.

In REPAIR:
- current Bank is the authored starting artifact only;
- read/materialize it from the declared pinned course repository or current request input;
- do not search File Library or public web for a previous package;
- preserve untouched records byte-for-byte when practical;
- identify touched records/surfaces explicitly;
- rerun MAP_FIDELITY + RENDER_QA across the COMPLETE final Bank.

If required current Bank bytes/assets cannot be materialized through allowed project sources/current request, FAIL CLOSED as BANK_CURRENT_ARTIFACT_UNAVAILABLE rather than searching elsewhere.
If repair reveals widespread semantic drift, switch to BUILD.

================================================================

  source_map/

Do not duplicate the full source-map record into each Bank record.

Any bundled source-map mismatch = SOURCE_MAP_SNAPSHOT_MISMATCH.

================================================================
7. CURRENT INVENTORY / DESTINATION CONTRACTS
================================================================

Author exactly destinations declared by accepted map/current profile.
Do not revive retired inventory because old files/history exist.

Current Algebra architecture:
- Exit
- secure Summative V1-V6
- Practice 1
- WTC
- approved/useful Seeds

EXIT
Execute the accepted Exit map exactly, including NEW/REASSESS role, carry-forward source, target, evidence job, structure, response, representation, and fresh-parallel variation.

SUMMATIVE — SECURE
Author every accepted secure form/slot as finished secure content: prompt/stimulus, mapped metadata, required representations, key, solution/scoring criteria, form/slot/family provenance.
Do not expose secure prompts/keys in the public inspection viewer.
Do not pad forms merely to consume time.

PRACTICE 1
Execute accepted Practice map exactly.
For current Algebra: 24 per section = 8 Intro + 8 Review + 8 Mastery.
Do not copy secure Exit/Summative prompts into Practice.

WTC
Execute accepted shared-stimulus multipart plan exactly.
For current Algebra: meaningful shared setup followed by Part A/B/C/D.
All parts use same situation/stimulus.
Preserve only real mapped dependencies; multipart formatting alone is not a multistep chain.

SEEDS
Preserve mapped seed identity, durable idea, and variation guidance. No filler quota.

================================================================
8. QUESTION / MATH QUALITY
================================================================

Every finished question must materially execute its mapped Question Structure. Metadata label alone is not enough.

Purposeful repetition is allowed. Mechanical finished-prompt cloning is not the default.
Across the whole Unit, vary allowed stem/values/representation/context/comparison/misconception as useful without fake noun swaps or arbitrary difficulty inflation.

Selected matching/classification order may not leak answers.

ALGEBRA MATHJAX
Use \( ... \) and \[ ... \] when useful.
Do not use `$...$` as inline MathJax because currency must remain normal text.
Avoid needless duplicate display of the same equation while still satisfying required equation representation.

================================================================
9. REPRESENTATION CONTRACT — HARD
================================================================

representation_mode describes what students can actually see/use.
QA must inspect finished student_html, not trust metadata labels.

Examples:
- mixed_graph_table => visible graph + visible table
- mixed_table_equation => visible table + visible equation
- mixed_graph_equation => visible graph + visible equation
- mixed_graph_table_equation => all three
- student_constructed_* => visible answer-neutral construction surface

Missing required visible component = REPRESENTATION_COMPONENT_MISSING.

TABLES
Use semantic HTML table when mapped. For Algebra small value tables use `<table class="values">` and canonical root CSS.

GRAPHS
When accepted route names registered graph tool:
- execute registered tool unchanged as instructed;
- save generated asset;
- reference it in student_html;
- preserve render_trace/tool identity/hash/dimensions as available.

Do not claim registered-tool provenance while using hand-built coordinate/function SVG.

Graph semantics:
- discrete = points only unless map explicitly connects;
- continuous = continuous relationship;
- no answer-revealing special marker/callout;
- every prompt-required graph feature/value must be visible inside bounds with usable margin;
- preserve native/square aspect as required.

Out-of-view required evidence = GRAPH_REQUIRED_EVIDENCE_OUT_OF_VIEW.
