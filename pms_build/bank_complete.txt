1. ENTRY GATE / COMPATIBILITY
===============================================================================

ENTRY GATE — HARD

- map qa.status = PASS when that field exists
- every destination slice declared by MAP_MANIFEST is readable

ACCEPTED MAP FINGERPRINT — HARD
- Recompute/verify the accepted map fingerprint according to MAP_MANIFEST.
- Verify the accepted map file hashes when MAP_MANIFEST declares them.
- Do not silently substitute a newer map.

PIN COMPATIBILITY — HARD
A repository HEAD SHA change by itself does NOT invalidate an accepted map.

When request pins are newer than the map's repository pins:
1. verify the accepted map snapshot and fingerprint are unchanged;
2. identify only the higher-authority files that could change the map's meaning:
   - Curriculum Philosophy
   - Question Structure authority
   - Course Framework
   - exact Unit Assessment Plan
   - canonical operational maps used by the Unit
   - Bank profile
   - registered tools/render contracts when their behavior is part of executable map routes;
3. compare those actual authority identities/content, not the whole repository commit;
4. harmless changes elsewhere in the repository are COMPATIBLE_DRIFT and do not require Step 3a;
5. if a relevant higher authority materially changed the accepted design meaning, stop as BANK_MAP_AUTHORITY_CHANGED and require a new Step 3a map.

Do not rerun Step 3a merely because Bank outputs, viewers, agenda files, unrelated Units, or this PM changed.

TARGETED SEMANTIC RECHECK — HARD
Use the accepted PASS map/report as starting evidence. Do not redo the full Step 3a design audit.
Reopen only the structure/route definitions actually used by the accepted map when a concrete ambiguity exists.
If the accepted map itself contains a real structure/action/response/representation conflict, fail as BANK_MAP_SEMANTIC_MISMATCH.

===============================================================================
2. EXECUTION MODE
===============================================================================

MODE SELECTION — HARD
Step 3b supports two internal execution modes:

A. BUILD
Use when:
- no usable current Bank exists;
- the accepted map fingerprint changed;
- canonical record identity changed;
- semantic design changed;
- the existing Bank is too incomplete or contaminated to repair safely.

BUILD authors the complete Bank from the accepted map.

B. REPAIR
Use when:
- a current Bank exists;
- its accepted_map_fingerprint matches the accepted Step 3a map;
- its canonical record ID set can be reconciled to the accepted map;
- requested defects are localized to authored wording/values, representations, rendering, viewer behavior, metadata exposure, QA, packaging, or other fixes allowed by the accepted variation contracts.

REPAIR is preferred over full reauthoring when most current authored records are already good.

REPAIR MODE — HARD
In REPAIR mode:
- accepted map remains authority;
- current Bank is only the authored starting artifact;
- materialize the complete prior Bank locally as early as possible using the FULL BANK ARTIFACT RECOVERY order below;
- identify an explicit touched-record/touched-surface set;
- preserve untouched authored records byte-for-byte when practical;
- repair touched records only inside their accepted map variation contracts;
- rebuild affected assets;
- rebuild viewer/reports/manifest as needed;
- rerun MAP_FIDELITY and RENDER_QA across the COMPLETE final Bank, not only touched records;
- package a complete replacement Bank, never a partial overlay.

If repair discovers widespread semantic drift, stop repair and switch to BUILD rather than layering more patches.

3. EXECUTION / CONTINUATION DISCIPLINE
===============================================================================

SOURCE-READ BUDGET — HARD
- Use request-declared and manifest-declared paths directly.
- Read each unchanged authority once per pinned/content identity.
- Record identities in the checkpoint.
- Do not repeatedly reread Philosophy, Framework, Assessment Plan, Question Structure, Bank profile, accepted map slices, or registered tools for reassurance.
- Do not inspect historical Banks/retired templates unless a HARD dependency explicitly requires it.

PRODUCTION-FIRST — HARD
- Validate early.
- Build the expected-record table early.
- Begin authoring/repair promptly.
- Write slices/assets incrementally.
- Prefer deterministic scripts for repetitive indexing, asset generation, comparisons, and QA.
- Do not spend the execution window reconstructing information already present in accepted map files.

FULL BANK ARTIFACT RECOVERY — HARD
In REPAIR mode or a continuation of REPAIR, a complete prior Bank package is the preferred way to materialize the authored Bank and binary assets into the working sandbox.

If the current sandbox does not already contain the complete Bank tree, use this recovery order immediately:
1. use a complete Bank ZIP already attached in the current conversation when available;
2. otherwise search the user's ChatGPT File Library ONCE with a targeted query for the most recent matching successful complete Bank ZIP, prioritizing the exact expected output name and course/unit/job identity (for example `algebra_1_u1_bank_complete.zip`);
3. materialize that complete ZIP locally and overlay the saved REPAIR checkpoint/touched files;
4. only if no matching complete Bank artifact exists in conversation files or File Library should connector/GitHub binary retrieval be attempted;
5. do not reconstruct dozens/hundreds of binary assets piecemeal when a prior complete Bank package exists.

FILE LIBRARY RECOVERY — HARD
- File Library is a normal artifact source for recovering a previously generated complete Bank package; it is not curriculum authority.
- Verify the recovered Bank's accepted_map_fingerprint and canonical record identity before using it as the REPAIR base.
- Prefer the most recent matching COMPLETE/PASS Bank artifact whose fingerprint matches the accepted map.
- Once a matching artifact is found, proceed directly to materialization + repair. Do not continue exploring alternate network routes.
- Do not repeatedly search the File Library. One targeted recovery search is the default; broaden only if the exact expected artifact name is not found.
- Do not use an unrelated or older Bank when the fingerprint/record set does not reconcile.

NO NETWORK-DETOUR NARRATION — HARD
Do not waste execution time or user-visible output narrating failed direct-network/GitHub binary materialization when a File Library recovery path is available.

Specifically, do NOT produce process chatter such as:
"The direct network route is blocked in the sandbox, but there's a better continuation path..."

Instead:
- search/recover/materialize silently as part of execution;
- if a matching artifact is found and a user-visible progress note is genuinely needed, use at most:
  `Found the prior complete Bank in File Library; resuming the repair from it.`
- then continue the repair immediately.

Only ask the user for a full Bank ZIP when:
- no complete matching artifact exists in the current conversation or File Library; AND
- the available connector cannot materialize the required binary assets.

WORKING CHECKPOINT — HARD
Create `.step3b_work/BUILD_CHECKPOINT.json` in staging with at minimum:
- mode = BUILD or REPAIR
- accepted_map_fingerprint
- verified authority identities
- expected record IDs/counts by destination
- touched record/surface set when REPAIR
- completed destinations/phases
- generated assets completed
- QA phases completed
- next_phase / next_destination
- last_updated.

The checkpoint is working state only and is not included in the final canonical Bank.

CONTINUATION — HARD
If execution time ends and there is no real HARD failure:
- save checkpoint and completed staging work;
- package a downloadable continuation/checkpoint ZIP containing the checkpoint and all staged work needed to resume;
- return internal status `STEP3B_INCOMPLETE_CONTINUE`;
- on `cont`, resume from checkpoint;
- do not restart discovery or reread unchanged authorities.

CONTINUATION USER RESPONSE — HARD
The user should never have to infer what to type next.

When Step 3b stops in a valid `STEP3B_INCOMPLETE_CONTINUE` state, the USER-VISIBLE RESPONSE must contain EXACTLY TWO LINES and NOTHING ELSE.

In REPAIR mode:
[Download the Step 3b Repair Checkpoint ZIP](<actual checkpoint ZIP link>)
TYPE `cont` TO GET REPAIRED BANK

In BUILD mode:
[Download the Step 3b Build Checkpoint ZIP](<actual checkpoint ZIP link>)
TYPE `cont` TO GET BANK

HARD presentation rules:
- no explanation paragraph;
- no status paragraph;
- no description of what was completed;
- no description of what remains;
- no troubleshooting prose;
- no code block;
- the download link is line 1;
- the type-cont instruction is line 2;
- `cont` is the exact continuation command;
- detailed phase/status information belongs INSIDE the checkpoint ZIP, not in the chat response.

Runtime exhaustion is not a bad request, missing dependency, or curriculum failure.

6. PROMPT / MATH QUALITY
===============================================================================

MATH RENDERING — ALGEBRA HARD
For Algebra student-facing HTML:
- use MathJax/TeX when it materially improves readability;
- use `\( ... \)` and `\[ ... \]`;
- do NOT register `$...$` as inline MathJax because currency such as $5 must remain ordinary text;
- keep student_text readable plain text for indexing/search;
- do not turn simple prose, integers, or table headings into unnecessary math markup.

NONREDUNDANT MATH — HARD
If the complete equation/expression is already naturally present in the prompt, do not repeat the identical full expression in an adjacent equation card or standalone block unless the second display has a documented instructional/reference purpose.

IMPORTANT:
Nonredundant does NOT mean "remove the equation representation."
If representation_mode requires an equation, the finished student surface must still contain a visible equation either:
A. naturally inline in the prompt; OR
B. as a separate equation/reference object.
It must contain one usable equation representation, not zero and not needless duplicates.

PROMPT QUALITY — HARD
Purposeful repetition of a learning job is allowed.
Mechanical duplication of finished non-fluency prompts/stimuli is not the default.

Review the whole Unit, not only one section:
- vary stem, values, representation pair, comparison focus, context, or misconception inside allowed axes;
- do not fake variety with noun swaps only;
- do not inflate difficulty just to make items look different;
- exact or near-exact fresh-parallel duplicates across sections are invalid unless exact repetition is explicitly required/documented.

MATCH / CLASSIFICATION ORDER — HARD
Visible panel/category order may not leak the answer key.
When matching families/categories to A/B/C/D panels, shuffle order/pattern so list order does not reveal answers.

7. REPRESENTATION COMPLETENESS
===============================================================================

REPRESENTATION MODE IS A FINISHED-SURFACE CONTRACT — HARD
representation_mode describes what the STUDENT CAN ACTUALLY SEE/USE, not merely metadata.

Before PASS, parse/inspect every finished student_html and reconcile visible representation components to representation_mode and accepted routes.

Examples:
- `mixed_graph_table` => visible graph + visible table.
- `mixed_table_equation` => visible table + visible equation.
- `mixed_graph_equation` => visible graph + visible equation.
- `mixed_graph_table_equation` => all three visible.
- `supplied_graph` / `supplied_context_graph` => referenced graph asset actually visible.
- `student_constructed_table` => answer-neutral table response surface visible.
- `student_constructed_graph` => answer-neutral graph response surface visible.
- diagram/mapping/number-line routes => the mapped semantic representation actually visible.

EQUATION PRESENCE RULE — HARD
For modes requiring an equation:
- a complete equation visible in the natural prompt counts;
- a separate equation-card/reference counts;
- an answer/solution-only equation does NOT count;
- metadata/trace-only equation does NOT count;
- an equation mentioned generically ("the equation") without displaying it does NOT count.

For example, a prompt saying "Compare the table and equation" with only a table rendered is invalid.

REPRESENTATION COMPONENT QA
Emit component-level mismatches with record ID, expected components, and observed components.
A mixed representation missing one required component = REPRESENTATION_COMPONENT_MISSING.

No PASS based only on representation_mode strings.

8. GRAPH TOOL / GRAPH SEMANTICS
===============================================================================

REGISTERED GRAPH TOOL EXECUTION — HARD
When the accepted route names a registered graph tool:
1. use the registered tool unchanged as instructed;
2. append only record-specific generation code where permitted;
3. execute it;
4. save the generated asset under the Bank figures/assets folder;
5. reference the asset from finished student_html;
6. store render_trace with tool identity, function, asset path/hash, dimensions when available.

Do not claim graph-tool provenance while substituting a hand-built coordinate/function SVG.

GRAPH MARKUP COMPLETENESS — HARD
Scan every finished student_html for graph-like markup, regardless of metadata.
Any coordinate/function/modeling `<svg>`, `<canvas>`, hand-built axis/grid, or improvised plot must reconcile to the accepted executable route.
Unexpected graph markup cannot escape QA by being absent from metadata.

GRAPH SEMANTIC MODE — HARD
- discrete relations/point sets: plot points only unless the map explicitly requires connecting them;
- continuous relationships: render the continuous curve/relationship;
- do not turn continuous functions into misleading point chains;
- do not connect discrete data merely because it follows a pattern.

ANSWER-NEUTRAL GRAPH STIMULUS — HARD
Do not add special visual emphasis that directly reveals the feature students are asked to determine:
- no special intercept dot when asked for the intercept;
- no callout/halo/annotation on requested vertex, zero, intersection, endpoint, coordinate, etc.;
- natural data points are allowed when the point set itself is the legitimate supplied stimulus;
- a marker may be used when it is a given datum for a different task and does not reveal the requested answer.

GRAPH EVIDENCE CONTAINMENT — HARD
Every mathematical value/feature the prompt requires the student to read, use, identify, compare, or construct from a graph must be inside the usable graph window.

Before rendering/final PASS:
1. derive the prompt-required graph evidence;
2. compute/check its actual graph coordinate(s)/feature location;
3. verify those coordinates/features are visible inside the rendered bounds;
4. require usable margin, normally at least one grid interval from the clipping edge when practical, unless the boundary itself is intentionally the evidence;
5. verify labels/arrows do not obscure the required evidence.

Examples:
- "Find y when x = 5" requires the actual point `(5, f(5))` to be visible.
- "Find x when y = 8" requires the relevant intersection with `y=8` to be visible.
- "Identify the y-intercept" requires the intercept to be inside the visible graph.
- a student construction asking for `(4,9)` requires `(4,9)` to fit on the response surface.

If a required point is outside a fixed standard graph range:
- do NOT modify the registered graph tool styling/range contract just to rescue the item;
- instead choose a new allowed equation/value/query inside the accepted variation contract so required evidence fits.
For context graphs whose bounds are part of the allowed route, choose natural bounds that contain the required evidence.

Failure code:
GRAPH_REQUIRED_EVIDENCE_OUT_OF_VIEW.

GRAPH RANGE / ASPECT — HARD
- standard coordinate grids remain visually square;
- preserve native image aspect ratio in HTML;
- no horizontal/vertical stretching;
- required plotted points/features/labels cannot be clipped;
- context graph bounds must be natural and readable.

COMPACT TABLE STYLE — HARD
Small input/output/data tables use semantic HTML `<table class="values">`.

Preferred teacher/student inspection appearance:
- natural content width;
- narrow readable columns;
- visible borders;
- centered numeric/math contents;
- compact padding;
- distinct header cells;
- table aligned near its partner representation rather than stretched across the card.

Equivalent viewer CSS must preserve:
  .values{
    border-collapse:collapse;
    width:auto;
    max-width:100%;
    margin:8px 0;
  }
  .values th,.values td{
    border:1px solid #777;
    min-width:52px;
    padding:7px 11px;
    text-align:center;
  }
  .split{
    display:flex;
    gap:16px;
    flex-wrap:wrap;
    align-items:flex-start;
  }
  .split>.values{
    flex:0 0 auto;
    align-self:flex-start;
  }

If a generic `.split>*` rule exists, the table-specific override must win the cascade.

GRAPH + TABLE LAYOUT
For `mixed_graph_table`, show the graph and compact table as a real pair:
- graph may take the larger visual area;
- table stays compact;
- both align near the top;
- do not place the table far away or make it a giant panel.

EQUATION DISPLAY
A separate equation reference may use a compact `.equation-card` when it has a real representation job.
Do not force a separate card when the same complete equation is already naturally readable in the prompt.
