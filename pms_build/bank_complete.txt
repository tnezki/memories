EXECUTION / CONTINUATION CONTRACT — HARD
Step 3b is a large production job. A valid build must not fail merely because one uninterrupted model turn is too short. Treat the work as ONE logical job that may continue from an explicit checkpoint.

SOURCE-READ BUDGET — HARD
- Use request-declared and manifest-declared paths directly. Do not perform repository-wide discovery/search when the required file/path is already declared and readable.
- Read each required authority once per unchanged pinned identity. Record its path + commit/blob/fingerprint in the working checkpoint.

Reopen only when a dependency is missing, a stored identity/hash does not match, or an actual conflict requires targeted resolution.
- Do not inspect old Banks, historical artifacts, retired PMs, unrelated Units, or unrelated Question Structure types after the entry gate unless a HARD dependency explicitly points there.
- The accepted 3a Map and its PASS MAP_REPORT are the primary semantic design proof. Step 3b verifies that the accepted map content is intact and that relevant higher-authority/tool identities remain compatible; it does not require whole-repository commit equality and does not redo Step 3a.

PRODUCTION-FIRST BUDGET — HARD
- Complete the entry gate, targeted semantic recheck, expected-record table, and first checkpoint early; begin authoring promptly rather than spending the majority of the run on source review.
- Once authorities are pinned and reconciled, stop broad analysis and move to generation.
- Write destination slices and generated assets incrementally to the staging workspace as they are completed. Do not keep the entire Bank only in transient reasoning state.
- Prefer deterministic scripts/batched transforms for repetitive record authoring support, asset generation, indexing, and QA comparison when this reduces repeated manual work without changing curriculum decisions.
- Update the checkpoint after each major destination/phase so continuation can resume at the next unfinished phase.
- Do not spend remaining execution time writing a long explanation while required production work is still unfinished.

WORKING CHECKPOINT — HARD
Create a noncanonical working checkpoint in the staging workspace before large-scale authoring, e.g. `.step3b_work/BUILD_CHECKPOINT.json`. It must track at minimum:
- accepted_map_fingerprint
- pinned authority identities/commits/blob hashes already read
- expected record IDs/counts by destination
- completed destinations/phases
- generated representation/assets completed
- QA phases completed
- next_phase / next_destination
- last_updated status.
The checkpoint is working state only. Do NOT include `.step3b_work/` in the final canonical Bank ZIP.

CONTINUATION — HARD
If execution must stop because the run/turn is ending and NO HARD dependency/semantic/QA failure has been found:
- do NOT say the request is invalid, blocked, or impossible;
- do NOT emit a FAIL-CLOSED curriculum code;
- persist the checkpoint and all completed staging outputs;
- respond with status `STEP3B_INCOMPLETE_CONTINUE`, the completed phase, and the exact next phase;
- on a user continuation such as `cont`, read the existing checkpoint first and resume from `next_phase`; do NOT restart source discovery, reread unchanged authorities, or discard completed outputs.
A continuation is the same Step 3b job, not a new build.

CHECKPOINT INVALIDATION — HARD
Restart the entry gate only when the accepted map fingerprint/content has actually changed, a relevant higher-authority/tool CONTENT identity has changed incompatibly, required staging files are missing/corrupt, or the user explicitly requests a restart. A repository commit SHA advancing by itself is NOT checkpoint invalidation. Otherwise resume.

PARTIAL OUTPUT — HARD
Never package or label a partial Bank COMPLETE. Runtime incompleteness is resumable working state; HARD validation/QA failure is a real fail-closed state. Keep these distinct.

CONTENT-ADDRESSED PIN COMPATIBILITY — HARD
Repository commit SHAs are provenance snapshots, not blanket semantic invalidators. The accepted 3a Map may remain executable after either repository advances. Do NOT require the request's whole-repository commit SHA to equal MAP_MANIFEST.pinned_snapshot.

Before declaring a pin mismatch, perform a TARGETED compatibility check:
1. Reconcile the accepted map directory against MAP_MANIFEST file hashes and map_fingerprint. If those map files still match, the accepted map itself is unchanged.
2. Compare only the CURRENT higher-authority/tool files that could change the map's meaning: Curriculum Philosophy; universal Question Structure authority actually used; current Course Framework; exact Unit Assessment Plan; canonical operational/mastery/spiral maps used by the Unit; current Framework Bank profile; and registered tools named by accepted representation routes.
3. A newer repository commit is compatible when those relevant content identities are unchanged, or when the only intervening changes are downstream/lower-authority/nonsemantic files.

Changes that DO NOT by themselves invalidate an accepted map include:
- this Step 3b PM / bank_complete.txt or other lower build-orchestration PM changes;
- generated Bank outputs, viewers, QA reports, figures/assets, staging or replacement packages;
- agenda/calendar/site output changes;
- storage/commit of the already-accepted map itself when its manifest hashes/fingerprint still reconcile;
- cleanup/removal of retired Banks or unrelated artifacts;
- unrelated Unit/course files.

Changes that DO invalidate the accepted map include an actual incompatible content change to a relevant higher authority/tool above, or any accepted map file/hash/fingerprint mismatch. If invalidation is real, FAIL CLOSED as BANK_MAP_AUTHORITY_CHANGED and list the exact changed authority/tool file(s) and content identities. Do NOT report a generic repository-pin mismatch.

When commit SHAs differ but the targeted compatibility check passes:
- continue Step 3b from the same accepted map;
- record pin_compatibility = COMPATIBLE_DRIFT in provenance/build report;
- preserve MAP_MANIFEST.pinned_snapshot unchanged as the map's original provenance;
- separately record the current Step 3b request/build repository pins as build-time provenance.

This rule exists specifically so improving Step 3b itself or syncing generated Bank output does not force a pointless Step 3a rebuild when the accepted map and its real authorities have not changed.

MATH RENDERING — ALGEBRA HARD
Student-facing algebraic notation in HTML must use TeX rendered by MathJax when MathJax improves readability. This includes powers, fractions, radicals, function notation, inequalities, systems, and multi-term algebraic expressions.
- Keep student_text as readable plain text for search/indexing.
- In student_html, wrap inline math in \\( ... \\) and display math in \\[ ... \\].
- Use ONLY \\( ... \\) / \\[ ... \\] delimiters in the viewer. Do NOT register $...$ as an inline MathJax delimiter because ordinary currency such as $5 must remain ordinary text.
- Prefer TeX such as \\(2a-a^2\\), \\(f(x)=3x-2\\), and \\(\\frac{y_2-y_1}{x_2-x_1}\\) rather than raw caret notation or Unicode superscripts when rendered HTML is available.
- Render the algebra where it naturally appears in the sentence. If the complete expression/equation is already present in the prompt, do NOT repeat that same expression in a second standalone math block merely to make MathJax render it.
- A separate display-math/reference block is allowed only when it has a real visual/instructional job: a large system, a formula that must remain visible across parts, a supplied equation separate from prose, or another genuinely useful reference object.
- Do not turn ordinary prose, labels, simple integers, or table headings into unnecessary MathJax.
- unit{unit}.html must load MathJax and re-typeset after dynamically rendering/changing tabs, filters, or search results.
- A math block that visibly exposes unrendered TeX delimiters/caret syntax in the GitHub Pages viewer is a render defect.
- A prompt that repeats the same full algebraic expression immediately below itself with no instructional purpose is a render/content defect.

PROMPT / STIMULUS QUALITY — HARD
Purposeful repetition of a learning job is allowed; mechanical duplication of the finished prompt is not the default.
- Preserve the mapped evidence job and student action.
- When several non-fluency Practice rows intentionally revisit the same job, vary the natural stem, values, representation, decision path, or misconception focus within the accepted variation contract.
- Do not produce a long cluster of verbatim identical student_text prompts merely because the map rows share a structure.
- Exact duplicate student_text appearing more than twice within the same section/stage must be explicitly justified as fluency repetition; otherwise rewrite the prompts without changing the mapped demand.
- Do not create fake variety by changing nouns only or inflating difficulty.

UNIT-WIDE FRESH-PARALLEL / DUPLICATION GUARD — HARD
The duplication review is UNIT-WIDE, not only within one section/stage.
- For non-fluency Practice/Exit tasks that revisit the same spiraled learning job in later sections, do not copy the same finished prompt + values + stimulus into the later section. Author a fresh parallel inside the accepted variation contract.
- Exact or near-exact duplicates across sections are invalid when the task is supposed to be a fresh Review/reassessment/practice opportunity.
- Compare normalized prompt text AND stimulus signature (values/equation/table/graph parameters/context). Changing only the record ID, section number, or one noun does not make a fresh parallel.
- Reuse is allowed only when the accepted map explicitly requires the identical shared stimulus or when exact repetition is deliberately documented as fluency.
- `duplicate_prompt_review_mismatches` must include cross-section duplicates and near-duplicates that violate this rule.

NONREDUNDANT MATH / REPRESENTATION GUARD — HARD
- If an equation/expression is already fully written in the natural prompt sentence, do not repeat the identical expression in an adjacent `.equation-card` or standalone math block unless that separate object has a documented instructional purpose.
- QA must normalize TeX/whitespace and compare prompt math against adjacent equation/reference blocks. An exact duplicate with no separate purpose is `MATH_REDUNDANT_DISPLAY`.
- For a table+equation task, either place the equation naturally in the prompt OR provide it as the separate reference representation; do not automatically do both.

MATCH / CLASSIFICATION ORDER — HARD
When students match labeled representations to a supplied category/family list, the visible order must not leak the key.
- If the prompt lists categories as A, B, C, D equivalents, do not arrange graph/panel A-D so the correct answers follow the same list order.
- Shuffle the panel order and/or category order while preserving the mapped evidence job.
- Parallel items must not reuse a predictable answer-position pattern.
- A four-family item that lists linear, quadratic, exponential, absolute-value and renders A=linear, B=quadratic, C=exponential, D=absolute-value is invalid because the layout gives away the matching order.

GRAPH MARKUP COMPLETENESS — HARD
The prior QA mistake to avoid: counting only records that already declared graph_tool while ignoring extra improvised graphs embedded in student_html.
- Scan EVERY finished student_html record for coordinate/function/modeling graph markup, regardless of representation metadata.
- Any graph-like inline <svg>, <canvas>, hand-built axis/grid markup, or other improvised plot must be reconciled to the accepted representation route.
- For Algebra coordinate/function/modeling graphs, a graph-like inline SVG such as <svg class="graph"> is NOT an acceptable substitute for the registered graph-tool asset.
- Semantic non-graph SVG is allowed only when the accepted route explicitly calls for it, such as an accessible mapping/diagram representation.
- If representation_mode says table+equation but student_html contains a coordinate graph, that is BOTH a representation-content mismatch and an unauthorized graph substitution.
- Render QA graph_tool_expected_count must be derived from the accepted routes PLUS a full scan of finished graph-bearing content; unexpected graph markup cannot escape the denominator.

Graph routing rules:
- Standard algebra/coordinate graphs: create a square figure (normally 3.5 in × 3.5 in), invoke make_standard_graph, preserve its axes, arrows, tick/grid treatment, and native aspect ratio in HTML. Do not stretch the image with CSS.
- Context/modeling graphs: invoke make_context_graph with natural bounds/labels. Preserve the generated asset's native aspect ratio; do not distort it to fill a card.
- Blank coordinate response surfaces: generate the blank coordinate plane through the registered graph tool (for example make_standard_graph with no answer-bearing function) and keep it answer-neutral.
- Discrete relations/point sets: use the registered graph-tool coordinate-plane styling, then plot the supplied points as POINTS ONLY in the appended generation block. Do not connect discrete points with line segments.
- Continuous relationships: if the mathematical object is a continuous linear/function relationship, render the continuous relationship/curve. Do not make it look like a discrete data set by showing only oversized sample dots connected by segments unless those sampled points are themselves the evidence job.
- A graph of a relation used for function/not-a-function evidence must preserve whether the relation is discrete or continuous; never connect points merely because they share a pattern.

ANSWER-NEUTRAL GRAPH STIMULUS — HARD
A supplied graph may contain the mathematical relationship/data needed to solve the question, but it must not add a visual cue that directly marks the feature the student is being asked to identify.
- Do not add an isolated dot, callout, annotation, special color, label, halo, arrow, or other emphasis to an intercept when the question asks students to identify/interpret that intercept.
- Apply the same rule to vertices, extrema, intersections, zeros, endpoints, specific coordinates, slope triangles, or other answer-bearing features.
- Example: for "Identify the y-intercept and interpret it as a starting amount," draw the relationship normally; do NOT place a special dot on the y-intercept.
- Natural discrete data points are allowed when the point set itself is the required stimulus. The prohibition is against extra answer-revealing emphasis, not legitimate data.
- A marker may be used when the marker itself is a given datum the student must use for a different task and does not reveal the requested answer.
- Student-construction response surfaces must contain no completed mathematical answer.

Graph legibility rules:
- Standard coordinate-plane grid cells must remain visually square; x/y axes must be visible and distinguishable from grid lines according to the registered tool.
- Axis/tick labels must be readable without crowding or duplication.
- Graphs must not be horizontally or vertically stretched by viewer/card layout.
- Every plotted, labeled, or student-required point/value must fit within the generated axis bounds with usable margin. If a WTC asks the student to plot (4,9), a response surface ending at y=6 is invalid.
- Do not clip required intercepts, vertices, endpoints, points, arrows, labels, or student construction space.
- A hand-built graph with visibly rectangular grid cells cannot pass as a registered coordinate graph merely because its surrounding card has the right width.

GRAPH TOOL FAIL-CLOSED CODES
- GRAPH_TOOL_NOT_EXECUTED: record claims graph_tool but no executed generated asset/trace exists.
- GRAPH_TOOL_SUBSTITUTED: graph_tool route was replaced by improvised inline SVG/manual graph rendering.
- UNREGISTERED_GRAPH_MARKUP: finished content contains graph-like markup that is not represented by an accepted executable graph route.
- REPRESENTATION_MARKUP_MISMATCH: representation_mode/route says one representation while finished student_html materially renders another.
- GRAPH_SEMANTIC_MODE_ERROR: discrete points were connected, or a continuous relationship was rendered as a misleading point chain.
- GRAPH_ANSWER_LEAK: a graph adds special emphasis to the feature/value the student is asked to determine.
- GRAPH_RANGE_CLIP: required evidence/construction lies outside the response/stimulus bounds.
- GRAPH_ASPECT_DISTORTION: standard coordinate graph is visibly stretched/non-square after rendering.

TABLE RENDERING — HARD
Small Algebra data/input-output tables use semantic HTML <table class="values"> and must stay compact and readable.
- Natural content width by default; do not stretch a two-column/four-row table across the whole card merely because it appears beside a graph.
- Center mathematical/numeric cell contents; keep headers visually distinct.
- Blank student-entry tables use the same compact geometry and preserve obvious blank cells.
- In graph+table or other split layouts, the graph may use the available visual area while the table keeps natural width and aligns to the top.
- Do not let generic flex rules such as .split>* { flex:1 ... } force tables to become giant panels.

Required Algebra viewer CSS behavior (equivalent implementation allowed):
  .values{border-collapse:collapse;width:auto;max-width:100%;margin:10px 0}
  .values th,.values td{border:1px solid #777;min-width:52px;padding:7px 11px;text-align:center}
  .split>.values{flex:0 0 auto;align-self:flex-start}
  .graph-img{display:block;max-width:420px;width:100%;height:auto;object-fit:contain}

Student-facing tables should not alternate randomly between giant stretched panels and tiny cramped tables when the underlying table job is the same.

VIEWER TABLE CSS ENFORCEMENT — HARD
The generated unit viewer itself must contain an effective compact-table override. It is not enough for this PM to state the desired CSS.
- When `.split>*` has a flexible rule, the final viewer MUST also contain an effective table-specific override equivalent to `.split>.values{flex:0 0 auto;align-self:flex-start}` after/with sufficient specificity to win the cascade.
- Final Render QA must inspect the generated viewer CSS/DOM contract and fail if split tables can inherit a flex-grow rule that stretches them.
- `table_layout_contract_mismatches` must include missing/overridden compact-table CSS, not just malformed table markup.
