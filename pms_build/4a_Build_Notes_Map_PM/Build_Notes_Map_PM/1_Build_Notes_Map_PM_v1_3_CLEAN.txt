3. CENTRAL NOTES STORY RULE
======================================================================

Physics Notes use substantially more conceptual reading and visual explanation than Math Notes.

Build the section as a sequence of CONCEPTUAL STORY BEATS.

A substantial beat normally contains:
1. a physics idea/phenomenon/model to develop;
2. one or more short developed reading paragraphs planned for 4B;
3. zero, one, or several useful images that advance that idea;
4. a PROCESSING ANCHOR before moving on.

PROCESSING ANCHOR RULE
- If one of the already-mapped canonical EX/YTI pairs naturally belongs after that reading/visual beat, place that EX/YTI pair there.
- If no mapped EX/YTI pair naturally fits there, map a content-specific STOP & DISCUSS.
- Do NOT invent an extra EX/YTI pair merely because a reading/image needs processing.
- Do NOT force an extra Stop & Discuss immediately before or after a mapped EX/YTI merely to satisfy a quota.

Every substantial reading/visual beat must have a meaningful processing destination before the conceptual story moves on.

======================================================================
4. IMAGE-FIRST SEQUENCING
======================================================================

Inspect the image catalog before sequencing prose.

Use Hewitt/source-textbook images generously. Production cost is irrelevant; image quality and instructional usefulness decide placement.

4A SHOULD FAVOR BROAD USE:
- phenomenon openers;
- striking examples;
- conceptual models;
- comparisons/rankings;
- evidence images;
- diagrams that make an invisible relationship visible;
- misconception-revealing figures;
- historical/contextual visuals when they strengthen understanding;
- graph/data/experimental visuals;
- bridge-to-equation/model figures.

Do not ration images because a section already has several.
Do not impose a fixed image count.
Use every strong image that materially advances the section's conceptual story.

OMIT an image only when it is:
- irrelevant to the mapped I-cans/story;
- substantially redundant without adding a new comparison/perspective;
- unreadable/poor quality;
- answer-bearing in a way that conflicts with the intended student processing task;
- better suited to another section/unit.

IMAGE IS NOT DECORATION
For every selected image, map:
- image_id;
- toolkit_path;
- source/provenance fields when available;
- story_role;
- exact concept/I-can connection;
- what_students_should_notice;
- why this image belongs here;
- whether it leads to EX/YTI, Stop & Discuss, or continued reading.

MULTIPLE IMAGES IN ONE BEAT
Allowed and encouraged when the images tell a sequence, comparison, or progression. Example: phenomenon -> model -> comparison -> application.

REUSE
Do not prohibit reuse. A strong source image may serve more than one Notes section when it genuinely supports different instructional purposes. Record the reason each time.

7. STOP & DISCUSS MAP
======================================================================

A Stop & Discuss exists when students need to process a reading/image beat and no mapped EX/YTI naturally serves that role.

For each Stop & Discuss, map these fields with exact ownership/semantics:
- after_story_beat_id;
- i_can_ids;
- discussion_job;
- prompt_skeleton;
- source_image_ids: ARRAY OF IMAGE IDs ONLY. If the discussion depends on a visual, each value must be a current Physics Notes Image Toolkit ID in the form PHYS-XXXXXXXXXXXX. Never place teacher reasoning text in this field. Use [] when no image is required;
- expected_reasoning_evidence_to_listen_for: ARRAY OF TEACHER-FACING REASONING/EVIDENCE STATEMENTS ONLY. Never place an image ID in this field;
- optional Hewitt inspiration type: Think and Discuss / Think and Explain / Think and Rank / prediction / comparison / evidence.

STOP & DISCUSS FIELD OWNERSHIP IS HARD CONTRACT DATA.
Do not infer, swap, or overload these fields. source_image_ids references images; expected_reasoning_evidence_to_listen_for tells the teacher what reasoning/evidence to listen for.

Do not write a long final student prompt. A concise prompt skeleton is allowed only if needed to make the intended reasoning unambiguous.

Avoid generic processing such as "What do you notice?" unless the map names exactly what evidence/relationship the teacher should elicit.

11. CONTENT-STABLE BANK FINGERPRINT — HARD HANDOFF CONTRACT
======================================================================

4A MUST identify the source Bank by curriculum/content identity, NEVER by the raw bytes of unitN_bank.zip. ZIP timestamps, compression, archive ordering, and other container metadata are not curriculum changes.

Use the bundled ~stable_bank_fingerprint_v1.py against the extracted/materialized Bank root. It implements the exact contract below. Record the returned method and fingerprint without alteration.

Compute source_bank_fingerprint using this precedence:

PRIMARY — FINALIZED STAGE 3E BANK IDENTITY
1. Extract/read the current materialized Bank.
2. Locate the Bank-owned STAGE_3E_HANDOFF.json.
3. Read canonical_authored_content_sha256.
4. Validate that it is exactly 64 hexadecimal characters.
5. Record:
     source_bank_fingerprint_method = "stage3e-canonical-v1"
     source_bank_fingerprint = "stage3e-canonical:<lowercase-64-hex>"

FALLBACK — DETERMINISTIC EXTRACTED-CONTENT MANIFEST
Use only when the required Stage 3E canonical hash is unavailable and the current authority allows proceeding with a non-Stage-3E Bank.
- Work from extracted Bank contents, not the ZIP container bytes.
- Ignore __MACOSX/, .DS_Store, AppleDouble files (._*), __pycache__/, and *.pyc.
- Normalize every relative path to POSIX forward slashes.
- For every regular file, compute SHA-256 of the file bytes.
- Sort records lexicographically by normalized relative path.
- For each record, feed exactly UTF-8(path) + NUL + lowercase_file_sha256 + LF into SHA-256.
- Record:
     source_bank_fingerprint_method = "content-manifest-v1"
     source_bank_fingerprint = "content-manifest:<lowercase-64-hex>"

FORBIDDEN
- Do NOT hash raw unitN_bank.zip bytes for the cross-stage source Bank identity.
- Do NOT write source_bank_fingerprint values using the legacy raw-ZIP form "sha256:<zip-bytes-hash>".
- Do NOT treat harmless rezipping as a stale-map condition.

The same method/value contract is consumed by 4B. A real authored-content change MUST produce a different fingerprint; harmless repackaging MUST NOT.
