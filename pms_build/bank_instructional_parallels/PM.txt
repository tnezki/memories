====================================================================

STATUS: CURRENT BANK-V2 PILOT PM
ROLE: Author the complete canonical Practice family layer directly into an accepted modular Bank-v2 build.

STARTUP - HARD
--------------
Read the current Curriculum Philosophy and Runtime Contract.
Resolve required authorities through the pinned manifests.
Fetch declared resources directly.

Do not use generic web search or repository-wide search to locate known curriculum authorities. Do not substitute old Banks,
prior chat copies, retained ZIPs, similarly named files, or alternate representations for declared canonical sources.

WEB / SEARCH RULE - HARD
------------------------
This job does not need open-ended web search to discover curriculum sources. If a map/profile explicitly declares an
external source or exact URL as required evidence, fetch that declared source directly. Otherwise do not web-search for

GENERIC RUN COMMAND
-------------------
Carefully read PM and Run.

"Run" means complete this entire Unit phase, author every mapped Practice family, validate the family contracts and seed
content, update the real modular Bank files, package only new/changed repo-relative files, reopen the package, and return it
in the same response.

PURPOSE
-------
Step 3B authors the canonical nonsecure Practice family seeds declared by `practice_map.json`.

It does NOT author Practice Set 1, 2, 3, or Extra Practice as finished worksheets. Those downstream artifacts are
deterministic selections and controlled instances of these canonical families.

Bank-v2 sequence:
  2.5 Bank Map
    -> 3A Instructional Core
    -> 3B Practice Families
    -> 3C Assessment Families
    -> complete canonical modular Bank

Step 2.6 is NOT required.
There is no Stage 3D or Stage 3E in Bank-v2.

SCOPE
-----
Build one Unit at a time.

Author ONLY every `family_seed` record declared in:
  `banks/unitN_bank_map/practice_map.json`

Preserve all existing 3A files unchanged except the two routing/front-door files that 3B must update:
  `banks/unitN/BANK_MANIFEST.json`
  `banks/unitN/ITEM_INDEX.json`

Do NOT author or modify:
- Notes/WTC/Example/YTI exact content;
- CYU exact content;
- Warm-Up exact content;
- Exit families;
- Summative families;
- downstream Practice worksheets or answer keys;
- downstream Notes, Activities, Exit Tickets, or Summatives.

The course Bank profile owns counts and composition. Do not hard-code Physics inventory into another course.
For the current Physics Unit 1 pilot, the accepted map contains 30 Practice families per section x 5 sections = 150 families.

MAP CONTRACT NORMALIZATION - HARD
---------------------------------
The current pilot map may use semantic lock names that are aliases of explicit map fields. 3B must materialize a fully
explicit canonical family contract rather than copying unresolved lock tokens forward.

Known pilot aliases may be normalized only when their source is unambiguous:
- `question_structure` -> `question_structure_id`;
- `approximate_difficulty` -> `difficulty_intent`;
- `representation_job` -> the explicit representation contract formed from `representation_mode`, `representation_need`,
  and any `representation_variation_rule`;
- `intended_reasoning` -> materialize an explicit `intended_reasoning` field derived narrowly from the mapped evidence job
  plus question structure. It must not change the evidence job or add a new instructional target.

Every token named by `locked_elements`, `allowed_variations`, `required_variations`, and `forbidden_variations` must resolve
to an explicit canonical contract property or a declared transformation rule. Unknown/unresolvable tokens are a hard stop.
Record any alias normalization in `provenance/3b_build.json`; do not mutate the Bank Map itself.

COURSE-AWARE AUTHORING - HARD
-----------------------------
This PM is universal. The current course Framework/profile owns disciplinary behavior and favored family patterns.

For Physics:
- begin quantitative work with a concrete physical situation, not naked variable assignments;
- treat equations as relationships describing phenomena;
- preserve conceptual/model reasoning rather than empty algebra shells;
- use real graphs, FBDs, vectors, tables, motion diagrams, models, or data when they carry evidence;
- keep wording concise by default;
- use physically plausible data and units.

For Algebra, Calculus, or another course, use that course's declared family patterns instead. Course-specific structures
such as Diamond Problems belong to the course Framework/profile, not to this universal PM.

CANONICAL PRACTICE FAMILY CONTRACT
----------------------------------
Each map family becomes ONE canonical family record. At minimum preserve/materialize:

IDENTITY / ROUTING
- `family_id` exactly equal to map `family_id` / `record_id`;
- `record_mode = family_seed`;
- `destination = practice`;
- `section`;
- `family_type`;
- `primary_i_can_id` + exact `primary_i_can`;
- `supporting_i_can_ids` when mapped;
- `selection_tags` and any mapped deterministic-selection metadata needed downstream.

EVIDENCE DESIGN
- `evidence_job`;
- `intended_reasoning` - explicit, concise, and faithful to the mapped evidence job;
- `question_structure_id`;
- `response_mode`;
- `representation_mode`;
- `representation_need`;
- `difficulty_intent`;
- `security_level`;
- `wording_profile` when mapped.

FULLY AUTHORED CANONICAL SEED
- `canonical_seed.student_text`;
- `canonical_seed.student_html`;
- `canonical_seed.choices` when applicable;
- `canonical_seed.answer`;
- `canonical_seed.solution_text`;
- `canonical_seed.solution_html`;
- `canonical_seed.figure_refs` for actual purpose-built figures used by the seed;
- actual embedded table/data/model content when that representation is part of the item rather than an external figure.

TRANSFORMATION CONTRACT
- `locked_elements` as explicit key/value locks, not unresolved labels;
- `allowed_variations` as explicit permitted axes/rules;
- `required_variations` as explicit change requirements for a sibling instance;
- `forbidden_variations` as explicit prohibited changes;
- `representation_variation_rule` when mapped;
- `source_map_record_id`;
- `source_basis` when mapped/useful.

Do NOT add `audit_status`, `NEEDS AUDIT`, `KEEP`, `CLEAN`, or `REBUILD` fields.
Do not expose family IDs, map language, or transformation metadata in student-facing prompt text.

SEED QUALITY - HARD
-------------------
A family seed is not a vague template and not "write another question like this."
It is one complete, classroom-usable canonical question with a correct answer and full solution that demonstrates exactly
what the family means.

Each seed must:
- perform the mapped evidence job;
- match the mapped response and question structure;
- represent the intended approximate difficulty;
- include the actual representation when evidence depends on one;
- be independently solved/checked after final wording/data are fixed;
- be sufficiently complete that a downstream builder can instantiate valid siblings using only the family contract.

FAMILY VARIATION QUALITY - HARD
-------------------------------
Allowed variation is controlled, not random.

A valid sibling must preserve every locked property and satisfy every required variation. It may change only allowed axes.
A variant is invalid when it merely swaps names/objects, changes wording profile only, scrambles choice order only, or changes
numbers when the family contract requires a deeper evidence/stimulus/representation change.

Do not over-constrain legitimate variety. Different course families may validly vary vocabulary direction, situation,
evidence set, misconception target, values/units, unknown, representation values/type, dependency path, or wording profile
when the map permits them.

PRACTICE POOL / DOWNSTREAM SELECTION
------------------------------------
Author the complete mapped family pool, not just the current feasibility witness or one selected set.

For the Physics pilot this means all 30 families per section.
The map's deterministic selection rules remain metadata/authority for downstream Practice builders:
- hard coverage/composition constraints first;
- deterministic tie-break second;
- no uncontrolled randomness;
- same pinned Bank identity + same declared set key -> same selected family IDs/order.

3B does NOT materialize the four Practice sets.

REPRESENTATIONS / FIGURES
-------------------------
If a canonical seed requires a graph, diagram, FBD, vector, table, model, or other representation, the actual student-safe
representation must exist.

Purpose-built Bank figures belong under:
  `banks/unitN/figures/`

Use stable filenames tied to family IDs. Every figure reference must resolve. No orphan generated figures.
Respect any manifest-declared `reference_in_place` rule for shared toolkit assets.
