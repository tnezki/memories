BUILD BANK INSTRUCTIONAL CORE — PORTABLE MEMORY v1.0 — STEP 3A BANK-V2
=====================================================================

STATUS: CURRENT BANK-V2 PILOT PM
ROLE: Author the exact-content instructional core directly from an accepted Bank-v2 map.

STARTUP — HARD
--------------
Read the current Curriculum Philosophy and Runtime Contract.
Resolve required authorities through the pinned manifests.
Fetch declared resources directly.

Do not use generic web/repository search to locate known curriculum authorities. Do not substitute old Banks, prior chat
copies, retained ZIPs, similarly named files, or alternate representations for declared canonical sources.

GENERIC RUN COMMAND
-------------------
Carefully read PM and Run.

"Run" means complete this entire Unit phase, validate every authored item, write the real modular Bank files, package
only the new/changed repo-relative files, reopen the package, and return it in the same response.

PURPOSE
-------
Step 3A authors only canonical `exact_content` records that downstream curriculum artifacts must reproduce exactly.
It does NOT author Practice families, Exit families, or Summative families.

Bank-v2 authoring sequence:
  2.5 Bank Map
    -> 3A Instructional Core
    -> 3B Practice Families
    -> 3C Assessment Families
    -> complete canonical modular Bank

Step 2.6 is NOT required. This PM consumes the accepted `banks/unitN_bank_map/` artifact directly.

SCOPE
-----
Build one Unit at a time.

Author ONLY the exact-content records declared in:
- `notes_map.json` — WTC + Example/You Try It;
- `cyu_map.json` — Check Your Understanding;
- `warmup_map.json` — Warm-Ups.

Do NOT author or modify:
- Practice family seeds;
- Exit family seeds;
- Summative family seeds;
- downstream Notes pages;
- Practice worksheets;
- Activities;
- Exit Ticket forms;
- Summative forms.

The course Bank profile owns counts. Do not hard-code Physics inventory into another course.
For the current Physics Bank-v2 pilot, Unit 1 is expected to resolve to 45 Notes exact items, 30 CYU exact items,
and 60 Warm-Up exact items = 135 exact-content items, but the pinned map/profile remain authoritative.

AUTHORITY ORDER
---------------
1. Current explicit teacher instruction for this job.
2. Current Curriculum Philosophy.
3. Current System Runtime Contract.
4. Current course Framework + ORIGINAL Unit Assessment Plan.
5. Current Framework/course manifest-declared Bank profile and required course runtime files.
6. Accepted Unit Bank-v2 map (`banks/unitN_bank_map/`).
7. Current `_question_structure/` authority.
8. This PM for authoring and storage procedure.
9. Optional external/source research only when the current Framework/profile/map explicitly requires it.

PINNING / DIRECT FETCH — HARD
-----------------------------
At job start, pin the memories repository commit and course repository commit once. Do not mix later commits into the run.

Resolve through manifests, then fetch exact declared files. For this phase, read the Bank map front door first:
  `banks/unitN_bank_map/MAP_MANIFEST.json`

Then fetch only the three required map slices:
  `notes_map.json`
  `cyu_map.json`
  `warmup_map.json`

Do not load Practice/Exit/Summative map slices merely because they exist.

MAP HARD GATE
-------------
Before authoring, verify:
- requested course and Unit are unambiguous;
- `MAP_MANIFEST.json` exists and identifies the same course/Unit;
- map status/QA is PASS;
- the three required slice paths are declared and readable;
- their fingerprints/counts agree with `MAP_MANIFEST.json`;
- every consumed record uses `record_mode = exact_content`;
- all consumed `record_id` values are unique;
- exact I-can IDs/text resolve against the pinned Framework / ORIGINAL Assessment Plan;
- every `question_structure_id` resolves through current `_question_structure/` or a manifest-declared course extension;
- required representation behavior is explicit enough to author the item honestly.

If a required authority or map record is materially missing/contradictory, STOP. Do not invent a replacement map inside 3A.
Minor prose awkwardness in map authoring notes is not a blocker when the actual I-can/evidence/structure contract is clear.

COURSE-AWARE AUTHORING — HARD
-----------------------------
This PM is universal. The current course Framework/profile owns disciplinary behavior.

For Physics, preserve current Physics rules such as:
- concrete physical situations rather than naked variable assignments;
- equations as relationships describing phenomena;
- conceptual/model reasoning before empty algebra shells;
- graphs, FBDs, vectors, tables, motion diagrams, models, and other representations when they carry evidence;
- concise wording by default.

For Algebra, Calculus, or another course, use that course's declared patterns instead. Do not import Physics-specific
question behavior merely because this PM was first piloted in Physics.

CANONICAL ITEM CONTRACT
-----------------------
Each authored exact-content item must preserve the map identity and design fields needed downstream and add finished
content. At minimum include:

- `item_id` — exactly the map `record_id`;
- `record_mode` = `exact_content`;
- `destination`;
- `section`;
- `primary_i_can_id` + exact `primary_i_can` text;
- `supporting_i_can_ids` when mapped;
- `evidence_job`;
- `question_structure_id`;
- `response_mode`;
- `representation_mode`;
- `security_level`;
- map relationship fields such as `notes_role`, `pair_id`, `pair_number`, `warmup_number`, `slot`, etc. when present;
- `student_text`;
- `student_html`;
- `choices` when the response mode uses choices, otherwise omit or use an empty array;
- `answer`;
- `solution_text`;
- `solution_html`;
- `figure_refs` — canonical repo-relative paths for actual figures used by the item;
- `source_map_record_id` — exactly the originating map record ID;
- `source_basis` when useful for provenance.

Do NOT add `audit_status`, `NEEDS AUDIT`, `KEEP`, `CLEAN`, or `REBUILD` workflow fields.
Do not expose internal map/family language in student-facing content.

Finished answers and solutions must correspond to the final instantiated prompt, not to an earlier draft.
For selected response, exactly one answer must be defensible unless the declared structure explicitly requires otherwise.

EXACT-CONTENT RULE — HARD
-------------------------
These are canonical exact items. Downstream builders must be able to fetch and reproduce the finished prompt/content,
answer/solution, and required figure references exactly.

Do not leave prose templates, placeholders, pseudo-prompts, or "generate later" instructions inside the Bank.

NOTES BANK CONTRACT
-------------------
Author every `notes_map.json` record.

WTC:
- one coherent shared situation/stimulus per mapped WTC;
- normally 3–5 connected parts when the profile/map says so;
- use the mapped evidence-bearing representation rather than describing an unseen representation;
- parts should form a real reasoning/navigation chain rather than unrelated mini-questions;
- WTC may use cross-Unit content when the current profile/map permits it.

Example / You Try It:
- preserve `pair_id` and `pair_number` exactly;
- Example explicitly models the mapped reasoning/evidence job;
- YTI is a comparable application under the same mapped evidence architecture;
- YTI must change meaningful evidence/context/data/representation details rather than copying the Example surface shell;
- do not change the mapped I-can, evidence job, structure, response demand, or approximate instructional demand merely
  to make the YTI look novel.

CYU BANK CONTRACT
-----------------
Author every `cyu_map.json` record as a concise exact canonical check.
- assess what students should now be able to do;
- use the mapped structure/representation;
- similarity to strong instructional work is allowed when purposeful;
- keep the item focused rather than turning CYU into a mini-test.

WARM-UP BANK CONTRACT
---------------------
Author every `warmup_map.json` record exactly as mapped.
The current course profile owns the recurring slot pattern.

For the Physics pilot, preserve:
- Q1 current/recent Physics retrieval;
- Q2 older/spiraled Physics retrieval;
- Q3 concise conceptual/vocabulary/application retrieval;
- Q4 recurring Physics math/formula skill.

Physics Q4 hard rule:
Use a short concrete physical situation that naturally supplies the measurements. Supply an appropriate relationship
when useful. Students use, rearrange/invert, interpret, or combine that relationship. Do not default to naked variable
assignments.

At a Unit start, when genuinely older Unit content is unavailable, use the map/profile-declared prior-knowledge fallback;
do not import future Unit content.

REPRESENTATIONS / FIGURES
-------------------------
If the mapped evidence requires a graph, diagram, FBD, vector, table, model, or other representation, the actual
student-safe representation must exist.

Use current Framework-declared figure/graph tools and manifest-declared course resources. Respect any `reference_in_place`
delivery rule; do not copy canonical toolkit assets into the Bank merely for convenience.

Purpose-built Bank figures belong under:
  `banks/unitN/figures/`

Use stable descriptive filenames tied to the item ID. Every `figure_ref` must resolve. No orphan generated figures.
Do not reuse one figure across unrelated canonical items merely to save work, but intentional shared-stimulus use inside
one multipart item is allowed.

MODULAR CANONICAL STORAGE — HARD
--------------------------------
Do NOT create a giant `unitN_bank_data.json`.
Do NOT create one giant destination JSON when section-sized files are practical.

The canonical Bank root is:
  `banks/unitN/`

3A creates/updates:
  BANK_MANIFEST.json
  ITEM_INDEX.json
  notes/section_<section-id>.json
  cyu/section_<section-id>.json
  warmups/section_<section-id>.json
  figures/                         (only files actually needed)
  provenance/3a_build.json
  provenance/3a_report.txt

Example Physics Unit 1 paths:
  `banks/unit1/notes/section_1_1.json`
  `banks/unit1/cyu/section_1_1.json`
  `banks/unit1/warmups/section_1_1.json`

Use filename-safe section IDs (`1.1` -> `1_1`).

Each section file contains only that destination + section's canonical items, in deterministic instructional order.
This section-sized storage is intentional: downstream jobs should fetch the smallest authoritative file that contains
the needed items rather than opening/searching a huge Bank aggregate.

BANK_MANIFEST.json
------------------
Create the stable Bank routing front door with at least:
- schema/version;
- course + Unit identity;
- `status = BUILDING` after 3A;
- `ready_for_downstream = false` until all required Bank phases are complete;
- pinned Bank-map identity/path/fingerprint;
- pinned course Bank-profile identity/path/fingerprint;
- completed phase list containing `3A_instructional_core`;
- pending phase list containing the remaining declared Bank phases;
- canonical artifact paths grouped by destination/section;
- counts by destination and total;
- `item_index = ITEM_INDEX.json`;
- next phase = `3B_practice_families`.

Do not duplicate all item bodies into the manifest.

ITEM_INDEX.json — RETRIEVAL CONTRACT
------------------------------------
Build one compact routing index for exact retrieval. For every authored item record:
- `item_id`;
- `record_mode`;
- `destination`;
- `section`;
- exact canonical file path containing that item.

Later 3B/3C append their new family routes to this same index.
Do not put prompt/solution bodies in ITEM_INDEX.json.

AUTHORING ORDER
---------------
1. Read Philosophy + Runtime Contract.
2. Pin memories/course commits.
3. Resolve Framework, ORIGINAL Assessment Plan, Bank profile, and `_question_structure/` directly.
4. Fetch `MAP_MANIFEST.json`, then only the three 3A map slices.
5. Run the map hard gate and reconcile expected exact-content inventory.
6. Author WTC items section by section.
7. Author Example/YTI pairs pair-by-pair.
8. Author CYU items section by section.
9. Author Warm-Ups in actual warm-up/slot order.
10. Independently solve/check every finished item.
11. Generate/verify required representations.
12. Render `student_text` and `student_html` from the same finished content; render answer/solution fields from the
    same solved item.
13. Write section-sized canonical files.
14. Build `ITEM_INDEX.json` and `BANK_MANIFEST.json`.
15. Write compact provenance/report files.
16. Run final 3A QA.
17. Package only the new/changed repo-relative `banks/unitN/` files and verify the package.

3A QA — HARD GATES
------------------
Before returning PASS, verify:
- every expected 3A map record is authored exactly once;
- no Practice/Exit/Summative family was authored;
- all item IDs and exact I-can text match the map;
- every finished item performs its mapped evidence job;
- every finished item uses its mapped question structure honestly;
- all Example/YTI `pair_id` relationships are complete and valid;
- every YTI is a legitimate comparable application, not a copied shell or unrelated novelty task;
- every WTC has its mapped coherent shared stimulus/representation and connected parts;
- CYU and Warm-Up inventories match the map/profile;
- Physics Q4 items obey the physical-situation/formula rule when Physics is the current course;
- every answer/solution is independently verified against the final prompt;
- every referenced figure exists and matches the prompt/solution;
- no orphan generated figures exist;
- no placeholders, internal authoring labels, or audit-status fields appear in canonical item objects;
- section files are small, destination/section-correct, and deterministic in order;
- every ITEM_INDEX route resolves to the correct section file;
- BANK_MANIFEST counts equal actual item counts;
- BANK_MANIFEST status is `BUILDING`, `ready_for_downstream = false`, completed/pending phases are correct;
- the output package contains only new/changed repo-relative Bank files and no copy of the Bank map.

DELIVERY CONTRACT
-----------------
Return one ZIP named:
  `<course>_uN_bank_3a_instructional_core.zip`

The ZIP must preserve course-repository-relative paths beginning with:
  `banks/unitN/`

Teacher repository action:
Extract/merge the ZIP into the ROOT of the current course repository so the files land under `banks/unitN/`.
Do not replace the entire `banks/` folder.

For a first build, `banks/unitN/` may be new. On a rerun, replace only the files supplied by this package unless the
teacher explicitly requests a full Unit Bank folder replacement.

Do not retain the ZIP as a canonical Bank source after extraction/sync. Canonical GitHub storage is the expanded files.

3B reads `banks/unitN/BANK_MANIFEST.json`, verifies 3A completion against the same Bank-map identity, then authors only
