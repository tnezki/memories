CORE ARCHITECTURE
-----------------
Do NOT begin by filling Practice, Exit, Summative, WTC, or other destination slots.

  Mastery Goal

=================================================
4. THREE FAMILIES PER I CAN — HARD
=================================================

Author EXACTLY THREE materially different question families per I Can:

Family A — CORE / DIRECT EVIDENCE
  Clean, strong direct proof of the I Can.

Family B — ALTERNATE REPRESENTATION / APPLICATION
  Same I Can through a meaningfully different representation, setup, context, or direction.

Family C — REASONING / MISCONCEPTION / TRANSFER
  A genuinely different reasoning route: interpretation, comparison, reverse thinking, error diagnosis, missing information, transfer, etc.

Do NOT force error analysis when another third route is more natural.

MATERIAL DIFFERENCE RULE:
Changing only numbers, names, nouns, coordinates, colors, or context words is NOT a new family.
Families should differ in the way students demonstrate the skill.

9. VIEWER — LOCKED LAYOUT
=================================================

  Tools/templates/algebra/bank/student_bank_template.html

Copy them as:

`unitN.html` is the technical/teacher family matrix.
`student.html` is the student practice view grouped Mastery Goal -> I Can -> Family A/B/C.
Do not invent different viewer layouts.

Required visual organization:
- strongest grouping = Mastery Goal;
- each Mastery Goal has a full-width, obvious MG banner;
- exactly four I Can columns on a normal desktop when the MG has four I Cans;
- display the families as three rows:
    Row A = Family A for I Can 1, 2, 3, 4
    Row B = Family B for I Can 1, 2, 3, 4
    Row C = Family C for I Can 1, 2, 3, 4
- therefore each normal family row has FOUR cards across;
- every card shows its I Can identity/text, family label/name, purpose, exemplar, and collapsible answer/specification;
- responsive layout may reduce to 2 or 1 columns on narrow screens.

GRAPH DISPLAY SIZE IN VIEWER:
- coordinate/context graph images: max-width 220px;
- center graphs inside the card;
- do not allow graphs to dominate the card/page.

STABLE FRAGMENT ANCHORS — HARD:
- every Mastery Goal container MUST expose its exact canonical goal ID as its HTML id;
- every I Can heading/container MUST expose its exact canonical I Can ID as its HTML id;
- every family card MUST expose its exact canonical family_id as its HTML id;
- examples: #U1-MG01, #U1-MG01-IC04, and #U1-MG01-IC04-A;
- do not invent aliases, shortened slugs, index-based anchors, or anchors derived from display wording;
- if an I Can ID is derived under Section 3, use that same recorded stable ID as the fragment anchor;
- fragment IDs are part of the public interface and MUST remain stable across rebuilds unless the canonical ID itself changes;
- the viewer loads Bank data asynchronously, so it MUST explicitly honor location.hash after rendering and on later hash changes;
- direct URLs such as unit1.html#U1-MG01-IC04 and student.html#U1-MG01-IC04-A must scroll to and visibly highlight the exact requested target after the target exists in the DOM;
- the student viewer MUST keep all three families for one I Can grouped together and MUST stack them vertically on narrow/mobile screens;
- the canonical viewer templates own this behavior so all future Unit Banks inherit it.

10. LIGHT QA — ONLY FIVE CHECKS
=================================================

1. COUNT / IDENTITY / ANCHORS
   - exact MGs/I Cans preserved;
   - exactly 3 families per I Can;
   - unique family IDs;
   - expected family count reconciles;
   - every MG, I Can, and family has exactly one matching canonical fragment anchor;
   - direct-fragment behavior is tested for at least one MG, the first/last I Can, and at least one family in the unit;
   - student.html is tested at desktop and narrow/mobile width so one I Can's A/B/C families remain visually grouped.

2. FAMILY DISTINCTNESS
   - A/B/C for one I Can are materially different types;
   - number-only / noun-only clones FAIL.

3. EXEMPLAR COMPLETENESS
   - complete usable prompt;
   - all referenced values/data present;
   - required representation visible;
   - no TODO/TBD/placeholders.

4. MATH / REPRESENTATION
   - answer/solution correct;
   - graph/table/equation agrees with prompt;
   - registered graph tool used when required;
   - no answer leakage.

5. FINALIZATION
   - run Tools/finalize_output.py on finished Bank tree;
   - require FINALIZATION_QA: PASS.

That is the QA. Do not expand into a giant audit.
If one check fails, repair the concrete defect and rerun that check + finalization.
