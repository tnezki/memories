BUILD UNIT FAMILY BANK - QUALITY FAMILY POOL / OFFLINE-READY
============================================================
STATUS: CURRENT
STEP: 3
JOB: bank
REVISION: 2026-09-26 v4.0

ROLE
Build the canonical Unit Bank as reusable question-family/generator architecture organized:
  Mastery Goal -> exact I Can -> approved Question Families.
The Bank is not a warehouse of finished Practice/Quick Check/Summative questions.

0. AUTHORITY / SOURCE BOUNDARY - HARD
Use current teacher instruction, pinned Philosophy/Runtime, current Algebra Framework + exact Unit Assessment Plan, current bank profile, Question Structure, registered tools, and local transfer contract. No public-web research or prior-chat curriculum sourcing.

1. ALL CURRENT I CANS - HARD
Use every exact current Unit Mastery Goal/I Can. Preserve IDs/text exactly.
Teacher/student displays use:
  <CANONICAL CODE> — <FULL EXACT I CAN STATEMENT>

2. FAMILY COUNT - QUALITY GATE
No fixed A/B/C count.
- aim for about 8-10 materially different quality families per I Can;
- about 6 may be enough for a narrow I Can;
- exceed 10 only when another family genuinely adds a useful student job;
- never create filler to hit a quota.
Existing family letters remain stable IDs only; they do not encode stage, difficulty, or universal semantic roles.

3. FAMILY RECORD - HARD
Each family records stable identity, exact MG/I Can, family name/purpose, evidence job, student action, Question Structure when applicable, response/representation mode, invariants, variation axes, forbidden variations, fresh-instance rule, security/destination guidance, one complete exemplar, answer/solution/scoring guidance, and provenance.

4. OFFLINE GENERATOR METADATA
Classify each family as STATIC, PARAMETERIZED, or DETERMINISTIC when useful. For parameterized/deterministic families include only defensible metadata such as parameter ranges, constraints, answer rule, graph/table generation, approved inversions, misconception/distractor rules, context/unit pools, seed behavior, and validated test seeds. Do not force deterministic generation where it harms quality.

5. DISTINCTNESS / REPRESENTATION
A new family must materially change how students demonstrate the I Can. Number/name/noun swaps alone are variations, not new families. Use registered graph/representation tools. Do not add decorative or answer-leaking representations.

6. OUTPUT
Canonical course path:
  banks/unitN/
Include current manifest/index/delivery/provenance/viewers/mastery-goal records and figures only when needed. Do not create permanent WTC, CYU, Tarsia, Blooket, Practice-set, Quick-Check, or Summative finished-question inventories unless a later current secure contract explicitly owns them.

7. QA / DELIVERY
Validate exact identities, family distinctness, exemplar completeness/correctness, generator constraints, representation fidelity, anchors/viewers, JSON/schema integrity, and registered finalization. Return ONE github_transfer / 2 ZIP. No Git operations.

END - UNIT FAMILY BANK
