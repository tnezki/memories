BUILD NOTES — SINGLE PASS / BANK-V2
==================================

STATUS: CURRENT
ROLE: Build the complete student + teacher Notes for one Unit directly from the current Framework, finalized Bank-v2 Notes anchors, and the Framework-declared instructional source/spine.

This is ONE Notes build.
There is no separate Notes Map stage.

The job is:
  SOURCE -> CONDENSE -> PLACE -> ASSEMBLE -> RENDER -> CHECK

It is NOT:
- a Bank rebuild;
- a Bank Map audit;
- a paragraph-by-paragraph textbook mapping exercise;
- permission to redesign the established Notes format.

AUTHORITY / STARTUP
-------------------
Read current Philosophy + Runtime first.
Resolve and pin required repositories once at job start.
Resolve Framework / Notes profile / visual contract / Tools through current manifests.
Fetch exact declared paths directly.

For current Physics, pin:
- system repo;
- course repo;
- textbook repo.

No web/File-Library/prior-ZIP/repository hunting for declared sources.

FAILURE DIAGNOSTICS — HARD
--------------------------
When failing before authoring, classify the failure:

BANK_INPUT_DEFECT
- Bank is not COMPLETE/ready;

SOURCE_INPUT_DEFECT

Do not collapse these into a generic "missing field" message.

SOURCE-SPINE RULE — HARD
------------------------
For current Physics, the Framework-declared textbook/source is the instructional spine.

Preserve:
- the source's major conceptual order;
- its terminology and physics meaning;
- the order of its instructional figures/images.

The Notes do NOT need to preserve paragraph-level textbook wording.

Summarize and condense aggressively enough that the complete student Notes for the section are reasonably usable in approximately 30–40 minutes.

That time target includes:
- opening/WTC;
- skim;
- reading;
- normal student processing;
- EX/YTI work;
- close.

When the section is too long:
1. remove repetition/tangents first;
2. compress prose;
3. combine nearby explanatory paragraphs;
4. preserve essential conceptual transitions;
5. do NOT delete canonical WTC or complete EX/YTI pairs to hit the time target.

SOURCE MODES
------------
Classify each section before writing:

1. textbook_direct
   A usable declared source exists for the target.
   Condense it while preserving conceptual and figure order.

2. textbook_partial_gap
   The declared source itself contains a real missing subsection/span needed by the Framework target.
   Preserve the gap honestly.
   Do not invent fake textbook prose.
   Supply only the minimum Framework-grounded bridge needed for the uncovered target.

3. framework_synthesis
   The declared source explicitly identifies the section as synthesis/application rather than a corresponding textbook passage.
   Use that declared synthesis as the source.
   Do not pretend it is extracted textbook prose.

Source/provenance notes in the source file are evidence for the build.
They are not automatically student-facing text.

TEXTBOOK IMAGE CONTRACT — HARD
------------------------------
Use EVERY usable instructional image/figure present in the declared student-source section, in SOURCE ORDER.

Do not silently select only favorite images.

Exclude only:
- logos/navigation/UI chrome;
- decorative media icons;
- answer-key-only images;
- an image that directly leaks an answer the student is supposed to produce.

For every retained source image:
- keep it near the concept where it appears in the source;
- preserve meaningful labels/captions as needed;
- preserve source order;
- never crop away evidence needed to read it;
- never replace a good source figure with a crude redraw.

SIZE:
- default maximum displayed height = 4 inches;
- width remains automatic and never exceeds the content width;
- preserve aspect ratio;
- center through the established figure wrapper;
- if labels are genuinely unreadable at 4 inches, increase only that figure as needed, normally to 5 inches and never beyond 6 inches without a clear reason.

On-screen zoom is expected; do not make every figure huge just because a student might zoom.

CLOSE READING DIRECTIONS — EXACT BLUE BOX

READING / EXACT I-CAN COMPARTMENTS — HARD
-----------------------------------------
The Philosophy requires Notes to remain compartmentalized around exact I-can learning jobs.
The textbook remains the source spine and source order must still be preserved.

For each exact I-can:
- create at least one major reading block headed by the exact I-can text;
- use `<section class="notes-ican-start">`;
- use `<h2 class="h-intro notes-ican-heading">EXACT I-can text</h2>`;
- place the summarized source reading/figures that teach that learning job beneath it.

Do not invent a generic `<h2>Close Reading</h2>` and then hide the I-cans only at the top of the document.
Do not reorder source concepts merely to force clean I-can boundaries; preserve source order and use the nearest honest I-can focus.

READING / PROCESSING RHYTHM
---------------------------
Move through summarized source in conceptual/source order.

After every SUBSTANTIAL reading block, immediately use exactly ONE primary student-processing event before the next major application:
- Stop & Discuss; OR
- one complete canonical Example/YTI pair.

A short transitional/support paragraph does not automatically require a processing event.
Never place Stop & Discuss AND EX/YTI at the same reading boundary.

A Physics Note, source figure, diagram, Formula / Relationship box, graph, or model may coexist with the reading.
Those are instructional supports, not a second primary processing event.

STOP & DISCUSS — HARD
---------------------
A Stop & Discuss is one processing event containing 2–4 short prompts.
Default = 3 prompts. Use 2 when the reading is narrow; use 4 only when all four earn their place.

Every Stop & Discuss must include:
- at least ONE vocabulary/notation question tied to a term just used in the reading; AND
- at least ONE conceptual/representation question that requires students to explain, compare, interpret, critique, or connect something from the immediately preceding reading/figure/model.

Additional prompts may target:
- misconception repair;
- evidence/model interpretation;
- connection between representations;
- prediction or explanation.

No stock generic comprehension questions.
No question may depend on material that has not yet appeared.

Use the established shell EXACTLY:

  <section class="notes-discuss-task">
    <div class="stop-discuss">
      <strong>Stop and Discuss</strong>
      <ol>
        <li>...</li>
        <li>...</li>
        <li>...</li>
      </ol>
    </div>
    <div class="notes-ws"></div>
  </section>

HARD:
- prompt box is the colored/red discussion box;
- writing workspace is OUTSIDE that box;
- workspace is plain white Notes space;
- never put `.notes-ws` inside `.stop-discuss`.

TEACHER GUIDE STRUCTURE — HARD
------------------------------
Every canonical WTC / Example / YTI teacher block must use a readable teacher-guide structure.
Do not render teacher support as one long red paragraph.

Required order:

Answer / Acceptable Reasoning
- use bullets for separate reasoning ideas;
- for multipart tasks, use one bullet per labeled part:
  - (a) ...
  - (b) ...
  - (c) ...
- calculations should show the relationship, substitution/reasoning, result, units, and interpretation when relevant;
- constructed diagrams/models should describe the required features clearly.

Teacher Moves
- 1–3 concise moves or prompts the teacher can use to advance thinking;
- phrase as usable discourse prompts/actions, not generic advice.

Student Moves
- 1–3 likely productive student actions/reasoning moves;
- describe what students should notice, say, draw, compare, calculate, or justify.

Listen For / Likely Misconception
- include when useful;
- identify the specific idea, vocabulary confusion, representation error, or reasoning issue worth listening for.

For a very short single-answer item, Answer / Acceptable Reasoning may contain one bullet.
Teacher Moves and Student Moves still remain separate labeled lists when instructional guidance is useful.

Do not create filler discourse moves merely to satisfy a count.
The purpose is fast browser-side teacher support that is easy to scan while teaching.

Answers remain clearly teacher-only according to established course behavior.

PURPOSE:
- human/AI troubleshooting;
- reconstruct why a specific item changed;
- compare repeated fresh-chat repair passes;
- preserve the original local identity/metadata that existed before a repair.

THIS FILE IS NOT CURRICULUM AUTHORITY.

Future build/repair PMs and generic repair tools MUST NOT use

audit repair history, or investigate why something changed.

NORMAL BUILD:
- if no prior log exists, create it only when at least one actual repair/change
  beyond ordinary first-time authoring needs documenting;
- do not generate noisy entries for every unchanged block;
- "PASS — no changes" may be appended when a deliberate repair/audit pass made
  no changes and preserving that fact is useful.

REPAIR / REBUILD:
- preserve existing log text exactly;
- append new entries at the end;
- never rewrite, summarize, normalize, or delete prior entries;
- one run gets one run header;
- one changed item gets one compact item entry.

RUN HEADER records:
- timestamp when available;
- artifact/course/unit/section scope;
- repair/build mode;
- pinned system/course/source commits when available;
- tool/PM identity;
- result summary:
  - PASS — no changes
  - or count by repair class.

FOR EACH CHANGED ITEM, record ORIGINAL metadata BEFORE repair:
- stable item/task ID;
- section;
- artifact type;
- primary I-can ID;
- exact original I-can text visible/resolvable in the artifact;

Then record:

- fields changed;
