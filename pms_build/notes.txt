BUILD NOTES — SINGLE PASS / BANK-V2.3 — ALGEBRA TEXTBOOK-STYLE PILOT vNEXT.1
=========================================================================

STATUS: PILOT
ROLE: Build complete student + teacher Notes for one Unit from the current Framework,
the completed Bank, the accepted source_map that travels with the Bank, and any
Framework-declared instructional source/spine.

This remains ONE Notes build. There is no separate Notes Map stage.

JOB
---
SOURCE -> PLAN -> GENERATE -> PLACE -> ASSEMBLE -> RENDER -> CHECK

This job is NOT:
- a Bank rebuild;
- a Bank Map redesign;
- permission to alter Exit Tickets;
- permission to expose secure Summative items;
- a requirement that every possible Notes routine appear in every section;
- a requirement that the teacher complete every included Notes component in class.

CORE PRINCIPLE — BUILD A COMPLETE TOOLBOX; TEACHER CHOOSES WHAT TO USE
----------------------------------------------------------------------
Notes must teach the exact section Learning Target / I-can jobs and provide a useful
set of ready-to-use instructional pieces.

IMPORTANT:
The builder should NOT omit useful standard components merely because the teacher
may choose not to use them in class.

Every normal Algebra section should provide:
- a short Let's Get Started;
- the exact canonical WTC;
- the full generated EX/YTI inventory;
- the core reading / visual Math Notes;
- a concise Summary;
- Common Mistakes to Watch as the final section.

The teacher is NOT expected to do every included component every time.
The Notes are a toolbox, not a required minute-by-minute script.

Vocabulary Preview, Talk to the Text / Close Reading, Stop & Discuss, and similar
reading/discourse routines remain selective. They should appear only when they earn
their place.

Build each section so that:
- the core reading stands on its own;
- the teacher can skip any activity/routine without breaking later reading;
- standard components are available without becoming a checklist the teacher must complete;
- optional routines earn their place.

OPENING DENSITY — HARD
----------------------
A normal Algebra section includes BOTH Let's Get Started and WTC, but neither should
become a second lesson.

Default opening:
- title / target / I-cans / Why It Matters;
- short Let's Get Started;
- exact canonical WTC;
- then move into the core mathematics.

Do NOT automatically stack Vocabulary Preview + Close Reading directions on top of
that opening. Add either only when it clearly earns the time/space.

EXAMPLE / YOU TRY IT — NEW GENERATION CONTRACT
-----------------------------------------------
Canonical Bank EX/YTI pairs are retired.

Generate Notes EX/YTI pairs DURING the Notes build.

DEFAULT:
- ONE complete Example/YTI pair per exact I-can.

SECOND PAIR:
A second pair for the same I-can is allowed ONLY when that I-can has a materially
different second learning job that cannot be represented well by the first pair.

Examples of earned second-pair reasons:
- two genuinely different required representations;
- two different procedures/decision paths;
- conceptual interpretation plus a distinct application/modeling job;
- a high-value misconception that needs a separate corrective instance.

Do NOT create a second pair merely for more practice.

PAIR FUNCTION
-------------
Example:
- models the mathematical thinking clearly;
- may be slightly more scaffolded;
- shows a complete teacher solution in teacher copy.

You Try It:
- fresh parallel instance of the SAME I-can/evidence job;
- less scaffolded;
- requires students to do the thinking;
- must not be the same values/context/stimulus as the Example.

The teacher is not required to complete every generated pair in class.
Pairs are a ready-to-use instructional inventory inside the Notes.

PAIR AUTHORING SOURCE
---------------------
Generate each pair from:
  exact I-can
  -> accepted map evidence job / representation route
  -> Question Structure
  -> Practice1 calibration when useful
  -> fresh Notes-specific authored instance

Do NOT generate from the Exit prompt.

QUESTION STRUCTURE
------------------
When EX/YTI is a question/task, follow the current Question Structure authority:
target/evidence -> natural structure -> response mode -> representation -> executable route
-> author -> solve/check -> render-level QA.

Direct reads stay direct.
Construction tasks need real answer-neutral response surfaces.
Mixed representations must visibly include every named representation.

EXIT TICKET FIREWALL — HARD
----------------------------
Before finalizing ANY GENERATED Notes question/task — including Let's Get Started, Example/YTI, or question-like discussion prompts — compare it against ALL Unit Exit records.

Same I-can/evidence job is allowed.

PROHIBITED overlap:
- same prompt;
- same or trivially changed wording that preserves the Exit's distinctive task sequence;
- same values/data set;
- same context;
- same graph/table/equation stimulus;
- same distinctive representation with only cosmetic changes;
- a near-parallel item that effectively lets students rehearse the Exit answer.

If a conflict is found:
- regenerate the Notes item;
- do NOT alter the Exit;
- re-run the firewall check.

Record for every generated Notes task:
  exit_firewall_checked = true

QA must report:
  notes_exit_duplicate_count = 0

Fail code:
  NOTES_EXIT_NEAR_DUPLICATE

WTC — STANDARD AND CANONICAL
----------------------------
Every normal Algebra section includes the exact canonical Bank WTC ONCE.

- preserve item ID, prompt, representation, I-can identity, answer/solution lineage;
- do not rewrite or simplify it silently;
- teacher copy may add instructional/discourse support;
- student copy must not leak the answer;
- the teacher may skip the WTC during instruction, but the build should still provide it.

If teacher input explicitly omits WTC for a particular build, honor that request and
record the omission in the build report.

If the canonical WTC itself is a near-duplicate of an Exit item, do NOT silently alter
either artifact. Flag the upstream conflict for review.

LET'S GET STARTED — STANDARD SHORT OPENER
-----------------------------------------
Every normal Algebra section includes one short Let's Get Started.

Purpose:
- activate prior knowledge;
- preview a useful representation/pattern;
- create a quick notice/predict/compare moment;
- connect to a prerequisite without teaching the whole section early.

Keep it short enough to use or skip easily.

Preferred shell:
  <section class="skim-section-task lets-get-started">
    <h2 class="lets-get-started-heading">Let's Get Started</h2>
    <div class="starter-visual">...</div>      <!-- when a visual helps -->
    <p class="starter-prompt">...</p>
    <div class="starter-response"></div>
  </section>

Design rules:
- normally 1 prompt or a tiny coherent set;
- prefer a visual/table/pattern/diagram when natural;
- do not require a large calculation;
- do not turn it into an Example/YTI pair;
- do not force prediction/notice/wonder wording when another short move is better;
- all GENERATED Let's Get Started tasks must pass the Exit-ticket firewall.

MATH NOTES — VISUAL FIRST
-------------------------
Math Notes should behave more like a compact textbook reference/figure than a paragraph
inside a colored box.

DEFAULT:
Each I-can compartment should include one meaningful VISUAL ANCHOR in or immediately
beside its Math Notes when the mathematics supports one.

Useful visual anchors include:
- input -> rule -> output flow;
- annotated expression/equation with labels/arrows;
- mini table tied to an equation or graph;
- graph + labeled feature;
- side-by-side comparison cards;
- representation translation flow;
- process/decision flow;
- small diagram or model;
- compact formula/reference display.

HARD PREFERENCE:
Visual first; prose second.
The text should explain or name what the visual shows. It should not merely repeat the
same idea as a paragraph.

A paragraph-only Math Notes box is acceptable ONLY when a visual would be artificial or
less clear.

Preferred semantic shells:

Flow:
  <div class="math-visual math-flow" aria-label="...">
    <div class="math-flow-node">Input</div>
    <div class="math-flow-arrow">→</div>
    <div class="math-flow-node">Rule</div>
    <div class="math-flow-arrow">→</div>
    <div class="math-flow-node">Output</div>
  </div>

Comparison:
  <div class="math-visual math-compare-grid">
    <div class="math-compare-card">...</div>
    <div class="math-compare-card">...</div>
  </div>

Annotated structure:
  <div class="math-visual annotated-expression">
    ...
  </div>

Do not make decorative visuals.
Every visual must teach, organize, compare, or make structure visible.

Use registered graph tools for new coordinate/function graphs.
Use semantic HTML/CSS for simple non-graph flows, labels, arrows, tables, and process
diagrams.
