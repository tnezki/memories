BUILD BANK MAP — STEP 2A / BANK-V2
=====================================

STATUS: CURRENT
ROLE: Build one complete Unit Bank design map before any final Bank question prose is authored.

2A is the executable design stage.
It maps the evidence job, question structure, response mode, representation, tool/render route, variation contract, and destination before 3A/3B/3C author final content.

STARTUP — HARD
--------------
Read:
1. current Curriculum Philosophy;
2. current Runtime Contract;
3. current `_question_structure/` entrypoint + question-design schema/workflow;
4. current course Framework + exact Unit Assessment Plan;
5. current Framework-manifest Bank-v2 profile/runtime files;
6. `Tools/MANIFEST.json`.

Resolve/pin repositories once. Fetch declared paths directly.
No web search, public-web fetch, File Library search, prior-stage ZIP search, or repository search for a declared authority.

AUTHORITY ORDER
---------------
1. current explicit teacher instruction
2. Curriculum Philosophy
3. current Question Structure authority
4. current course Framework + exact Unit Assessment Plan
5. current Framework-declared Bank-v2 course profile
6. this PM for mapping procedure
7. registered tools for executable render routes

PURPOSE
-------
Separate:
1. DESIGN MAP — what exact evidence/jobs/structures/representations must exist;
2. CANONICAL BANK CONTENT — authored in 3A/3B/3C;
3. DOWNSTREAM INSTANCES — deterministic selections or controlled family variants.

2A authors NO final student prompts, final answer choices, final answers, or final solutions.

QUESTION-DESIGN MAP — HARD
--------------------------
Build `unitN_question_design_map.json` using the current question-design schema.

For every exact I-can, map:
- evidence_job;
- content_modes;
- formula/reverse paths when applicable;
- vocabulary directions when applicable;
- best-fit question structures;
- structures to avoid;
- representation opportunities;
- tool opportunities;
- parallel-variation axes.

For every destination slot/family, map:
- slot_id;
- primary_i_can_id;
- supporting_i_can_ids as needed;
- structure_id;
- response_mode;
- representation_mode;
- tool route when applicable;
- dependency_chain when applicable;
- security role;
- variation axes;
- concise notes.

A structure/response/representation/tool field is executable. It is not a suggestion.

COMMON DESTINATION RECORD
-------------------------
Every map record includes, as applicable:
- record_id
- record_mode
- destination
- section or Unit scope
- primary_i_can_id + exact primary_i_can
- supporting_i_can_ids
- evidence_job
- student_action
- question_structure_id
- response_mode
- representation_mode
- representation_need
- design_slot_id
- tool
- render_contract
- wording_profile / length intent
- security_level
- source_basis
- concise authoring_notes

For `selected_response`, also map:
- choice_count or course default;
- distractor_basis;
- whether single-select or explicit multi-select.

For table/data representations, `render_contract` must require semantic HTML table rendering and identify the established compact table class when the data set is small.

For graph representations supported by the registered graph tool:
- `tool = graph_tool`
- do not map an improvised graph route.

For diagram/FBD/vector/model representations:
- a generic route label such as `framework_approved_diagram_route` is NOT executable and must not PASS;
- for an existing canonical asset, record an explicit `representation_route` with route_type=`canonical_asset`, repository, pinned commit, exact canonical path, and asset_id when available;
- for a deterministic generator, record route_type=`registered_tool`, a `tool` key that resolves through `Tools/MANIFEST.json`, and the parameter / answer-neutrality contract needed by downstream authoring;
- for a student-constructed diagram/FBD/vector, map an explicit blank response-surface contract; do not require a completed answer diagram;
- if no exact asset or registered tool exists, redesign the slot to an evidence-equivalent non-diagram task only when the target permits it; otherwise FAIL the slot and report the missing route.

FAMILY MAP RECORD — HARD

WTC — DECOMPOSITION / NAVIGATION HARD GATE
--------------------------------------------
Map one WTC per section, but WTC content is NOT locked to that section or even the current Unit.

PRIMARY PURPOSE:
WTC teaches students how to unpack and navigate a long multi-part FRQ. Content difficulty is not the goal. A WTC may use straightforward prior/current/future Physics so students can focus on identifying givens/asks, reading the shared representation, tracking dependencies, selecting a relationship/plan when useful, and communicating reasoning.

Each WTC map record must specify:
- coverage_role = wtc_frq_practice;
- one shared coherent stimulus/representation;
- normally 3–5 connected labeled parts;
- at least one part that actually reads/uses the shared stimulus/representation;
- at least one real dependency / carry-forward in which a later part uses information, a conclusion, or a decision from an earlier part;
- an explicit `decomposition_move_plan` chosen from the course-profile WTC move menu;
- content provenance I-can when useful for teacher metadata;
- accessibility plan if the Physics content has not yet been taught.

The move menu is NOT a universal checklist. Planning/model-choice/justification is not mandatory in every WTC. Map only moves the planned student-facing parts will actually require.
The problem may look long or intimidating while the underlying Physics remains straightforward; do not raise content difficulty merely to make WTC feel rigorous.

If a legacy `required_frq_moves` field is emitted, it must contain only moves truly required by that WTC; do not auto-fill a fixed universal trio.
WTC does not satisfy current Unit I-can coverage floors.
Do not map WTC as four independent mini-questions.

REPRESENTATION / TOOL PLAN — HARD
---------------------------------
The map must distinguish:
- graph -> registered graph tool when supported;
- small data table -> semantic HTML `<table class="values">`;
- diagram/FBD/vector/model -> approved source or deterministic route;
- image/phenomenon -> declared course/Framework source;
- direct text/equation -> no fake decorative figure.

If representation_mode says students must use a representation, 3A/3B/3C must be able to render it visibly.

PRACTICE MIX — FIT BEFORE CATEGORY
----------------------------------
The section pool size remains the current course-profile count, but family-type composition is NOT a universal quota.

For each section:
1. map the exact I-cans/evidence jobs first;
2. decide which content/question modes genuinely fit those jobs;
3. allocate the full Practice pool from that fit;
4. allow any family category to be zero when the section does not naturally support it.

Do NOT create:
- a quantitative/modeling family for a vocabulary/conceptual I-can merely to fill a quantitative bucket;
- a vocabulary family for a model/relationship target merely to fill a vocabulary bucket;
- a diagram/graph/table merely to satisfy representation variety.

Quantitative/modeling is justified only when the target genuinely calls for relationship use, calculation, quantitative comparison, model interpretation, or similar mathematical reasoning.

EVIDENCE / RESPONSE / REPRESENTATION ALIGNMENT — HARD
-----------------------------------------------------
Every destination record must state the actual `student_action` and pass this alignment check:

  exact I-can -> evidence_job -> student_action -> question_structure_id
  -> response_mode -> representation_mode -> tool/render route

All links must describe the SAME evidence job.

Examples:
- evidence_job = "draw/construct a force diagram" -> constructed_response + student_constructed_fbd + blank response surface;
- evidence_job = "identify which supplied force diagram is correct" -> selected_response + supplied diagram choices/representation;
- evidence_job = "critique a supplied diagram" -> constructed_response or selected_response only if the chosen response actually captures critique evidence.

Do NOT map a selected-response item as evidence that the student drew/constructed/built a representation.
If response mode changes the student action, rewrite the evidence job honestly or choose a different response mode.

DETERMINISTIC SELECTION
-----------------------
For destinations with pools:
- satisfy I-can/evidence/composition/security/representation constraints first;
- deterministic tie-break second;
- no uncontrolled randomness.

Stable key recipe:
  course|unit|section-or-unit|destination|form-or-set|bank_fingerprint

MAP BUILD ORDER
---------------
1. Pin memories/course commits.
2. Resolve Framework, exact Assessment Plan, Bank-v2 profile, Question Structure, Tools manifest.
3. Build exact Unit I-can/evidence architecture.
4. Build `unitN_question_design_map.json`.
5. Resolve destination inventory/record modes.
6. Map WTC rigor/routes.
7. Map exact instructional anchors.
8. Map Practice families.
9. Map CYU/Warm-Up exact content slots.
10. Map secure Exit/Summative families and blueprints.
11. Reconcile representations/tools/render contracts.
12. Write destination slices + MAP_MANIFEST.
13. Run integrated structural/executable audit.
14. Repair map defects.
15. Write MAP_REPORT and package.

INTEGRATED MAP AUDIT — HARD
---------------------------
Before PASS:
- every declared slice path exists;
- IDs unique;
- exact I-can IDs/text correct;
- every record resolves to one design slot;
- every question_structure_id resolves;
- response_mode is compatible with the structure;
- every record's evidence_job, student_action, response_mode, and representation_mode collect the same intended evidence;
- construct/draw/build evidence is not mapped as selected_response unless the evidence job is explicitly selection/critique instead of construction;
- Practice family type/content mode is justified by the actual I-can/evidence job, not a category quota;
- selected_response records have a planned choice/distractor contract;
- representation-required records have a real render/tool/source route;
- every non-student-constructed diagram/FBD/vector route resolves to an exact pinned canonical asset OR a registered deterministic tool;
- generic diagram route aliases/placeholders are forbidden;
- graph records use `graph_tool` when supported;
- small-table records require semantic compact HTML tables;
- diagram/FBD/vector records do not rely on prose substitution;
- WTC records satisfy the connected shared-stimulus/dependency decomposition gate;
- each WTC decomposition_move_plan matches the actual planned parts and does not claim a universal move merely because it appears in a template;
- WTC is not rejected solely because the underlying Physics is straightforward;
- family locks/variation axes explicit;
- deterministic selection feasible;
- secure families forbid exposed finished-prompt reuse;
- no finished prompt/answer prose leaked into the map.

FAIL if the map only labels structure/representation without an executable route.
FAIL if family/category allocation forces a task type that does not fit the I-can/evidence job.
FAIL if evidence_job, student_action, response_mode, and representation_mode disagree.
FAIL if WTC move metadata/planning claims a move that its planned parts do not actually require.
