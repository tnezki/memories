QUESTION STRUCTURE — HARD
Every mapped FINISHED QUESTION/TASK must resolve through the current universal Question Structure workflow:
  learning/evidence target -> evidence job -> student action -> structure -> response -> representation -> tool/render route.
A course may explicitly exempt a resource. If the Framework says Warm-Ups are exempt, do not force Warm-Ups through Question Structure.
Seed records are not finished questions; Question Structure applies when a seed becomes an authored question.

SEMANTIC STRUCTURE FIT — HARD
A structure ID that exists in the catalog is NOT enough to PASS. For every mapped finished task, read the CURRENT definition of the selected structure and verify all of the following agree:
- evidence job
- actual student action
- structure reasoning architecture
- structure required representation
- response mode
- mapped representation mode(s)
- executable tool / asset / response-surface route(s)

Do not use a generic fallback structure merely because it is broadly applicable.
Direct tasks may stay direct when a more elaborate architecture is not earned by the evidence job.

HARD SEMANTIC GUARDS
1. CONSTRUCT / PLOT / CREATE / DRAW / BUILD
   - If the evidence job requires the student to construct a representation, the response mode must collect that construction and the map must provide a real answer-neutral construction surface.
   - A read-only supplied-representation structure such as FEATURE-IDENTIFY cannot stand in for construction evidence.

2. PROC-MULTISTEP-CHAIN
   - May PASS only when the map records a genuine dependency: an intermediate result/decision is required and is carried into a later step to obtain the final requested result.
   - Store the dependency explicitly (for example intermediate_result_needed + carried_forward_to_final).
   - Multiple actions or labels alone do not make a task multi-step.

3. ERROR-DIAGNOSE-WORKED-SOLUTION
   - May PASS only when there is a specific documented misconception/error target, a supplied worked-solution stimulus containing that error, and a student action that locates/explains/repairs the error.
   - Do not map ordinary independent evaluation/solving to Error Diagnose merely to add variety.

4. MIXED / MULTIPLE REPRESENTATIONS
   - Every representation named by the evidence job/student action must have an executable route.
   - A graph+table task requires both a graph route AND a semantic table route (or one declared composite route that explicitly renders both).
   - representation_mode and representation_routes must honestly describe the full task.

5. STUDENT-CONSTRUCTED GRAPHS / NUMBER LINES / TABLES
   - Use an answer-neutral response surface. Do not pre-render the completed mathematical answer with a graph tool.
   - A registered tool may create blank axes/templates only when that exact route is supported and answer-neutral.

6. STRUCTURE REASONING ARCHITECTURE
   - QA must compare the catalog's actual reasoning architecture/required representation/response type with the mapped evidence job and action. Metadata presence alone cannot earn PASS.

PROFILE-DRIVEN INVENTORY — HARD
Do not hard-code Notes pairs, CYU, Warm-Ups, Practice 2/3, Exit A/B/C, or any historical count.
Read the CURRENT Framework Bank profile and map ONLY the destinations it declares canonical Bank inventory.

For Algebra 1 v7.2, the current profile resolves to:
- official Exit evidence/questions;
- secure Summative V1-V6;
- Practice 1;
- WTC;
- useful reusable Seeds when they earn a canonical role.
Extra Practice, CYU, middle practice, Notes Examples/YTIs, and finished Warm-Up questions are downstream-generated and therefore are NOT Bank Map destinations.
Other courses may resolve differently; follow their current profile.

CANONICAL FRAMEWORK MAPS

For Algebra:
- curriculum/exit_evidence_map.json owns which Mastery/I-Can evidence jobs appear on each Exit and the reassessment chain;
- curriculum/warmup_progression_map.json is NOT a Bank destination but is a downstream Framework authority.

QUESTION-DESIGN MAP
For every exact target/I-Can/evidence job needed by a canonical destination, map:
- design_slot_id
- exact target / goal / I-Can IDs + text
- stage when relevant (Intro / Review / Mastery or course equivalent)
- evidence_job
- student_action
- candidate/selected question_structure_id
- response_mode
- representation_mode + need
- representation_route OR representation_routes sufficient for every required representation
- difficulty intent
- allowed/required/forbidden variation axes
- source_basis
- security role
- structure_fit_notes when needed to prove semantic alignment
- dependency_contract when selected structure is a genuine multi-step chain
- misconception_contract when selected structure is error diagnosis

EXIT — HARD
Follow the Framework Exit map exactly.
For Algebra normal sections:
- 2 new current-Mastery evidence jobs
- 2 fresh parallel reassessment jobs inherited from the previous section carryforward pair.
U1.1 follows its Framework opening exception.
Do not remap Intro/Review into official Exit slots unless the current Framework says to.
Map secure/exposure status and parallel-variation axes. Reassessment must preserve evidence target and usable difficulty; it is not a literal-copy requirement.

SUMMATIVE — HARD
Build the Summative evidence blueprint from current Unit Mastery Goals and the Framework Exit evidence plan.
For Algebra:
1. target approximately TWO secure evidence opportunities per CURRENT Unit Mastery Goal;
2. design the complete form for about a 40-minute class period;
3. resolve exact item count from Mastery Goal count + actual task complexity/time; do NOT hard-code 8 items across all Units;
4. map V1 first as the anchor secure form;
5. map V2-V4 as parallel forms preserving blueprint/evidence/difficulty;
6. map V5-V6 after V1-V4 as additional secure forms under the same evidence blueprint and comparable rigor.
The map must record the estimated total student time and explain any deliberate deviation from roughly two opportunities per Mastery Goal.
Do not reduce parallel forms to number-only clones when the structure permits meaningful fresh variation.

PRACTICE 1 — HARD
For Algebra 1, Practice 1 is EXACTLY 24 questions PER SECTION:
- 8 Intro
- 8 Review
- 8 Mastery
Use visible stage headings.
Intro = current section Intro learning.
Review = exact current Review goal at Review demand.
Mastery = exact current Mastery goal at independent demand, informed by Exit evidence without copying secure Exit prompts/stimuli.
Within each 8-question block, distribute work for useful repetition, I Can coverage, and natural Question Structure variety. Do NOT mechanically assign two questions to every I Can if that produces filler or fake structure variety.

WTC
When canonical, map one coherent section-level multipart routine using the current course profile. Normally 3-5 connected labeled parts, shared stimulus/representation, and at least one real carry-forward/dependency. Keep the role preview/decomposition; do not inflate difficulty to look rigorous.
Every representation required by any WTC part must have an executable route or student response surface.

SEEDS
Seeds have NO quota.
Map a seed only when it has durable reuse value. A seed may preserve:
- context/situation
- dataset
- graph/diagram/visual idea
- representation pairing
- misconception/error pattern
- source problem idea
- useful mathematical setup
Record what is locked, what may vary, why it is useful, and which later artifacts may use it.
Do not create filler seeds to reach a count, and do not force every seed into a finished question now.

REPRESENTATIONS / TOOLS
Map only representations that serve evidence. Routes must be executable: registered graph tool, canonical asset, semantic HTML table, registered deterministic tool, declared composite route, or explicit student response surface. No decorative visual quota.
If an evidence job names more than one representation, route every one of them.
