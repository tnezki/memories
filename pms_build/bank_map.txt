BUILD BANK MAP — STEP 3A / BANK-V2 / CORE DESIGN CONTRACT
============================================================

STATUS: CURRENT
STEP: 3a
JOB: bank_map
ROLE: Build one complete, executable Unit Bank design map before any final Bank question prose is authored.

3a owns DESIGN, not finished questions.

The Map must be strong enough that a separate memoryless Bank builder can author the complete
Bank without guessing curriculum intent, evidence demand, family identity, representation route,
security role, or downstream selection behavior.

CORE STANDARD
-------------
The goal is a strong usable design contract, not maximal polish.

PASS when the map is:
- curriculum-correct;
- complete for the Unit;
- traceable to current authorities;
- executable by the Bank builder;
- explicit about evidence, response, representations, families, security, and selection;
- structurally/metadata complete.

Do NOT spend time at map stage polishing final wording, final visuals, exact graph aesthetics,
or finished question prose. Those belong in Bank authoring or later memoryless improvement audits.

2. MAP_MANIFEST STATUS CONTRACT — HARD
============================================================================

This field is REQUIRED.

When the integrated Map audit passes, MAP_MANIFEST.json MUST contain:

  "status": "PASS"

It must ALSO preserve the nested status fields:

  "question_design": {
    "status": "PASS",
    ...
  }

  "qa": {
    "status": "PASS",
    ...
  }

Do not omit the top-level status.

Downstream Bank jobs are allowed to require:

  MAP_MANIFEST.status == "PASS"

If Map QA has not passed:
- do NOT emit top-level status PASS;
- do NOT describe the map as accepted;
- do NOT instruct downstream Bank authoring to proceed.

The map fingerprint recipe must fingerprint the actual design slice files, not create a
self-referential dependency on MAP_MANIFEST.json itself.

============================================================================
3. QUESTION-DESIGN ARCHITECTURE — HARD
============================================================================

Build `unitN_question_design_map.json` using the current question-design schema.

For EVERY exact Unit I-can map:
- exact I-can ID and text;
- evidence_job;
- student action required to demonstrate the evidence;
- content modes;
- formula/reverse paths when applicable;
- vocabulary directions when applicable;
- best-fit question structures;
- structures to avoid;
- representation opportunities/requirements;
- tool opportunities/routes;
- parallel-variation axes.

For EVERY destination slot/family map:
- slot_id;
- record_id;
- record_mode;
- destination;
- section or Unit scope;
- primary_i_can_id + exact primary_i_can;
- supporting_i_can_ids as needed;
- evidence_job;
- student_action;
- question_structure_id;
- response_mode;
- representation_mode;
- representation_need;
- design_slot_id;
- tool / representation route;
- render_contract;
- dependency_chain when applicable;
- wording/length intent;
- security role/level;
- source_basis;
- concise authoring_notes;
- explicit variation axes.

A structure/response/representation/tool field is EXECUTABLE.
It is not a suggestion.

Alignment must be true:

  exact I-can
  -> evidence_job
  -> student_action
  -> question_structure_id
  -> response_mode
  -> representation_mode
  -> executable render/tool route

All links must collect the SAME evidence.

============================================================================
4. FAMILY-SEED DESIGN CONTRACT — HARD
============================================================================

Every `family_seed` additionally maps:
- family_id;
- family_type;
- difficulty_intent;
- intended_reasoning;
- locked_elements;
- allowed_variations;
- required_variations;
- forbidden_variations;
- representation_variation_rule when applicable;
- selection_tags.

Every lock token must resolve to an explicit mapped property.

Required variation must demand meaningful semantic change when the family is instantiated again.

Forbidden:
- vague "make another like this";
- noun-only clones counted as meaningful variety;
- number-only clones when deeper semantic independence is required;
- irrelevant measurements inserted merely to make a variant look different.

The Map defines enough variety axes for the future builder/auditor to improve a family later
without changing its evidence job.

============================================================================
5. REPRESENTATION ROUTES — HARD
============================================================================

Representations exist only when they serve the evidence job.

Graph:
- route through registered `graph_tool` when supported;
- record the exact tool key/route;
- map the evidence the graph must carry;
- do not invent an alternate graph generator.

Small data table:
- semantic HTML;
- require `<table class="values">` when the established compact-table treatment applies.

Existing canonical image/diagram:
- route_type = canonical_asset;
- exact repository;
- pinned commit;
- canonical path;
- asset_id when available.

Registered deterministic visual generator:
- route_type = registered_tool;
- exact tool key;
- parameter contract;
- answer-neutrality contract when applicable.

Student-constructed vector/FBD/model/diagram:
- explicit blank response-surface contract;
- answer-neutral;
- do not require a completed answer diagram as the student surface.

Direct text/equation:
- no decorative figure merely to create "variety."

Generic aliases such as:
  framework_approved_diagram_route
are NOT executable and must not PASS.

If an evidence-essential representation has no executable route:
- redesign only if an evidence-equivalent task is valid;
- otherwise FAIL that slot and report the missing route.

============================================================================
6. DESTINATION DESIGN
============================================================================

Resolve destination counts from the CURRENT Bank-v2 course profile.
Do not hard-code counts from another course.

The current Map must fully design every destination required by the profile, including as applicable:
- WTC;
- Notes Example/YTI;
- CYU;
- Warm-Up;
- Practice family pool;
- Exit family pool;
- Summative family pool/blueprints.

PRACTICE
--------
Fit before category.

Map exact I-cans/evidence jobs first, then allocate the required pool.
Do not force quantitative/vocabulary/graph/diagram categories merely to fill a quota.

The Practice map must make downstream deterministic selection feasible while preserving:
- all required I-cans;
- evidence/representation requirements;
- family fidelity;
- security status;
- current profile set-size/count rules.

EXIT / SUMMATIVE
----------------
Map enough secure families and explicit blueprint metadata to satisfy the current profile.

Secure families may reuse learning/evidence architecture.
They may NOT depend on reuse of exposed finished prompts or distinctive exposed stimuli.

Selected-response records must map:
- choice count/course default;
- selection mode;
- distractor basis tied to plausible evidence-job errors/misconceptions.

Summative blueprint feasibility must be explicit and deterministic.

============================================================================
7. WTC / MULTIPART ROUTINES
============================================================================

When the current course profile requires WTC:
- map the profile-required count;
- one shared coherent stimulus/representation;
- normally 3–5 connected labeled parts;
- at least one part uses the shared stimulus;
- at least one real carry-forward/dependency;
- explicit decomposition_move_plan limited to moves the routine actually requires;
- coverage_role = wtc_frq_practice unless the current profile says otherwise.

Do not inflate content difficulty simply to make the routine look rigorous.
Do not use WTC to satisfy Unit I-can coverage floors unless the current profile explicitly says so.

============================================================================
8. DETERMINISTIC SELECTION
============================================================================

For any destination with a pool:
1. satisfy hard I-can/evidence/security/representation constraints;
2. deterministic tie-break second;
3. no uncontrolled randomness.

Default stable-key architecture unless the current profile supersedes it:

  course|unit|section-or-unit|destination|form-or-set|bank_fingerprint

Map enough family diversity that deterministic rotation can actually produce meaningfully different
sets/forms without violating coverage.

============================================================================
9. GOOD-ENOUGH MAP AUDIT — HARD
============================================================================

Before PASS verify:

[ ] exact Unit I-can inventory is correct
[ ] every I-can has a clear evidence job
[ ] every required destination record exists
[ ] IDs are unique
[ ] every record resolves to one design slot

[ ] graph routes use graph_tool when supported

[ ] no generic visual-route aliases/placeholders
[ ] selected-response records have choice/distractor contracts
[ ] Practice family counts/coverage/selection are feasible
[ ] family locks + allowed/required/forbidden variations are explicit
[ ] meaningful family variation is feasible
[ ] Exit selection is feasible
[ ] Summative blueprint(s) are feasible
[ ] secure families forbid exposed finished-prompt reuse
[ ] no finished prompt/choice/answer/solution prose leaked into Map
[ ] map fingerprint is deterministic
[ ] question_design.status = PASS
[ ] qa.status = PASS
[ ] TOP-LEVEL MAP_MANIFEST.status = PASS

This audit judges whether the Map can drive a correct complete Bank.

It does NOT require:
- ideal final prose;
- ideal graph styling;
- perfect visual sizing;
- maximal context novelty;
- aesthetic optimization.

Those are later authoring/improvement jobs.
