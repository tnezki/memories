BUILD FIRST 4 DAYS — PLAN-DRIVEN / NON-UNIT OPENING ORCHESTRATOR / BOOTSTRAP-SAFE
====================================================================================

STATUS: CURRENT
STEP: 16
JOB: first_4_days

ROLE
----
Build a course's special opening-of-school sequence from a teacher-approved opening plan.
Do not invent Unit 0, a permanent Bank, fake mastery goals, or normal Unit counts merely to
make the workflow fit.

This PM is also responsible for one narrow bootstrap case:
a supported course may have a complete current Framework and file-structure contract but no
deployed live family shells/CSS yet. In that case, and ONLY when the Framework explicitly
establishes compatibility with an existing mature course implementation, this PM may bootstrap
the missing implementation surface in the same deployable patch.

FLOW
----
  PHILOSOPHY + RUNTIME
    -> CURRENT COURSE FRAMEWORK + FILE-STRUCTURE CONTRACT
    -> TEACHER OPENING PLAN
    -> REQUESTED CURRENT FAMILY PMS
    -> LIVE COURSE SHELL/CSS GATE
       -> NORMAL MODE when live course shell/CSS exists
       -> CONTROLLED BOOTSTRAP MODE when explicitly allowed below
    -> PRIVATE PRE-AUTHORING MICRO-MAP
    -> AUTHOR REQUESTED OPENING ARTIFACTS
    -> RENDER / VERIFY / REPAIR
    -> BUILD FIRST 4 DAYS INDEX
    -> RETURN COURSE-ROOT-RELATIVE DEPLOYABLE PATCH

====================================================================================
5. FAMILY ROUTING — NORMAL MODE
====================================================================================

For every requested recurring artifact family:
1. resolve its CURRENT PM from `pms_build/MANIFEST.json`;
2. resolve selected-course paths from the current Framework/file-structure contract;
3. direct-fetch current selected-course CSS and shell implementation when present;

Never copy questions/content/answers from an old course artifact.
A live HTML file is an implementation-shell exemplar only unless current authority explicitly
makes its content reusable.


====================================================================================
5A. CONTROLLED BOOTSTRAP MODE — HARD, NARROW EXCEPTION
====================================================================================

PURPOSE:
Allow a supported course with a complete Framework but an undeployed/empty live repository
to complete First 4 Days without inventing generic HTML or silently downgrading visual quality.

ACTIVATE ONLY WHEN ALL ARE TRUE:
1. selected course Framework resolves successfully;
2. selected course file-structure contract resolves successfully;
3. teacher opening plan is complete;
4. requested family PMs resolve successfully;
5. selected course genuinely lacks the needed deployed shell/CSS for one or more requested families;
6. the selected course Framework/file-structure contract explicitly establishes compatibility
   with another mature course implementation.

CURRENT AP CALCULUS AB BOOTSTRAP RULE:
The current AP Calculus AB file-structure contract states that its shared deployed course
structure is established by the supplied Algebra/Physics Frameworks and current universal task PMs.
For AP Calculus AB when its live course repo lacks family shell/CSS:
- use `tnezki/physics` as the deterministic PRIMARY implementation reference;
- pin that Physics repo once;
- use ONLY the current deployed CSS and one current shell exemplar needed for each requested family;
- use the current AP Calculus Framework for ALL mathematics, notation, AP/CED behavior, learning
  targets, examples, tasks, graphs, calculator expectations, and wording;
- NEVER copy Physics questions, Physics answers, Physics I-cans, Physics labels, or Physics content.

REFERENCE ROLE:
Reference-course files own only:
- stable DOM hooks;
- layout classes;
- print/projector/page architecture;
- response-surface styling;
- implementation selectors;
- accessibility/visual mechanics.

They do NOT own:
- course content;
- learning targets;
- item counts;
- teacher plan;
- AP Calculus notation;
- AP task style;
- examples;
- answers;
- graph mathematics.

CSS BOOTSTRAP:
When a required selected-course CSS file does not exist:
- copy the current compatible reference-course CSS bytes into the corresponding selected-course
  root `css/` path as a NEW bootstrap deployment file;
- include that new `css/...` file in the production patch;
- do not rename classes merely to make them sound Calculus-specific;
- do not edit mature selectors unless the current AP Calculus family PM requires a compatibility
  correction;
- do not copy unrelated CSS.

SHELL BOOTSTRAP:
When a selected-course live HTML shell does not exist:
- current family PM is the procedural/structural authority;
- reference-course HTML is inspected only to confirm the deployed implementation of the PM's
  required hooks;
- generate the AP Calculus opening artifact from the teacher plan + AP Calculus Framework;
- do NOT deploy a fake empty Unit shell merely to satisfy this gate.

CONFLICT RULE:
If the current family PM and reference implementation conflict:
- current family PM wins on current required structure;
- do not blindly copy stale reference DOM;
- record the incompatibility in the build report and implement the CURRENT PM contract.

FAIL BOOTSTRAP if:
- no explicit Framework compatibility basis exists;
- reference shell/CSS cannot be resolved;
- reference selectors are incompatible with the current family PM;
- safe course-neutral implementation cannot be separated from reference-course content.

BOOTSTRAP IS ONE-WAY:
After selected-course live shell/CSS exists, future runs return to NORMAL MODE and the selected
course live files become implementation authority.
