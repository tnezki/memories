RESOURCE PURPOSE
----------------
DEMO
- A short projector/screen-first spark of curiosity or intellectual tension.
- Usually 5-8 minutes unless the Framework says otherwise.
- Make students notice, predict, compare, argue, observe, confront an intuition, or ask a useful question.
- A Demo does NOT need to teach the entire section.
- End with a short discussion set: normally 2-4 worthwhile questions that surface the main noticing/reasoning and bridge into instruction.
- Prefer a small number of high-value reveals/slides over a long mini-lecture.
- Slides may intentionally ask students to record a compact representation or observation when that information will be used later.

INVESTIGATION
- An optional student learning experience, not a renamed Practice Set or generic worksheet.
- Students should do something with mathematical/scientific structure: collect/organize data, test a claim, compare models, build/translate representations, sort/match by meaning, investigate a pattern, critique a model, use a simulation/tool, make/revise a prediction, or conduct a short physical experiment.
- Use the Framework's actual learning target and representation system.
- Preserve a coherent learning flow, but do not force every Investigation into identical mechanics.
- Many Investigations will naturally launch, investigate, and synthesize, but there is NO universal task count or middle-phase sequence. The chosen Investigation type determines the actual flow; preserve a meaningful synthesis/debrief when it helps students articulate what emerged.
- Optional Investigations may deepen, rehearse, connect, or make visible core learning. They may not become the only location of required core instruction or required secure evidence.

PLAN-FIRST AUTHORING GATE — MAP THE EXPERIENCES BEFORE BUILDING HTML
-------------------------------------------------------------------
For every multi-section or all-course build, the builder MUST create the complete Demos/Investigations BUILD PLAN before writing any student or teacher HTML. This is a real Phase 1 deliverable inside the build process, not a vague mental checklist. Do not start rendering one section while later sections are still unplanned.

The plan is created from the current Philosophy + Framework + original Assessment Plans. It is a design map, not a permanent course mandate: the teacher may later skip, alter, replace, combine, or reorder any optional Demo/Investigation. Useful teacher choice remains the point. Do not force novelty for its own sake or impose equal-use quotas.

PHASE 1A — MAP THE LEARNING JOBS
For every active section, resolve the exact section learning job, important representations, likely misconceptions, and any useful Framework enrichment/source hooks.

PHASE 1B — ASSIGN AN INVESTIGATION TYPE BEFORE WRITING TASKS
For every section, choose the Investigation TYPE / classroom experience first. The current course Framework supplies its course-specific type library and representation/tool options. The chosen type must describe what students will actually DO, not merely a heading placed over a generic worksheet.

For every section, the plan records at least:
- section ID/title and exact learning job
- Investigation type
- primary student action(s)
- physical/social structure when relevant (individual, partner, group, movement, gallery, stations, whole-class data, etc.)
- concrete student artifact/output (record sheet, constructed model, collected table, graph, matched set, written claim, created example, etc.)
- representations students will read/build/use/compare/translate
- graph/figure/data decision
- materials / movement / measurement / data-collection needs
- 3-6 step experience sequence in plain language
- one-sentence reason this type fits the section

The graph/figure/data decision is explicit for EVERY section and must be one of:
  TOOL-GENERATED STUDENT EVIDENCE — a generated graph/model/data display is part of what students investigate;
  TOOL-GENERATED TEACHER REVEAL — students first predict/build, then compare with an authoritative generated representation;
  STUDENT-CONSTRUCTED REPRESENTATION — creating the graph/model is itself the learning job; teacher guide still shows/defines the expected result when useful;
  NO GRAPH/FIGURE NEEDED — with a brief reason.

PHASE 1C — MAP THE DEMO HOOKS
For every section, also choose the Demo hook mode, what students actually do/record, the evidence/reveal used, and the final discussion purpose. Demo planning may be shorter than Investigation planning, but it still happens before Demo HTML.

PHASE 1D — PLAN QA BEFORE RENDERING
Read the entire plan as a course. Check for:
- a suspicious cluster of identical Investigation types or identical 3-6 step sequences caused by template convenience;
- types whose described student action does not match the section learning job;
- representation-heavy sections planned as text-only without a defensible reason;
- graph/figure/tool capabilities ignored even though they would create the actual learning experience;
- movement, making/building, data collection, or model comparison named in the type but absent from the planned steps/materials/artifact.

If the plan fails this review, revise the PLAN before authoring HTML. Repetition is still allowed when it is genuinely the best experience for multiple sections.

PLAN ARTIFACTS
Create these BEFORE any section HTML:
  ~demos_investigations_build_plan.json   machine-readable source of truth for rendering
  ~demos_investigations_build_plan.html   compact teacher-readable map of the same plan
Keep both at the root of the final Demos/Investigations ZIP so the teacher can inspect or later revise the design map. The HTML is not student-facing curriculum.

RENDER-FROM-PLAN GATE
After Phase 1 passes, build the requested Demos/Investigations from the plan. The renderer must honor the planned experience instead of collapsing it into a convenient generic page:
- MOVEMENT means the student resource supplies movement/setup/recording directions appropriate to movement.
- DATA COLLECTION means students actually collect/record data before modeling it.
- MAKE/BUILD means students actually construct/arrange/create the object or representation.
- GALLERY/SORT/CLASSIFY means the resource contains the cards/posters/records or directions needed to do that structure.
- GRAPH/MODEL INVESTIGATION means the actual graph/model evidence exists in the student resource or planned teacher reveal.
- STUDENT-CONSTRUCTED GRAPH means the handout provides the needed data/grid/scaffold rather than pre-solving the representation.
Do not downgrade a planned experience into Task 1 + Task 2 + Synthesis simply because that is easier to render.

SAME VISUAL SYSTEM DOES NOT MEAN SAME EXPERIENCE. Stable CSS, filenames, navigation, and teacher-guide organization are desirable; cloned intellectual choreography is not. A successful prototype is a visual-quality reference, not a universal task template.

DEMO AUTHORING CONTRACT
-----------------------
1. Projector/screen-first. One slide fills the viewport.
2. Large readable text. Keep student attention on one intellectual job at a time.
3. Use prediction/reveal/compare/bridge structure when it fits; do not force superficial novelty.
4. Student-facing slides should not expose internal I-can/DOK/Mastery metadata unless that wording is actually part of the lesson.
5. DEPENDENCY / STUDENT-RECORD RULE: if a later slide depends on a table, graph, diagram, data set, statement, or other evidence introduced earlier, explicitly tell students to copy/record the needed information before advancing. Later slides should normally require students to use what they recorded rather than re-displaying the earlier representation. Do not add compact carry-forward evidence boxes merely to keep prior content visible. Repeat prior evidence only when the teacher explicitly requests it or when a genuine accessibility/safety need makes repetition necessary.
6. The final student-facing slide is a DISCUSSION / CARRY-FORWARD slide with normally 2-4 questions. Questions should prompt noticing, evidence, comparison, prediction, or a bridge into the upcoming instruction rather than become a quiz.
7. Use the current Framework representation priorities. A Demo may use a physical object, image, graph, table, equation, data, model, animation/simulation direction, or other discipline-appropriate representation.
8. Never add descriptive captions beneath student-facing representations. Put needed explanatory wording before the visual; keep only necessary labels inside it.

INVESTIGATION AUTHORING CONTRACT
--------------------------------
1. Student handout is print/Notability-friendly and must read cleanly on screen.
2. Use natural page hierarchy. Avoid box-within-box clutter and decorative metadata panels.
3. The task flow matters more than a fixed template. Use only the phases the learning job needs.
4. Directions must be concise and actionable.
5. Give workspace where students actually need to record, sketch, calculate, annotate, or explain; do not add workspace mechanically after every paragraph.
6. Representation use must be substantive: students read/build/use/compare/translate/annotate/interpret it.
7. Tables should be compact and purpose-sized. Figures should be large enough to reason from.
8. Student-facing representation captions/titles beneath visuals are forbidden by the universal Philosophy rule.
9. Synthesis should make students state, compare, revise, generalize, or defend the mathematical/scientific idea that emerged. It is not an automatic Exit Ticket and is not secure evidence by default.
10. When a physical cut/sort/card structure is the actual investigation, card borders are functional and appropriate. Ordinary explanatory/task content should not be boxed merely for decoration.


DISCOURSE PLANNING / TEACHER-GUIDE LAYER
----------------------------------------
For every substantive discussion-bearing Demo slide/step or Investigation lab/task phase,
include in the matching TEACHER guide:

  Discourse Moves
  Teacher Moves — 2–4 short phase-specific bullets
  Student Moves — 2–4 short phase-specific bullets

Teacher move families include wait, invite multiple observations/strategies, revoice, ask
students to restate, probe evidence, compare claims, and connect representations/observations.

Student move families include explain, clarify, restate, compare, support with evidence,
build on, and challenge.

Tie the bullets to the actual phase artifact: data collected, graph produced, model built,
prediction made, measurement taken, or claim tested. Avoid generic "discuss with a partner"
language detached from the task.

For discussion-rich tasks, use anticipate -> monitor -> select -> sequence -> connect during
planning so the teacher guide can identify what to look for and what ideas to connect.

Student Demo slides and student Investigation handouts remain free of teacher discourse blocks.

TEACHER GUIDE CONTRACT
----------------------
Every Demo and Investigation gets a teacher guide beside the student resource.

KEEP THE PRACTICAL OVERVIEW FIRST. Useful default sections:
- Why This Fits
- Time / grouping / core idea quick view
- Materials
- Before Class / setup
- Suggested Flow with teacher focus
- Answer / Evidence Guide or expected observations
- Watch For / likely misconception
- Strong Synthesis / productive discussion target

DEMO TEACHER GUIDE — SLIDE-BY-SLIDE DETAIL AFTER THE OVERVIEW:
- After the practical overview, include one teacher-detail page per student slide.
- The TOP HALF of each teacher-detail page shows a readable replica of that exact student slide/content.
- The LOWER HALF gives detailed teacher notes for that slide. Use the notes that matter for the slide, such as: purpose, suggested teacher move, expected/acceptable student responses, what students should notice, evidence to press for, likely misconception, move-on criterion, and transition.
- The teacher should be able to run the Demo from the teacher guide without mentally reconstructing what is on the projected slide.
- The final discussion slide's teacher notes include suggested/acceptable responses for every discussion question.

INVESTIGATION TEACHER GUIDE — ANSWERED STUDENT WALKTHROUGH AFTER THE OVERVIEW:
- Preserve the practical overview first; do not replace it with an answer key.
- Keep the quick Strong Synthesis / debrief target in that overview.
- Then mirror the substantive student Investigation task(s)/phase(s) that the teacher needs to reference while circulating or debriefing.
- Show a recognizable replica of the student prompt/representation, followed immediately by a strong answer/solution and a rationale / what-to-listen-for explanation.
- For multi-representation work, show how the representations agree; do not give only a naked final answer.
- Open-ended tasks may have one strong sample solution plus validity criteria for other acceptable answers.
- AFTER the substantive task walkthrough, mirror the student-facing SYNTHESIS again in the same teacher-copy style: recognizable student prompt/layout, suggested/acceptable responses, rationale/what to listen for, and useful teacher press questions. This end synthesis does not replace the quick Strong Synthesis at the top; both remain.
- Do not mechanically reproduce trivial directions. Prioritize the parts where a teacher benefits from seeing the actual student task beside the answer and reasoning.
- Teacher-guide tables should be visually clean, compact, and easy to scan: clear header treatment, restrained row separation, centered numerical data where appropriate, and no spreadsheet-like visual clutter.

Teacher guides should help the teacher run, respond to, and debrief the resource; they should not merely restate the student page.

SOURCE / AUTHORING RULES
------------------------
- Start from current Framework + original Assessment Plan, not from an old Demo/Investigation title.
- Use the Framework's section enrichment/future-resource hooks/source excerpts/reference figures/tables as idea sources when present.
- Borrow instructional roles and structures from references; do not copy protected wording by default.
- Demos/Investigations are AUTHORING resources, not mere downstream Bank renderers. The Framework's authoritative graph/figure/data tool MAY and SHOULD be used when its supported output cleanly serves the learning job.
- BEFORE manually drawing a graph/model or defaulting to a text/table-only treatment, read the Framework's graph-tool capability inventory. Use the authoritative tool for supported representations rather than inventing a second visual style.
- This is NOT a graph quota. Do not add a graph decoratively. If the section is representation-heavy, however, an actual generated graph/model/comparison should normally appear unless the more purposeful student action is to construct the representation themselves.
- The graph/figure tool may support projected Demo evidence, blank/student-completion scaffolds, comparison grids, context/modeling graphs, data displays, number lines, area/manipulative models, and other course-approved representations. Let the Framework define the relevant course-specific capability menu.
- Reuse an already-approved local representation when it genuinely fits. Otherwise create/adapt a new one using the Framework's supported toolchain.
- Do not silently import stale learning targets, section order, or representations from legacy Demos/Investigations.

PRE-ZIP MATHJAX / FINAL-BYTE GATE — HARD
-------------------------------------------------
For every build that produces HTML, run the CURRENT Framework's `tools/MathJax/final-byte fixer declared by the current Framework manifest` against the UNZIPPED staging output root BEFORE creating the deliverable ZIP:

  python3 <current-framework>/tools/MathJax/final-byte fixer declared by the current Framework manifest <staging-output-root>

This is a build-time final-byte step. Run it after authoring/teacher-guide insertion/figure-path assembly and before ZIP creation so the ZIP contains the repaired bytes. Then rerun the resource's HTML/MathJax/path QA on those repaired bytes. Any unresolved MathJax/final-byte warning must be repaired before delivery.

Do NOT package `MathJax/final-byte fixer declared by the current Framework manifest` inside the resource output unless the current Framework explicitly requires that tool in the deployed resource. The Framework remains the authoritative source copy.
