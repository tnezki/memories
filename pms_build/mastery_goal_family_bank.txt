BUILD ALGEBRA 1 MASTERY GOAL FAMILY BANK
=========================================

STATUS: PILOT / OLD CONTROL PANEL
JOB: bank_map_and_build
ROLE: Build a reusable Algebra 1 Bank organized by Mastery Goal -> I Can -> Question Family.

CORE IDEA
---------
Do NOT begin by filling hundreds of destination slots.

Build the reusable question architecture first:

  Mastery Goal
    -> exact I Can statements
      -> exactly 3 materially different question families per I Can
        -> one fully authored exemplar for each family
        -> clear variation rules for generating fresh instances later

For the normal current Algebra pattern of:
  4 Mastery Goals
  x 4 I Cans per Mastery Goal
  x 3 families per I Can
  = 48 question families

Those 48 families are the Bank's reusable question TYPES.
They are not 48 destination-specific clones.

This PM also creates a lightweight delivery map that records where each family may be used
(Practice, Exit, reassessment, Summative, recovery, Notes/activities when appropriate).
It does NOT mass-author every destination instance in this job.

=================================================
4. THREE FAMILIES PER I CAN - HARD
=================================================

For EVERY I Can, author EXACTLY THREE materially different question families.

Use family labels:
  Family A
  Family B
  Family C

The labels do not require the same structure across every I Can, but use this design instinct:

  Family A - CORE / DIRECT EVIDENCE
    The cleanest strong way to demonstrate the I Can.

  Family B - ALTERNATE REPRESENTATION / APPLICATION
    Same I Can, but a meaningfully different representation, setup, context, or direction.

  Family C - REASONING / MISCONCEPTION / TRANSFER
    Same I Can, but a genuinely different reasoning demand such as interpretation,
    error diagnosis, comparison, missing information, reverse thinking, or transfer.

DO NOT force a fake Family C.
If error analysis is not natural, choose another legitimate third way to prove the I Can.

MATERIAL DIFFERENCE RULE
------------------------
The three families must differ in the WAY students demonstrate the skill.

Changing only:
- numbers,
- names,
- nouns,
- colors,
- graph coordinates,
- context words

does NOT create a new family.

A new family should usually differ in one or more of:
- representation supplied;
- representation students produce;
- reasoning architecture;
- direction of thinking;
- interpretation demand;
- misconception being diagnosed;
- comparison structure;
- inverse/reverse task;
- decision students must make.

5. FAMILY RECORD - REQUIRED CONTENT
=================================================

Each family record must contain:

    - title

    - exact text
- family_name
- family_purpose
- evidence_job
- student_action
- question_structure_id
- response_mode
- representation_mode
- representation_need
- executable representation route(s)
- difficulty_intent
- invariant:
    what must stay true every time this family is instantiated
- variation_axes:
    what may change safely
- forbidden_variations:
    what would change the family or weaken evidence
- allowed_destinations:
    Practice / Exit / Reassessment / Summative / Recovery / other appropriate routes
- fresh_instance_rule:
    what must change before reusing this family for another assessment instance
- exemplar:
    one fully authored, student-usable example question
    answer/key
    short solution/scoring guidance
    structured representation data as needed

Every exemplar must be a REAL complete question, not a template placeholder.

=================================================
6. QUESTION STRUCTURE
=================================================

Every family must use a current Question Structure that fits the actual evidence job.

Do not select a structure because its name sounds close.
The student action, reasoning architecture, response mode, and representation must agree.

Keep direct tasks direct.
Do not inflate a simple graph read into unnecessary critique.

For construction:
- give a real answer-neutral response surface.

For error diagnosis:
- supply a specific worked error or misconception;
- require diagnosis/correction.

For multistep:
- use only when a genuine intermediate result is required.

For graph work:
- use the current registered graph tool;
- do not hand-build coordinate SVG as a substitute.

=================================================
7. EXEMPLAR AUTHORING
=================================================

Author ONE strong exemplar for each family.

For the normal 48-family build, this produces:
  48 family specifications
  + 48 complete exemplar questions

The exemplar exists so the teacher can inspect whether the family is actually useful.

Exemplars should:
- be student-ready;
- contain every number/data value required by the directions;
- show every required graph/table/equation/context;
- have a correct answer/key;
- have a short correct solution;
- use appropriate Algebra notation/MathJax;
- avoid answer leakage.

Do not author multiple parallel instances yet.
That comes later when a destination requests a fresh instance from a family.

10. LIGHT QA - ONLY FIVE CHECKS
=================================================

Do NOT build a large audit system.
Run only these five checks:

1. COUNT / IDENTITY
   - every exact Mastery Goal and I Can is preserved;
   - exactly 3 families per I Can;
   - all family IDs unique;
   - expected family count reconciles.

2. FAMILY DISTINCTNESS
   - A/B/C for the same I Can are materially different question TYPES;
   - number-only or noun-only clones FAIL.

3. EXEMPLAR COMPLETENESS
   - every exemplar is fully usable;
   - all referenced values/data are present;
   - required representation is visible;
   - no TODO/TBD/placeholders.

4. MATH / REPRESENTATION
   - answer and solution are correct;
   - graph/table/equation agrees with prompt;
   - registered graph tool used when required;
   - no answer leakage.

5. FINALIZATION
   - run Tools/finalize_output.py on the finished pilot Bank;
   - require FINALIZATION_QA: PASS.

If a check fails:
repair the concrete problem and rerun only that check plus finalization.

Do not create giant MAP_FIDELITY_REPORT or RENDER_QA_REPORT files.
