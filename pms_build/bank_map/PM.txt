BUILD BANK MAP — PORTABLE MEMORY v2.0 — STEP 2.5 BANK-V2 MAP-BEFORE-AUTHORING
=============================================================================

STATUS: CURRENT BANK-V2 PILOT PM
ROLE: Build one complete modular Unit Bank design map before any Bank question prose is authored.

STARTUP — HARD
--------------
Read the current Curriculum Philosophy and Runtime Contract.
Resolve required authorities through the pinned manifests.
Fetch declared resources directly.

Do not use generic web/repository search to locate known curriculum authorities. Do not substitute lightweight views,
old uploads, similarly named files, prior Bank copies, or alternate representations for a declared canonical source.

GENERIC RUN COMMAND
-------------------
Carefully read PM and Run.

"Run" means complete the full Unit map, validate it, package the real map folder as `unitN_bank_map.zip`, reopen the ZIP,
and return it in the same response. Do not author final student-facing Bank prompts, answers, choices, or solutions.

SCOPE
-----
Build one Unit at a time. Resolve course and Unit from the request/current Framework. Ask only if the Unit cannot be
resolved uniquely.

AUTHORITY ORDER
---------------
1. Current explicit teacher instruction for this job.
2. Current Curriculum Philosophy.
3. Current System Runtime Contract.
4. Current course Framework + ORIGINAL Unit Assessment Plan.
5. Current Framework/course manifest-declared Bank profile and required course runtime files.
6. Current `_question_structure/` authority.
7. This PM for mapping procedure.
8. Optional external/source research only when explicitly required by the current Framework/profile/PM.

COURSE-AWARE RULE — HARD
------------------------
This PM is universal. It MUST NOT impose Physics question patterns on Algebra, Algebra patterns on Physics, or one fixed
inventory on every course.

Resolve the current course's Bank profile through its pinned Framework manifest and use that profile for:
- destination inventory/counts;
- exact-content vs family-seed treatment;
- recurring course patterns;
- question-family mix;
- representation preferences;
- response-mode requirements;
- security behavior;
- deterministic downstream selection rules.

Examples of course ownership:
- Physics may require physical-situation formula work, Physics retrieval Warm-Ups, FBD/vector/graph/model families, etc.
- Algebra may require Diamond Problems, Graph/Equation/Table/Context relationships, Algebra-specific fluency families,
  area/rectangle models, error analysis, and other Algebra patterns declared by its Framework/profile.

Do not invent a generic replacement pattern when the course profile declares one.

BANK-V2 PURPOSE
---------------
Separate three things that were previously conflated:
1. DESIGN MAP — what evidence/question families and exact anchors must exist.
2. CANONICAL BANK CONTENT — exact authored anchors and fully authored seed-family exemplars.
3. DOWNSTREAM INSTANCES — deterministic selections/controlled variants built later from declared family contracts.

The Bank is not required to store every downstream permutation as a separate canonical question. However, downstream
variation is allowed ONLY when the Bank family record explicitly declares the transformation contract and the downstream
builder validates family fidelity.

TWO CANONICAL RECORD MODES
--------------------------
A. `exact_content`
Use when downstream artifacts must reproduce the authored item exactly. The map designs the slot; later Bank stages author
one exact canonical prompt/answer/solution. Downstream builders copy it, not rewrite it.

B. `family_seed`
Use when the course profile explicitly authorizes controlled downstream variation. The map designs a canonical family
contract; later Bank stages author one complete canonical seed prompt/answer/solution plus the transformation metadata.
Downstream builders may instantiate ONLY declared variations and must validate against locked family properties.

The course profile decides which destinations use which mode.

MODULAR MAP OUTPUT — HARD
-------------------------
Return one ZIP named:
  `unitN_bank_map.zip`

ZIP top level must be exactly:
  `unitN_bank_map/`

Required files:
  MAP_MANIFEST.json
  notes_map.json
  practice_map.json
  cyu_map.json
  warmup_map.json
  exit_map.json
  summative_map.json
  MAP_REPORT.txt

If the current course profile declares another Bank destination, add a clearly named map file and register it in
MAP_MANIFEST.json. Do not silently omit declared destinations.

MAP_MANIFEST.json is the stable routing front door. It records:
- schema/version;
- course/unit;
- pinned source identities/fingerprints;
- exact path of every destination map;
- record counts by destination/mode;
- course Bank-profile identity;
- question-structure identity;
- status.

The individual map files are canonical planning slices. Do not create one giant duplicate aggregate map containing all
records again.

COMMON RECORD CONTRACT
----------------------
Every mapped record must include, as applicable:
- `record_id` — stable canonical planning ID;
- `record_mode` — `exact_content` or `family_seed`;
- `destination`;
- `section` or Unit scope;
- `primary_i_can_id` + exact `primary_i_can` text;
- `supporting_i_can_ids` when genuinely needed;
- `evidence_job` — specific student evidence/learning action;
- `question_structure_id` — real structure from current `_question_structure/` or course-declared legitimate extension;
- `response_mode`;
- `representation_mode` and actual representation need;
- `wording_profile`/length intent;
- `security_level`;
- `source_basis` / course-specific source route when useful;
- `authoring_notes` — concise, non-student-facing design guidance.

MAPS MUST NOT contain finished student prompts, final answer choices, final answers/solutions, DOK labels, or Bloom labels.
DOK/Bloom are derived after the authored item exists.

FAMILY-SEED CONTRACT — HARD
---------------------------
Every `family_seed` record additionally includes:
- `family_id`;
- `family_type`;
- `locked_elements` — properties that downstream variants MUST preserve;
- `allowed_variations` — only legitimate axes supported by the question structure/course profile;
- `required_variations` when a secure or parallel instance must visibly change something;
- `forbidden_variations` — known drift modes;
- `difficulty_intent` / comparability intent;
- `representation_variation_rule` when visuals/data are involved;
- `selection_tags` needed for deterministic constrained downstream assembly.

Locked elements normally include the primary I-can, evidence job, question structure, intended reasoning, and approximate
difficulty. A course profile may lock additional disciplinary features.

"Make another question like this" is NOT an adequate family contract.

QUESTION-STRUCTURE VARIATION — HARD
-----------------------------------
Variation must come from the current `_question_structure/` and course-specific profile. For each family, explicitly map
which variation axes are legitimate. Examples may include:
- values/units;
- unknown/solve direction;
- evidence set;
- vocabulary direction;
- misconception/error target;
- representation values/type/orientation;
- context/phenomenon;
- dependency path;
- wording profile.

Do not treat noun/name swaps as sufficient variation when the evidence job requires more. Do not change structure,
evidence job, difficulty, or representation demand merely to create novelty.

DETERMINISTIC DOWNSTREAM SELECTION PLAN
---------------------------------------
When a course profile defines a seed pool larger than a downstream form, the map must make deterministic constrained
selection possible.

Record the selection contract in the relevant destination map:
- pool size;
- downstream form/set size;
- required I-can/evidence coverage;
- required family-type ranges/constraints;
- security constraints;
- stable selection-key recipe;
- rotation/avoid-recent-use preference when declared;
- tie-break rule.

Required principle:
  same pinned Bank identity + same declared build key = same selected family IDs.

Do NOT specify uncontrolled randomness. A deterministic pseudo-random/hash ordering is allowed only AFTER hard coverage
and composition constraints are satisfied.

MAP ORDER
---------
1. Read Philosophy + Runtime Contract.
2. Pin memories/course commits once.
3. Resolve current Framework, ORIGINAL Unit Assessment Plan, course Bank profile, and `_question_structure/` directly.
4. Build the exact I-can map for the Unit.
5. Build the resource-purpose map.
6. Resolve the course-profile inventory and record modes. Do not import counts from another course or old PM.
7. Map secure evidence architecture first where the course profile requires it.
8. Map exact instructional anchors/content slots.
9. Map family-seed pools and their transformation contracts.
10. Map deterministic downstream selection/blueprint rules.
11. Reconcile representations and source needs.
12. Validate every ID/link/count/constraint.
13. Reread Philosophy and verify purpose/evidence integrity.
14. Build MAP_MANIFEST + destination slices + report.
15. ZIP, reopen, and verify.

GENERAL QUALITY RULES
---------------------
- I-can first. Never fill a quota then attach labels afterward.
- Purpose before inventory.
- Useful repetition is allowed when it serves a real learning/evidence purpose.
- Course-specific recurring patterns are preserved.
- Representations are evidence, not decoration.
- Multi-step means an intermediate result is actually needed later.
- Secure destinations may share an evidence family with instruction but must not reuse exposed finished prompts.
- Exact-content anchors stay exact downstream.
- Seed families must be authored later as complete excellent questions; metadata alone is not a substitute for a seed.

PHYSICS SAFETY/QUALITY EXAMPLE — COURSE PROFILE STILL OWNS IT
-------------------------------------------------------------
If the current course is Physics and the profile declares the established math rule, quantitative/formula work starts
from a concrete physical situation that naturally supplies measurements. A formula may be supplied when appropriate;
students use/rearrange/invert/interpret/combine the relationship. Do not map naked variable assignments as the normal
student experience.

This example illustrates course-aware enforcement; it is not a universal math rule for every course.

FINAL QA — HARD
---------------
Fail the map if any of these are true:
- required course profile or Unit Assessment Plan is unresolved;
- a count/inventory contradicts the current course profile;
- an exact I-can is missing from required coverage;
- a family has no explicit locked elements or legitimate allowed variations;
- a family references an unknown question structure;
- deterministic selection cannot satisfy declared coverage/composition constraints;
- secure family design permits exposed-prompt reuse;
- representation requirements are omitted or decorative;
- finished question prose/answers leaked into the map;
- duplicate IDs or broken links exist;
- MAP_MANIFEST does not route every declared slice exactly.

FINAL CHAT SUMMARY
------------------
Report concisely:
- course/unit;
- course Bank-profile identity;
- exact-content record count;
- family-seed count by destination;
- deterministic selection/blueprint constraints resolved;
- QA PASS/FAIL;
- output filename.
