WHOLE-MAP CHECKS — HARD
-----------------------
1. `authority_alignment`
   - course/unit are correct;
   - pinned authority identities are present;
   - course Bank profile is current and manifest-declared;
   - no alternate/old source was substituted.

2. `manifest_routing`
   - every declared slice path exists exactly once;
   - no unregistered duplicate aggregate map competes with the slices;
   - counts in MAP_MANIFEST reconcile to slice contents.

3. `course_profile_inventory`
   - counts, record modes, family pool sizes, downstream form sizes, response modes, and recurring patterns match the
     current course Bank profile;
   - no Physics-specific rule is imposed on Algebra or vice versa.

4. `i_can_coverage`
   - exact Unit I-can IDs/text are correct;
   - all course-profile coverage floors are satisfiable;
   - no quota arithmetic has replaced evidence judgment.

5. `resource_purpose`
   - Notes anchors, Practice, CYU, Warm-Ups, Exit, Summative, and any course-specific destinations serve their intended
     instructional/evidence purposes.

6. `selection_feasibility`
   - every pool>form destination can satisfy its declared I-can/family-type/security constraints;
   - same Bank identity + same build key can deterministically resolve the same selection;
   - no uncontrolled randomness is required.

7. `security_architecture`
   - secure family pools are independent from exposed finished prompts;
   - allowed variation rules require genuine fresh secure instances where appropriate;
   - alternate blueprint behavior is credible.

8. `prose_leak`
   - no finished student prompt, final answer, distractor set, full solution, DOK, or Bloom has leaked into the map.

RECORD-LEVEL AUDIT
------------------
Every record receives PASS/FAIL/N/A for these dimensions:

1. `ican_alignment`
- exact primary I-can exists and belongs where claimed;
- supporting I-cans are real and genuinely supporting.

2. `evidence_job`
- specific enough to author from;
- matches the I-can/resource purpose;
- not generic filler such as "show understanding."

3. `question_structure`
- structure exists in current `_question_structure/` or a legitimate course-declared extension;
- structure fits the evidence job;
- multi-step really requires dependency when used.

4. `response_mode`
- fits destination/course profile;
- secure selected response plans include item-specific misconception/error intent when applicable.

5. `representation_plan`
- representation is planned when it materially carries evidence;
- no decorative quota;
- student representation is answer-neutral;
- family visual variation rules are explicit when variants need fresh data/visuals.

6. `wording_plan`
- concise/default wording unless context genuinely improves the task;
- disciplinary language is natural for the course.

7. `family_contract` — family_seed only
- family_id/type are meaningful;
- locked_elements are explicit;
- allowed_variations are legitimate for the chosen structure/course;
- required/forbidden variations prevent known drift;
- approximate difficulty/comparability intent is explicit.

8. `variation_integrity` — family_seed only
- variation can change surface instance without changing evidence job/structure/difficulty;
- noun/name swaps are not the only planned variation where richer change is required;
- course-specific recurring patterns remain intact.

9. `selection_tags` — family_seed pool only
- tags support deterministic constrained assembly;
- coverage/type/security constraints can be evaluated mechanically.

10. `security_plan`
- secure destinations do not authorize exposed prompt reuse;
- family transformations require fresh stimuli/data/context/representation when needed.

11. `course_specific_quality`
- apply the current course profile's disciplinary rules exactly.
- For Physics this includes physical-situation formula behavior when declared.
- For Algebra this includes its declared recurring mathematical structures/patterns rather than replacing them with
  generic Physics-like contexts.

DETERMINISTIC SELECTION AUDIT — HARD
------------------------------------
For every pool/form contract:
1. Verify pool count and unique IDs.
2. Verify hard coverage/composition constraints are satisfiable.
3. Verify stable build-key recipe is explicit.
4. Verify tie-break ordering is deterministic.
5. Verify selection does not depend on uncontrolled model choice.
6. Verify rotation/recent-use preferences never override hard coverage/security constraints.

The audit may simulate selections conceptually/mechanically, but it must not author questions.

EXIT FAMILY AUDIT — WHEN COURSE PROFILE USES FAMILY SEEDS
---------------------------------------------------------
Verify:
- secure seed-family pool count matches course profile;
- each family has a distinct useful evidence job;
- the ticket blueprint/form size can be satisfied with intended I-can coverage;
- A/B/C or equivalent forms preserve blueprint evidence while requiring genuine fresh secure instances;
- downstream variation may not change the tested skill merely to appear different.

SUMMATIVE FAMILY AUDIT — WHEN COURSE PROFILE USES FAMILY SEEDS
--------------------------------------------------------------
Verify:
- secure family pool count matches course profile;
- required form/blueprint size and response-mode mix are feasible;
- every required Unit I-can can be sampled according to course profile;
- same-day parallel blueprint forms preserve comparability;
- alternate/makeup blueprint is materially alternate overall where required;
- answer-position scrambling, if used, remains a downstream final assembly step rather than a map-content mutation.
