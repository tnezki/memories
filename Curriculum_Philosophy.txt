CURRICULUM PHILOSOPHY PORTABLE MEMORY v3.14
============================================
STATUS: PROPOSED UNIVERSAL TEACHING / LEARNING PHILOSOPHY
PURPOSE: Preserve the universal educational beliefs and authority boundaries that should shape every course without relying on prior chats, stale copies, or course-specific habits.

================================================================
READ THIS FIRST / CANONICAL AUTHORITY
================================================================

This Philosophy is the BASE layer. It owns universal beliefs about learning, instruction, evidence, teacher choice, useful abundance, representations, resource purpose, quality, authority boundaries, and controlled system improvement.

CANONICAL GITHUB RULE — HARD:
The current canonical GitHub repositories are the source of truth. Local folders are working/test copies until the teacher intentionally syncs approved changes to GitHub. Whatever is currently canonical on GitHub is authoritative for the next job.

BUILD SNAPSHOT RULE — HARD:
At job start, resolve the current canonical GitHub state once and pin every required repository/resource to that starting snapshot for the duration of the job. Do not mix authorities that changed mid-run. Read this Philosophy FIRST from that pinned snapshot.

FAIL-CLOSED RULE — HARD:
If a required canonical authority is missing, ambiguous, or cannot be resolved from canonical GitHub, stop and identify the exact problem. Do not silently substitute an old upload, remembered rule, similarly named file, or stale embedded copy.

AUTHORITY HIERARCHY:
  1. Current explicit teacher instruction for the specific job/artifact
  2. This universal Philosophy
  3. Current universal Question Structure authority
  4. Current Course Framework
  5. Current executable PM
  6. Current tool / HTML-CSS shell / renderer

A lower layer may specialize a higher layer only where the higher layer allows specialization. It may not silently contradict it. A direct teacher instruction may intentionally create a local exception; that exception remains local unless deliberately promoted upstream.

COURSE AUTHORITY RULE — HARD:
The current Course Framework is the canonical course authority. It must contain the approved Unit Assessment Plan exactly, including exact I-can statements and evidence architecture. Builds should not hunt for a separate competing "original Assessment Plan" authority.

PM OWNERSHIP RULE — HARD:
PMs primarily own PROCEDURE: what to resolve, validate, select, assemble, audit, and output. PMs should reference canonical higher authorities instead of embedding competing authoritative copies of Philosophy, Frameworks, Question Structure, Banks, or maps. PMs may still contain their own scripts, templates, and helpers required to execute their procedure.

CORE SENTENCE
Instruction creates opportunities to learn; assessment collects evidence; the portfolio organizes that evidence over time; and the grade communicates the best current professional judgment of what the student actually understands.

================================================================
1. BUILD FROM LEARNING ARCHITECTURE, NOT RANDOM INVENTORY
================================================================

Do not start by writing questions.

Correct sequence:
  current Course Framework, containing the exact approved Unit Assessment Plan
    -> exact I-can / learning-target map
    -> course-specific learning lifecycle / recurring-practice routing
    -> resource-purpose map
    -> learning progression
    -> evidence map
    -> representation plan
    -> item requirements
    -> approved question structure
    -> actual authored question
    -> independent verification

For any build that spans multiple items, sections, or resource instances, turn the learning/evidence/representation architecture into an explicit PRE-AUTHORING MAP across the full requested scope before writing final student materials. The map is a thinking tool, not a quota sheet. Use it to see coverage, missing opportunities, repeated structures, representation use, evidence routes, and the actual jobs students will do before template momentum starts driving the build. QA and revise the map before rendering when the pattern does not match the intended learning work.

Predictable routine is desirable. Formulaic placement and assembly can be good. Formulaic QUESTION THINKING is bad.

The exact I-can statements are the instructional spine. Section readings, explanations, Notes anchors, Examples/YTIs, Practice, evidence, and later downstream resources should revolve around those exact learning jobs rather than a generic textbook chapter template. If the learning architecture changes, downstream resources should be intentionally reconciled rather than quietly preserving an obsolete order.

================================================================
1A. COURSE LEARNING / EVIDENCE LANGUAGE AUTHORITY
================================================================

The current Course Framework contains the approved Unit Assessment Plan exactly. The Assessment Plan's own learning, evidence, source, and mastery language is authoritative for that course and Unit.

Do not invent, normalize, or rename course-specific learning-stage vocabulary into a universal lifecycle. If an Assessment Plan uses distinctions such as Current Learning Source, Retrieval Source, Mastery Source, Intro, Review, Mastery, or another course-specific structure, preserve those terms and relationships exactly as the Framework defines them. If the Assessment Plan does not use those distinctions, do not impose them.

Student-facing resource names do not by themselves define a learning stage or evidence role. Any resource-specific meaning, source relationship, or review/spiral behavior must come from the current Course Framework and its exact Assessment Plan, or from the lower-level PM when the Framework intentionally delegates that implementation detail.

This Philosophy owns the universal rule: course learning/evidence language comes from the exact Framework-embedded Assessment Plan and must not be silently reinterpreted.

================================================================
2. RICH MENU / USEFUL ABUNDANCE / TEACHER CHOICE
================================================================

The course is a rich menu of high-quality options, not a minimum viable packet or fixed calendar. The teacher may skip, shorten, substitute, combine, reorder, or spend longer on resources.

MORE CAN BE BETTER when additional material is genuinely useful. Unused high-quality material gives teacher choice, differentiation, reassessment options, alternate representations, repetition, and flexibility.

Underbuilding often forces the teacher to invent curriculum during class. Therefore do not stop simply because the smallest acceptable amount has been reached. The guardrail is PURPOSE, not minimalism. Do not add purposeless filler, but do not remove useful material merely because not all of it will be used.

DOWNSTREAM FULLNESS PRINCIPLE:
When a finalized canonical source route is already appropriately classroom-sized and a downstream wrapper can support the full route, preserve the full useful set by default. Intentional thinning is allowed when it serves a clear resource purpose or explicit teacher choice.

ABUNDANCE IS COURSE-RESPONSIVE.
Different courses and topics need different kinds and amounts of repetition. A course that depends heavily on procedural fluency may intentionally devote several nearby questions to the same high-value family. Another course may gain more from changing representation, phenomenon, model, or reasoning demand. The Course Framework should state the course-specific expression of this philosophy.

The rich digital Bank is allowed to contain more options than a teacher will use in one lesson or printout. A later artifact may select, adapt, condense, or replace that material for a specific classroom purpose.

================================================================
3. REPETITION IS OFTEN HOW LEARNING DEVELOPS
================================================================

Repetition is not automatically a defect. Repeated execution/retrieval can build fluency, accuracy, notation/control, discrimination, conceptual strength, and confidence.

Several direct solve/evaluate/simplify/graph/classify/calculate/formula questions may be better than forcing every question into a different context or reasoning wrapper. A useful family may legitimately appear several times with closely related values/structures when that is the learning work students need.

Even an exact duplicate is not automatically a curriculum failure in a rich teacher Bank. It may be harmless or intentionally reusable. Do not launch an anti-clone rewrite merely because prompts repeat.

Repeated questions should still read like ordinary student questions. Do not expose generator iteration labels or append one generic explanation/checking suffix across a whole Practice form. Explanation, verification, representation, units, or reasonableness language should be item-specific when it adds learning value.

MAP-FIRST REPETITION DISCIPLINE:
A pre-authoring map helps distinguish PURPOSEFUL REPETITION from ACCIDENTAL REPETITION. Repetition that serves a mapped learning job — fluency, retrieval, repeated evidence, consistency across forms, repeated use of an important representation, or deliberate return to a high-value structure — may be exactly right.

The map should expose repetition caused mainly by template convenience: the same question shell, experience sequence, representation choice, reasoning suffix, or student action repeated because it was easy to render rather than because the learning architecture called for it. When a suspicious cluster appears, ask what learning/evidence purpose the repetition serves. If the purpose is real, keep it. If it is only a byproduct of the template, revise the plan.

Do not use anti-repetition quotas such as "no structure more than twice." The goal is intentionality, not maximum variety.

================================================================
4. HIGHEST-STAKES BANK AREAS
================================================================

1. Exact I-can / learning-target mapping.
2. Strong WTC / section-opening experience.
3. Strong Notes Example/YTI anchors.
4. Strong Exit Tickets with explicit evidence maps.
5. Honest distribution of opportunities across the exact I-can statements.

Inventory completeness does not rescue weakness in these areas. Equal distribution is not required, but an explicit I-can should not accidentally receive almost no meaningful instructional/evidence opportunity unless the current Course Framework intentionally treats it as supporting or subsumed.

BANK / BANK-MAP STRUCTURE RULE:
The Bank and Bank Map are the structured reusable question-content layer. They own structured inventory counts, destination routing, exact I-can mappings, seed/parallel relationships, response modes, evidence roles, and other machine-readable Bank architecture required by the current Framework and Bank procedure.

This structure makes the Bank reliable and reusable. It does NOT make every downstream classroom artifact a frozen replica of Bank wording.

================================================================
5. REPRESENTATIONS ARE INSTRUCTIONAL CONTENT
================================================================

The Course Framework defines the representation system that matters for that discipline and Unit. Possible representations include graphs, equations, tables, contexts, diagrams, phenomena/images, data, formulas, models, units, experimental setups, number lines, geometric objects, code, or other course-specific forms.

Plan and actually USE the applicable forms; do not satisfy representation philosophy by merely mentioning that they were considered. Connect/translate among forms where meaningful. This is not an equal-percentage quota.

A representation counts only when students actually read, build, use, compare, translate, annotate, or interpret it. Decorative images and metadata labels do not count as representation reasoning.

Use the current canonical course-authoring tools when their supported type represents the intended content cleanly. Preserve editable source/provenance when useful. Recurring downstream artifacts should normally reuse approved canonical representations rather than needlessly redesign them, while a deliberately redesigned artifact may create a new representation when that better serves the task.

================================================================
6. PRACTICE CREATES LEARNING; DO NOT UNDERBUILD
================================================================

Practice exists primarily to CREATE LEARNING, not to generate grades.

The Bank/Bank Map may specify structured inventory counts and the Course Framework may specify course-specific repetition patterns or routing. Those are implementation rules, not the philosophical reason Practice exists.

A good Practice resource provides substantial productive work for the intended learner, with useful extra material allowed because the teacher can skip/select.

Practice may contain direct/repeated work, representations, conceptual/diagnostic work, and a smaller or larger number of deeper/integrated/transfer items depending on the course and target. Parallel forms preserve learning coverage/opportunity; they do not need to maximize sentence-shell variety.

================================================================
7. NOTES / EXAMPLE-YTI / WTC
================================================================

Notes are the main guided instructional pathway but not a script that must be completed top-to-bottom. Exact I-can mapping comes first; readings, explanatory notes, representations, Examples/YTIs, and teacher discussion should revolve around those learning jobs.

Notes sections should be deliberately compartmentalized around the current Course Framework's Assessment Plan structure. Formatting/order can improve over time, but do not blur exact I-cans into a generic undifferentiated chapter.

Instructional reading should be substantial enough to teach the idea, not a thin bridge inserted only to reach the next problem. The Course Framework owns the course-specific reading benchmark, density, language, and source style. After a substantial reading, students should immediately process meaning through a short discussion / sense-making task before the next major application. Discussion questions should be specific to the reading and representations rather than stock comprehension prompts.

Vocabulary should develop in context. When a course Notes profile uses a vocabulary preview, the first meaningful introduction or definition of a target vocabulary/notation term in instructional prose may be visually emphasized so students can connect the previewed word to its meaning; do not turn every later recurrence into bold clutter.

Math Notes / Model Notes are reference tools, not decoration. Useful abundance applies here too: a rich Notes resource may contain more high-value reference blocks, worked representations, connections, or models than a teacher uses in one lesson. The teacher can skip. Do not underbuild a durable reference merely to make the Notes shorter, but every block still needs a real instructional purpose.

WTC is a recurring FRQ-decomposition routine built around one coherent free-response-style stimulus and connected labeled parts. Its primary purpose is to teach students how to unpack a long multi-part question: identify what is given and asked, read/use the representation, notice dependencies among parts, choose a relationship or plan, and communicate reasoning. WTC content does NOT have to match the current section or even the current Unit; it may draw from prior, current, or future course territory when that makes a useful FRQ. Because WTC is skill practice for navigating FRQs rather than current-unit evidence, it does not satisfy current section/Unit I-can coverage floors. If the content has not yet been taught, the student-facing work must remain structurally accessible.

Example/YTI pairs are instructional anchors tied to mapped targets. Reading/visuals/discussion should revolve around conceptual learning behind the Example, not simply reveal its exact procedure immediately beforehand. A target may legitimately receive several pairs. The teacher may skip anchors or use them differently.

Notes should not contain a fake closing Exit Check simply for symmetry.

================================================================
7A. ACTIVITIES / INTERACTIVE PRACTICE / CUSTOM INSTRUCTION
================================================================

Activities create learning by changing the participation structure around worthwhile mathematical/scientific work. Movement, collaboration, station rotation, projected team work, peer checking, hands-on measurement, modeling, probes/sensors, discussion, and structured conversation can make retrieval, representation use, comparison, explanation, experimentation, and practice more visible and social. The activity structure serves the learning job; novelty is not the goal.

Activities are OPTIONAL instructional routes unless the current Course Framework explicitly defines a required experience. Core learning/evidence should not accidentally disappear merely because an optional Activity is skipped.

BANK-AS-SOURCE, NOT-PRISON RULE — HARD:
When an Activity or other downstream artifact is built from a finalized Bank, Bank questions are reusable source material. A builder may select, group, order, adapt, rewrite, replace, or purpose-author questions when that produces a better classroom experience. A local artifact improvement does NOT automatically change the Bank.

Choose an activity format because it fits the learning work. Short independent items may fit a social structure; a varied representation set may fit stations; richer questions may fit projected/team formats; experimental goals may call for a purpose-built lab or investigation.

CUSTOM ARTIFACT RULE — HARD:
Labs, investigations, projects, simulations, special activities, and other inherently custom resources may be purpose-built in the HTML/CSS structure that best serves the lesson, including embedded CSS when useful. They do not have to conform to a recurring universal shell merely for consistency. They still must satisfy the current Course Framework, accessibility/usability expectations, and declared canonical filename/location contract.

Activity closure is formative unless the current Course Framework explicitly says otherwise. Do not silently reuse secure Summatives or official secure evidence as ordinary activity material.

================================================================
7B. RECURRING / ASSESSMENT ARTIFACTS
================================================================

Recurring artifacts should normally use proven, canonical HTML/CSS shells for speed, consistency, and reliability. The shell owns format; the Course Framework owns intentional course-specific differences; the PM owns procedure.

TEMPLATE-DRIVEN DOES NOT MEAN FROZEN:
Recurring builds may assemble authoritative content in a formulaic way, but finished classroom artifacts remain editable. The teacher may replace, rewrite, add, remove, reorder, or specially author content when the actual classroom artifact would be better.

A local artifact change remains local unless deliberately promoted upstream. Do not mutate the Bank, Framework, PM, or shared shell merely because one artifact was intentionally improved.

USAGE MODE IS PART OF RESOURCE DESIGN. A projector resource should be designed around a viewport; a handwriting/Notability-first resource around tested writing/import geometry; a printed resource around physical page flow; and a screen study guide around navigation/readability.

Student-facing versions should show the learning task, not internal authoring metadata.

LIGHTWEIGHT PROVENANCE RULE:
Preserve useful hidden machine-readable provenance when available — such as Bank ID, exact I-can ID/text, structure family, source/parallel relationship, evidence role, response mode, and whether an item was locally rewritten or custom-created — provided it does not interfere with visible layout or student use.

================================================================
8. WARM-UPS
================================================================

Warm-Ups create a predictable instructional opening routine. Map their actual learning/retrieval job before writing them. Spiraling/recurring practice is purposeful, not random. Repeated direct skills are valid.

The Course Framework owns course-specific recurring routine, stage routing, and special question types. A Warm-Up set may contain different learning jobs. Those jobs should normally remain separate numbered questions rather than unrelated clauses bundled into one canonical item.

================================================================
9. EXIT TICKETS / EVIDENCE
================================================================

Exit Tickets are one of the highest-stakes Bank components. Build an explicit evidence map BEFORE questions. They are quick evidence pulses, not extra Practice. The Bank creates a useful evidence menu even if only one ticket is used.

Do not fake Mastery Goal mappings. Evidence should be interpretable and aligned with the Course Framework's exact Assessment Plan.

Quick Check = later deeper evidence. Performance Task = later richer evidence route.

PARALLEL DELIVERY / EQUIVALENT-FORM PRINCIPLE
------------------------------------------------
Short assessments may use parallel delivery formats when classroom use requires them. A projector/display form and a collected print form may present the same evidence job differently without creating a different assessment target. Likewise, multiple classroom versions may use a shared calibration anchor plus tightly parallel/varied items when that helps reduce direct copying and normalize portfolio comparison.

Equivalent forms must preserve the evidence target, representation demand, reasoning load, and usable difficulty. Delivery-format differences are not permission to change what is being assessed.

When a response requires a coordinate plane, number line, unit circle, table/grid, diagram, or other response surface, provide an appropriate blank scaffold unless constructing that scaffold is itself part of the evidence.

================================================================
10. ASSESSMENT / GRADING / PORTFOLIO
================================================================

Assessment determines what students currently understand/can do independently and what should happen next. Practice creates learning; assessment gathers evidence. Grades communicate demonstrated proficiency, not compliance or accumulated points.

Proficiency is professional judgment from a BODY OF EVIDENCE considering quality, consistency, independence, reasoning, representation use, recency, and broader pattern over time.

Do not use simple averaging, "latest score wins," or one weak event as the sole proficiency rule. Not Yet means insufficient evidence, not permanent failure.

Evidence may come from Exit Tickets, Quick Checks, Performance Tasks, investigations/labs, quizzes, written explanations, modeling, Summatives, and other valid opportunities. The same Mastery Goal may receive multiple independent evidence points across time, representations, and contexts.

Progress labels such as Not Yet / Approaching / Meeting / Exceeding describe the quality/body of evidence, not four item-difficulty tiers. DOK is descriptive metadata, not the assessment-design engine. A student Progress Tracker should help learners connect exact learning goals to portfolio evidence, current evidence status, and a next move; it should not turn DOK or a Learning Ladder into a student proficiency score.

The Course Framework owns course-specific response-format and Summative-format choices while its exact embedded Assessment Plan owns what learning/evidence must be assessed.

================================================================
11. QUESTION STRUCTURE AUTHORITY
================================================================

The canonical universal Question Structure library is a LIVE authoring/design authority. It may grow, refine, combine, or retire structures over time as the curriculum evolves.

The current build must use the current canonical Question Structure from the pinned GitHub snapshot. Do not invent a separate hidden structure system inside a PM or Course Framework.

Question Structure defines the shared design vocabulary for how questions can be built. It does NOT control curriculum coverage, item counts, DOK quotas, teaching sequence, or course-specific distribution. The Course Framework defines how the course uses the available structures; the Bank/Bank Map owns structured counts and routing; PMs execute the procedure.

Use the structure library especially for conceptual reasoning, representation connections, misconception diagnosis, modeling, comparison, argument/evidence, transfer, coherent multipart tasks, and unfamiliar applications.

Simple direct questions should remain simple when that is the right task. Do not wrap routine work in stock reasoning language merely to look rigorous. Values should be pedagogically natural for the target and intended representation; random-looking numbers do not create useful variety.

Every item has a specific instructional/evidence target. Multi-concept items require a coherent bridge. Context must affect the mathematics/science/interpretation rather than act as decorative nouns. Representations must be real when representation reasoning is claimed. Internal authoring labels belong in metadata, not student-facing prompt text.

================================================================
12. OPTIONAL / LATER / PURPOSE-BUILT RESOURCES
================================================================

Demonstrations, Investigations, Performance Tasks, Quick Checks, labs, projects, and other purpose-built resources may be designed later from the Course Framework and current learning/evidence maps unless the current workflow explicitly includes them.

Optional instructional routes must not accidentally carry required core instruction that disappears if skipped, unless the current Course Framework intentionally defines that experience as required.

Teacher-live improvements should be preserved when useful and may completely replace an older canonical artifact after teacher review and GitHub sync.

================================================================
13. VISUAL / WORKSPACE PHILOSOPHY
================================================================

Visuals are instructional content, not decoration. Source visuals are candidates, not automatically approved. Workspace, scale, layout, and readability should fit how the teacher/students actually use the resource. The Course Framework or artifact-specific procedure may define more specific device/print/workspace conventions.

STUDENT-FACING REPRESENTATION CAPTION RULE — UNIVERSAL / LOCKED:
Do not place descriptive captions, titles, source labels, representation labels, or figure-name text beneath a student-facing graph, table, diagram, image, or other representation. The prompt introduces the representation; the representation then stands alone. Preserve mathematically/scientifically necessary labels INSIDE the representation itself: axes, tick values, units, legends when necessary, point/function labels, force labels, values, and comparable data. If explanatory wording is necessary for the task, place it in the prompt BEFORE the representation rather than as a caption beneath it. A direct teacher instruction may create a local exception.

================================================================
14. RENDERING INTEGRITY / HUMAN-IN-THE-LOOP
================================================================

Correct curriculum content is not enough if rendering corrupts it.

Deterministic tools should handle mechanical tasks they are good at: final-byte checks, figure generation, answer-choice scrambling, packaging integrity, syntax validation, path validation, and other repeatable checks. They should not silently rewrite curriculum or declare pedagogically useful repetition bad.

Semantic curriculum judgment remains a teacher/AI review job. The teacher decides whether the actual classroom artifact is good enough to become canonical.

A generated artifact is a CANDIDATE until the teacher reviews/tests it and intentionally syncs it to canonical GitHub. Unsynced local experimentation has no authority over the next job.

================================================================
15. CANONICAL TASK GRANULARITY
================================================================

A resource set may contain several different questions. A single canonical question should contain one coherent job unless its parts share a real stimulus, dependency, representation connection, or compare/contrast bridge. Do not compress independent questions by joining them with "and," "then," or "also."

================================================================
16. OWNERSHIP / INHERITANCE PRINCIPLE
================================================================

Treat the curriculum system as layered authority:

  UNIVERSAL PHILOSOPHY
    universal beliefs, authority boundaries, and system-level instructional principles

  UNIVERSAL QUESTION STRUCTURE
    shared live vocabulary for question design

  CURRENT COURSE FRAMEWORK
    exact approved Unit Assessment Plans/I-cans, course-specific learning architecture, response modes,
    recurring routines, abundance patterns, representations, source intelligence, and intentional course differences

  EXECUTABLE PM
    procedure for resolving inputs, validating, selecting, assembling, auditing, and returning the requested output

  TOOL / HTML-CSS SHELL / RENDERER
    deterministic mechanics and approved recurring-artifact formatting behavior

  FINISHED ARTIFACT
    the actual classroom document, which may be locally improved or purpose-built within the teacher-declared job scope

Course-specific rules should live in the Course Framework instead of accumulating as exceptions inside universal Philosophy. Formatting mechanics should live in canonical shells/tools rather than being re-described in every PM. PMs should orchestrate rather than duplicate higher authorities.

When a rule changes, change the smallest correct owning layer and remove/demote contradictory lower-layer copies. Do not stack overrides indefinitely.

================================================================
17. CANONICAL GITHUB / JOB RESOLUTION
================================================================

Canonical GitHub is the authority store for the curriculum system. Stable canonical paths/names should identify current authorities; Git history preserves previous versions rather than requiring multiple current-looking filenames.

A normal job should identify the task and where its canonical dependencies live. The executing workflow then resolves required Philosophy, Question Structure, Course Framework, PM, Bank/Map, tools, shells, and other current inputs from the pinned canonical GitHub snapshot.

PINNED RETRIEVAL CONTRACT — HARD:
- Resolve and pin the required repository commit(s) once at job start. Every authority used by the job must come from those pinned commits.
- Retrieve each authority from its exact canonical path using the correct transfer mode for the file type. Text authorities may be read as text. Binary authorities such as ZIPs, images, PDFs, and other archives must be retrieved as binary bytes; never treat a binary authority as text merely to inspect it.
- When a binary archive must be inspected, retrieve that exact pinned archive once and selectively extract the entries the PM actually requires. Do not replace normal retrieval with repository archaeology, web searching, provenance reconstruction, remembered copies, or similarly named expanded files.
- The executing PM must identify the authorities and content slices it needs clearly enough that the normal route is deterministic. If the prescribed pinned retrieval route fails, fail closed and report the exact repository, commit, path, and failed requirement. Do not silently improvise a different authority route.
- Retrieval mechanics are execution details and should normally remain silent. Surface them only when a real retrieval failure requires teacher action or changes the build decision.

The teacher should not have to repeatedly upload canonical dependencies merely to run a normal job.

Exact repository paths, filenames, Control Panel UI, packaging implementation, authentication, and synchronization mechanics are operational concerns and belong below Philosophy.

================================================================
18. BUILD, AUDIT, REPAIR, AND CONTROLLED IMPROVEMENT
================================================================

Initial curriculum BUILD and long-term maintenance are related but distinct jobs. Once a course is substantially built, targeted audit/repair should not require reopening the entire build architecture every time the teacher notices a local problem.

TARGETED AUDIT PRINCIPLE:
Prefer small, specific audit jobs that expose the exact classroom content the teacher needs to judge. Examples include showing all questions in one Activity set in order, auditing one Exit form, reviewing one Practice family, or inventorying questions actually used across a Unit. Audit views should optimize review clarity rather than mimic the student-facing layout.

DECLARED OUTPUT-SCOPE RULE — HARD:
Each job declares the scope it is allowed to replace. That scope may be one HTML file, one artifact, one folder/package, one Practice family, all Unit Exit Tickets, an entire Unit package, or another coherent deployment scope. Everything inside the declared scope may be repaired, redesigned, or completely replaced when that is the job. Everything outside the declared scope is protected.

Return the smallest coherent deployable result that fully satisfies the requested scope while preserving the repository-relative structure needed for clean replacement. Exact packaging mechanics belong to the executing PM.

LOCAL ARTIFACT CHANGE RULE:
A downstream artifact may be improved without changing the Bank. If the teacher later decides that an artifact-level improvement represents a better canonical question or system rule, promote it deliberately to the smallest correct owning layer.

SYSTEMIC IMPROVEMENT LOOP:
A real build or repair run is also controlled regression testing of the workflow. If execution exposes a repeatable/systemic bottleneck, contradiction, ambiguous ownership rule, missing shell contract, or other system-level weakness, do not silently improvise around it.

First identify the owning layer:
- artifact-specific defect -> repair the artifact;
- Bank/Bank Map defect -> route to Bank improvement;
- Course Framework defect -> repair the course authority;
- PM defect -> repair the procedure;
- Question Structure defect -> repair the universal structure library;
- tool/shared-shell defect -> repair the mechanism;
- Philosophy defect -> repair the universal principle/ownership rule.

A systemic improvement should be flagged as a candidate, not automatically promoted. The teacher decides whether it belongs upstream. After approval, validate the exposing case and regression-check protected areas before treating the change as canonical.

This creates a long-term lifecycle:
  BUILD -> DEPLOY/TEACH -> OBSERVE -> TARGETED AUDIT/REPAIR -> PROMOTE UPSTREAM WHEN WARRANTED

================================================================
19. FINAL OPERATING PRINCIPLES
================================================================

1. CANONICAL GITHUB IS THE SOURCE OF TRUTH.
2. READ CURRENT PHILOSOPHY FIRST FROM THE PINNED STARTING SNAPSHOT.
3. FAIL CLOSED WHEN A REQUIRED CANONICAL AUTHORITY IS MISSING OR AMBIGUOUS.
4. THE CURRENT COURSE FRAMEWORK CONTAINS THE APPROVED UNIT ASSESSMENT PLAN EXACTLY.
5. PURPOSE BEFORE INVENTORY.
6. EXACT I-CAN / TARGET MAP BEFORE QUESTIONS.
7. EVIDENCE MAP BEFORE EVIDENCE ITEMS.
8. FOR MULTI-ITEM / MULTI-SECTION BUILDS, MAP THE FULL REQUESTED SCOPE BEFORE AUTHORING.
9. QUESTION STRUCTURE IS ONE LIVE UNIVERSAL DESIGN AUTHORITY; FRAMEWORKS DEFINE COURSE USE OF IT.
10. THE BANK / BANK MAP OWN STRUCTURED REUSABLE QUESTION INVENTORY AND COUNTS.
11. THE BANK IS A SOURCE, NOT A PRISON; FINISHED ARTIFACTS MAY BE INTENTIONALLY REWRITTEN OR CUSTOM-AUTHORED.
12. LOCAL ARTIFACT CHANGES DO NOT AUTOMATICALLY CHANGE THE BANK.
13. REPRESENTATIONS ARE INSTRUCTIONAL CONTENT; PLAN AND ACTUALLY USE APPLICABLE FORMS.
14. PREDICTABLE ROUTINE IS GOOD.
15. PURPOSEFUL REPETITION IS GOOD.
16. USEFUL ABUNDANCE IS GOOD; THE TEACHER CAN SKIP.
17. ABUNDANCE SHOULD BE COURSE-RESPONSIVE, NOT UNIVERSALLY EVEN.
18. UNDERBUILDING IS A REAL DEFECT.
19. PURPOSELESS FILLER IS BAD.
20. FAKE VARIETY IS BAD.
21. DIRECT QUESTIONS MAY REMAIN DIRECT.
22. MULTIPART REQUIRES A REAL CONNECTION.
23. RECURRING ARTIFACTS NORMALLY USE PROVEN HTML/CSS SHELLS; PMs SHOULD NOT REINVENT THEIR FORMAT.
24. CUSTOM LABS / INVESTIGATIONS / SPECIAL ACTIVITIES MAY USE PURPOSE-BUILT HTML/CSS, INCLUDING EMBEDDED CSS WHEN USEFUL.
25. RESOURCE USAGE MODE IS PART OF THE DESIGN CONTRACT.
26. PRESERVE LIGHTWEIGHT HIDDEN PROVENANCE WHEN AVAILABLE WITHOUT AFFECTING STUDENT USE.
27. DETERMINISTIC TOOLS HANDLE MECHANICAL CHECKS; TEACHER/AI REVIEW HANDLES SEMANTIC QUALITY.
28. A GENERATED OUTPUT IS A CANDIDATE UNTIL THE TEACHER APPROVES AND SYNCS IT TO CANONICAL GITHUB.
29. PMs OWN PROCEDURE; THEY SHOULD NOT CARRY COMPETING HIGHER-LEVEL AUTHORITIES.
30. A NORMAL JOB SHOULD RESOLVE CANONICAL DEPENDENCIES FROM GITHUB RATHER THAN REQUIRE REPEATED MANUAL UPLOADS.
31. DIRECT TEACHER INSTRUCTION MAY CREATE A DELIBERATE LOCAL EXCEPTION WITHOUT AUTOMATICALLY CHANGING THE SYSTEM.
32. EACH JOB DECLARES ITS REPLACEMENT SCOPE; NOTHING OUTSIDE THAT SCOPE SHOULD CHANGE.
33. RETURN THE SMALLEST COHERENT DEPLOYABLE RESULT THAT SATISFIES THE DECLARED SCOPE.
34. SMALL TARGETED AUDIT/REPAIR JOBS ARE PREFERRED OVER GIANT UNIVERSAL AUDIT SYSTEMS.
35. SYSTEMIC IMPROVEMENTS ARE FLAGGED AND PROMOTED DELIBERATELY TO THE SMALLEST CORRECT OWNING LAYER.
36. TEACHER PROFESSIONAL JUDGMENT REMAINS FINAL.
