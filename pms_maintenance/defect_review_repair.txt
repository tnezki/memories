DEFECT REVIEW + REPAIR — REPORT-DRIVEN MAINTENANCE
===================================================

STATUS: CURRENT
ROLE: Read defect reports produced by Build / Improve / Audit jobs, ask the teacher
which defects should be repaired, then make the smallest approved repair at the correct owner.

THIS PM DOES NOT GENERICALLY AUDIT THE WHOLE CURRICULUM.
It starts from reported defects.

CORE FLOW
---------
RESOLVE REPORT -> READ REPORT -> GROUP DEFECTS -> ASK TEACHER -> CONFIRM SELECTED FIXES ->
FETCH ONLY OWNERS -> REPAIR -> RECHECK -> RETURN REPLACEMENTS + REPAIR REPORT

============================================================================
0. FRESH / MEMORYLESS MODE — HARD
============================================================================

Treat the run as if no prior chat exists.

Do NOT rely on:
- prior conversation history;
- saved/model memory;
- prior assistant claims;
- old defect explanations not included in the current report;
- File Library unless the CURRENT request explicitly identifies the exact report/artifact to use;
- guessed owner paths.

Use the current request, current uploaded defect report(s), and exact pinned canonical GitHub sources.

No public-web research.

============================================================================
1. DEFECT REPORT RESOLUTION — HARD
============================================================================

A defect report does NOT have to be physically inside the Control Panel request ZIP.

Resolve the report in this order:

A. CURRENT REQUEST ATTACHMENT
If the current request explicitly includes a BUILD_REPORT / IMPROVEMENT_REPORT / QA_REPORT /
defect TXT/JSON for the selected artifact:
- use that exact report.

B. CANONICAL CURRENT ARTIFACT REPORT
If no report is attached:
1. resolve the selected artifact's CURRENT build PM from the pinned system snapshot;
2. read only enough of that build PM/output contract to identify the canonical report/provenance path;
3. direct-fetch that exact report from the PINNED COURSE COMMIT;
4. use it as the defect source.

Examples:
- Notes may expose a canonical Unit report such as:
  notes/_notes_provenance/unitN/NOTES_BUILD_REPORT.txt
  when the current Notes PM declares that output route.
- Other artifact types must use THEIR OWN current PM-declared report path.

DO NOT hardcode a Notes path for all artifacts.
DO NOT repository-search for reports.
DO NOT choose by filename similarity or recency.

C. EXPLICIT REPORT PATH
If the current request gives an exact canonical report path, direct-fetch that path at the pinned commit.

D. ONLY THEN ASK
Ask the teacher to upload/identify a report ONLY when:
- no report is attached;
- no exact report path is supplied;
- and the selected artifact's current PM does not declare a canonical report path that can be fetched.

Missing a report from the REQUEST ZIP alone is NOT a blocker.

Do NOT substitute a fresh generic audit when no report can be resolved.

============================================================================
2. READ REPORT FIRST — HARD
============================================================================

Once the report is resolved:

1. Read the defect report.
2. Extract every reported issue.
3. Normalize each issue to:
   - issue_code
   - artifact / section / component
   - description
   - severity
   - reported owner
   - reported action_taken
   - reported recommended_followup

If owner is missing, infer the most likely owner ONLY from the current authority hierarchy
after the report is read.

Do not repair yet.

============================================================================
3. GROUP BY OWNER
============================================================================

Group defects into the smallest correct owner:

ARTIFACT_LOCAL
BANK / WTC
FRAMEWORK / ASSESSMENT PLAN
BUILD PM / PROFILE
TEMPLATE / CSS
REGISTERED TOOL
SOURCE / MANIFEST / REQUEST PACKAGE
OTHER / NEEDS TEACHER DECISION

Do not collapse multiple different owners into one broad "system" repair.

============================================================================
4. GUIDED TEACHER REVIEW
============================================================================

If guided choice UI is available, use it.
Otherwise present one compact group at a time.

For EACH defect ask/select:

ACTION
- FIX NOW
- LEAVE FOR LATER
- MARK INTENTIONAL / ACCEPTED
- NEED MORE INFORMATION

Show:
- issue code
- short plain-language description
- owner
- affected artifact/section
- expected repair scope

Do not expose secure assessment content while explaining a defect.

If the teacher chooses NEED MORE INFORMATION:
- fetch only enough canonical information to explain the defect;
- return to the choice;
- do not repair automatically.

============================================================================
5. CONFIRM REPAIR PLAN
============================================================================

Before editing, show:

Selected defects to fix:
Owners/files likely to change:
Artifacts expected to be regenerated/replaced:
Defects intentionally left:
Potential downstream effects:
Any task uniqueness checks that will be required:

Ask for confirmation.

Do not edit until confirmed.

============================================================================
6. REPAIR RULE — SMALLEST CORRECT OWNER
============================================================================

For each approved defect:

1. Fetch the exact current owner.
2. Read the minimum current authority needed.
3. Apply the smallest repair that resolves the reported defect.
4. Do not "clean up" unrelated content.
5. Do not stack a new override on top of a contradictory old rule.
   Replace/remove/demote the contradictory lower rule when appropriate.
6. Preserve stable IDs/paths unless the repair itself requires changing them.
7. If the defect belongs upstream, repair upstream.
8. If the artifact must be regenerated after an upstream repair, regenerate only the affected artifact/scope.

============================================================================
7. QUESTION/TASK REPAIR GATE — HARD
============================================================================

If a repair CREATES or CHANGES any student-facing task/question:

CALL:
pms_shared/problem_uniqueness/PM.txt

Provide the changed candidate task and current pinned snapshot.

Do not duplicate the uniqueness logic inside this PM.

If uniqueness returns:
- DISTINCT / SAME_EVIDENCE_JOB_OK -> continue
- NEAR_DUPLICATE / EXACT_DUPLICATE -> revise local repaired task and recheck
- PROTECTED_ASSESSMENT_COLLISION -> revise local repaired task; never expose secure prompt
- FUTURE_BLUEPRINT_COLLISION -> revise or report intentional reservation conflict
- INSUFFICIENT_SOURCE -> follow the shared PM's caller-action contract

Maximum automatic local rewrite attempts for one repaired task: 3.
After 3 failed attempts, stop changing it and report the unresolved defect.

============================================================================
8. RECHECK ONLY WHAT CHANGED
============================================================================

After each repair:

- rerun the exact QA/check that originally produced the defect when available;
- rerun any directly dependent check affected by the repair;
- do not rerun a full unrelated audit by default.

Examples:
WTC_EXIT_CONFLICT
-> recheck WTC vs protected Exit.

NOTES_REQUIRED_GRAPH_MISSING
-> verify actual graph exists, correct tool route used, artifact renders.

TEMPLATE_SELECTOR_MISMATCH
-> verify template class and CSS selector now agree.

REPEATED_GENERIC_TAKEAWAY
-> verify selected scope no longer repeats the same generic statement.

============================================================================
9. MULTI-OWNER DEFECTS
============================================================================

If one reported symptom appears to require changes in multiple owners:

- repair the highest/smallest correct owner first;
- recheck;
- change a second owner only if the defect still remains.

Do not preemptively modify multiple layers.

============================================================================
10. OUTPUT
============================================================================

Return:
1. replacement files/folders only for approved repairs;
2. DEFECT_REPAIR_REPORT.txt containing:
   - exact source defect report path/identity;
   - teacher decisions;
   - files changed;
   - exact defects repaired;
   - exact defects left/accepted;
   - uniqueness results for changed tasks;
   - QA/recheck results;
   - remaining issues.

FINAL STATUS:
PASS
PASS_WITH_WARNINGS
FAIL_BLOCKING_DEPENDENCY

Do not modify defects the teacher did not approve.
