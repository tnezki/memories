GENERIC AUDIT + REBUILD — CURRENT TARGET / ACTUAL DEFECTS ONLY
============================================================

STATUS: CURRENT
JOB: generic_audit_rebuild
ROLE: Audit the current deployed artifact against its CURRENT registered build contract, repair only actual defects, and return the smallest correct deployable change.

================================================================
0. SOURCE / SAFETY BOUNDARY — HARD
================================================================

For Curriculum Control Panel jobs, use ONLY:
- current request/current explicit teacher instruction;
- request-provided files;
- exact pinned canonical project GitHub sources declared by the request/system.

Do NOT use prior chats, remembered project facts, File Library recovery, stale uploads/packages, public web search/fetch, or outside curriculum sources unless the CURRENT request explicitly opts into a different source policy.

SOURCE/DELIVERY SAFETY PRECEDENCE
- current request + SYSTEM_RUNTIME_CONTRACT define the allowed source and delivery boundary;
- the selected artifact build PM defines the artifact contract INSIDE that boundary;
- an artifact PM may not re-enable a source that the current request/runtime prohibits.

If an artifact-PM instruction conflicts with the current request/runtime source or transfer safety rules, obey the current request/runtime and report the stale PM conflict as an upstream maintenance defect.

Pin system/course commits once. No mixed commits.
FAIL CLOSED only when a genuinely required current canonical project source cannot be read.

================================================================
1. DO THESE STEPS IN ORDER
================================================================

1. Pin current system/course snapshots.
2. Resolve the selected artifact's CURRENT build PM.
3. Resolve the exact deployed target at the pinned course commit.
4. Run CURRENT-SHAPE FAST GATE before considering migration/rebuild.
5. Reconstruct only the CURRENT artifact contract from current authorities.
6. Run the applicable audit passes.
7. Classify findings as BLOCKER / REPAIR / IMPROVEMENT.
8. Choose PATCH vs CONTROLLED REBUILD from actual defects only.
9. Repair the smallest reliable scope.
10. Re-audit affected/dependent passes + mandatory artifact QA.
11. Run universal finalization.
12. Return the smallest correct local repository transfer change and STOP.

Do not spend time explaining historical architectures unless a present defect actually depends on them.

================================================================
2. CURRENT-SHAPE FAST GATE — HARD
================================================================

RUN BEFORE theorizing about old migrations.

Read the ACTUAL deployed target first:
- directory/file listing;
- current manifest/index/report when present;
- actual schema, filenames, counts, IDs, fingerprint, and provenance.

Compare that ACTUAL shape to the CURRENT build PM/profile.

NOT DEFECTS BY THEMSELVES
- different repository commit SHA;
- different PM version/date;
- different audit date;
- truthful older generation pins;
- retired filenames that are not actually present;
- historical inventory rules that are not active.

Do NOT:
- invent CREATE/DELETE work for absent legacy files;
- infer an old inventory from historical knowledge;
- read old PMs/package manifests merely to explain current shape;
- rebuild because pins changed.

If current shape matches current contract, preserve the architecture and proceed directly to semantic/content QA.
If an actual structural mismatch exists, record the exact present mismatch, then evaluate patch vs rebuild.

A stale convenience/retrieval pointer is not automatically a target BLOCKER when the current authority chain provides another exact declared route and the missing aid is not required for execution. Report it as upstream cleanup instead of inventing a substitute.

================================================================
3. FINDING CLASSES
================================================================

BLOCKER
- incorrect answer/math/physics;
- wrong target/evidence;
- missing required current content;
- genuinely broken required dependency;
- security exposure;
- unusable required representation;
- mandatory validator/finalization failure;
- output/transfer contract failure.

REPAIR
- current artifact violates current contract but remains understandable;
- false/incomplete metadata;
- material duplication/variety problem below good-enough floor;
- meaningful layout/figure/path inconsistency.

IMPROVEMENT
- worthwhile enhancement above good-enough.

Fix BLOCKER + REPAIR. Do not churn stable content for IMPROVEMENT unless requested.

GOOD ENOUGH = CORRECT + ALIGNED + COMPLETE + USABLE + VARIED ENOUGH + TRACEABLE + DOWNSTREAM/DELIVERY READY.

================================================================
4. AUDIT PASSES
================================================================

PASS 1 — CORRECTNESS / EVIDENCE
- exact target/I-Can/goal routing
- evidence_job + student_action
- Question Structure semantic fit
- response mode
- prompt/data/visual consistency
- math/physics/answer/solution correctness

PASS 2 — COMPLETENESS / TRACEABILITY
- required files/sections/cards/forms/counts
- unique IDs
- truthful source/design/family provenance
- section/Unit/stage metadata
- representation/difficulty/security metadata
- no active TODO/TBD/placeholders or stale routes

PASS 3 — REPRESENTATIONS
- accurate, relevant, legible
- correct executable route
- correct graph/table/diagram semantics
- aspect/containment preserved
- no clipping or answer leakage
- student-construction surface answer-neutral

PASS 4 — VARIETY / RIGOR / QUALITY
- obvious near duplicates
- number-only cloning where deeper variation is required
- fake noun-only variety
- required coverage and difficulty intent
- meaningful context/stimulus/representation variation
- secure-form independence

PASS 5 — USABILITY / SHELL
Only checks required by current build PM:
- canonical CSS/shell/classes
- readable hierarchy
- no collision/clipping
- usable response areas
- figure containment
- print rules when required
- MathJax when required
- teacher-only content protected

PASS 6 — SECURITY / DOWNSTREAM
- no answer/key leakage
- secure prompt freshness/independence
- form/blueprint counts
- canonical paths/IDs remain usable downstream

PASS 7 — ARTIFACT QA / DELIVERY
- run mandatory current-PM validators/tools
- verify tool/schema applicability
- do not force legacy validators onto current schemas
- verify paths/files/assets/ZIP inventory
- run universal finalization
- require FINALIZATION_QA: PASS

================================================================
5. BANK STAGE ADAPTERS
================================================================

BANK MAP / STEP 3A
- run Current-Shape Fast Gate first;
- audit design against current Framework, exact Unit authorities, Bank profile, operational maps, and Question Structure;
- verify WTC stimulus/parts/dependencies, security, variation, routes, IDs, counts, slices, hashes, fingerprint, manifest, and report;
- do not author finished questions;
- preserve byte-for-byte correct design/map files;
- if only audit provenance changes, preserve original generation snapshot and record current audit snapshot separately;
- regenerate hashes/fingerprint only when covered bytes actually change.

Different generation pins are not proof that a map is obsolete.

COMPLETE BANK / STEP 3B
- apply current Complete Bank entry gate using accepted map/fingerprint;
- audit authored fidelity, correctness, uniqueness, representations, WTC, security, inventory/index/manifest, MAP_FIDELITY_REPORT, RENDER_QA_REPORT, and required validators;
- recheck the COMPLETE final Bank after repair, not only touched records.

A truly defective current design map is UPSTREAM_DEFECT for a Step 3b-only audit. Do not silently redesign Step 3a inside Step 3b.

================================================================
6. PATCH VS CONTROLLED REBUILD
================================================================

PATCH when defects are localized and identity/content is fundamentally correct.

CONTROLLED REBUILD only when an ACTUAL current-contract mismatch makes patching unreliable, for example:
- structurally wrong shell/DOM;
- wrong current source routing;
- widespread/repetitive current-contract failures;
- deterministic structure cannot be safely restored in place.

A different historical commit, PM date, or generation version is not enough.
If existing content is correct and authoritative: PRESERVE IT.

================================================================
7. REPAIR ORDER
================================================================

1. required authority/source/path defects
2. correctness/answer defects
3. evidence/response alignment
4. missing required content/counts
5. metadata/traceability
6. representation correctness
7. security
8. variety/rigor below good-enough
9. shell/layout/usability
10. explicitly requested cosmetic improvement

================================================================
8. POST-REPAIR / STOP RULE
================================================================

After repair:
- rerun every pass that found BLOCKER/REPAIR;
- rerun dependent passes affected by the change;
- rerun mandatory artifact QA;
- rerun finalization and delivery/package checks.

STOP when:
- no BLOCKER remains;
- no REPAIR remains;
- mandatory current-PM QA passes;
- artifact is GOOD ENOUGH.

Do not recursively polish forever.

================================================================
9. CHANGE BOUNDARY
================================================================

Preserve:
- curriculum authority
- exact goals/I-Cans
- approved Bank routing
- security architecture
- canonical CSS/assets
- correct generation provenance
- current output contract

Do NOT:
- edit Framework/Assessment Plan/unrelated stages merely to make target pass;
- weaken validators;
- modify unrelated artifacts;
- invent missing authorities;
- use prohibited source recovery;
- manufacture legacy cleanup work that is not present.

If a real upstream defect blocks faithful target repair, report UPSTREAM_DEFECT and fail closed where required.

================================================================
10. DELIVERY — HARD
================================================================

Follow current SYSTEM_RUNTIME_CONTRACT + local_transfer_contract.

For Control Panel jobs with a known canonical repository destination:
- return ONE local repository transfer ZIP;
- maintenance returns only exact changed canonical files when narrow replacement is safe;
- DELETE only an actually present obsolete active file with required expected hash;
- perform NO Git operations.

The transfer wrapper is transport only and does not change canonical artifact content/directory shape.

================================================================
11. FINAL REPORT
================================================================

Keep concise:
- target + pinned system/course snapshots
- current build PM
- audit focus
- BLOCKER / REPAIR / IMPROVEMENT findings
- PATCH or CONTROLLED REBUILD
- exact files changed
- mandatory QA + finalization result
- final GOOD-ENOUGH status
- unresolved upstream/tooling issue, if any

END — GENERIC AUDIT + REBUILD
