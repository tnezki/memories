GENERIC AUDIT + REBUILD — MEMORYLESS / GOOD-ENOUGH CORE / CURRENT-PM DELEGATION
=================================================================================

STATUS: CURRENT
ROLE: Audit the current deployed curriculum artifact against the CURRENT registered build contract, repair only actual defects, and return the smallest correct deployable change.

THIS PM DOES NOT OWN AN ARTIFACT'S CURRICULUM OR BUILD CONTRACT.
The selected artifact's CURRENT registered build PM remains the procedural authority for curriculum sources, output paths, structure, CSS/assets, security, artifact-specific QA, and canonical delivery.

If this PM conflicts with the selected artifact build PM:
  THE SELECTED ARTIFACT BUILD PM WINS.

============================================================================
0. MEMORYLESS OPERATING MODE — HARD
============================================================================

Treat the run as if no prior chat exists.

Do NOT rely on:
- conversation memory;
- prior assistant claims;
- old request packages or ZIPs;
- guessed artifact paths;
- remembered Bank/Framework facts;
- old PM folders or stale package manifests;
- public web research.

At job start:
1. pin the current system repository once;
2. pin the selected course repository once;
3. use those SAME pins for the entire run;
4. resolve the current PM registries from the pinned system snapshot;
5. resolve the selected artifact's CURRENT build PM;
6. read that build PM and only the canonical authorities/resources it requires;
7. resolve the exact deployed target at the pinned course commit.

No mixed commits.

web_search_allowed = false
web_fetch_allowed = false
external_research_allowed = false

FAIL CLOSED only when a genuinely required current authority cannot be read from the declared pinned source.

============================================================================
3A. CURRENT-SHAPE / AUTHORITY-DRIFT FAST GATE — HARD
============================================================================

RUN THIS BEFORE theorizing about migrations, legacy inventories, or rebuild scope.

1. Read the ACTUAL deployed target directory/file listing first.
2. Read the target's current manifest/index/report when one exists.
3. Record the target's actual schema, filenames, counts, IDs, fingerprint, and declared provenance.
4. Compare that ACTUAL shape to the CURRENT build PM/profile.

HARD RULES:
- A changed repository commit SHA alone is NOT a defect.
- A changed PM version/date alone is NOT a defect.
- A changed audit date alone is NOT a defect.
- Old generation pins may remain truthful historical provenance.
- Record a newer audit snapshot separately when the artifact is re-audited without rebuilding.
- Do NOT infer that legacy filenames, retired destinations, or old inventory distributions exist unless they are actually present in the target.
- Do NOT plan CREATE/DELETE migration work for files that are already current or not present.
- Do NOT read historical PMs or old package manifests merely to explain why the current artifact looks different.
- A stale convenience/retrieval pointer is not a target-artifact BLOCKER when the CURRENT build PM/profile provides another exact canonical authority route and the missing aid is not required for execution. Report it as an upstream cleanup item instead of inventing a substitute.

FAST-GATE OUTCOMES:
A. CURRENT SHAPE MATCHES CURRENT CONTRACT
   - preserve the current architecture;
   - continue directly to semantic/content audit;
   - do not begin from a rebuild hypothesis.

B. ACTUAL LEGACY / STRUCTURAL MISMATCH EXISTS
   - record the exact present mismatch;
   - then evaluate PATCH vs CONTROLLED REBUILD.

This gate does NOT trust an existing PASS claim blindly. It only prevents speculative migration work. Semantic and artifact-specific QA still run.

============================================================================
5. FINDING CLASSES / GOOD-ENOUGH FLOOR
============================================================================

BLOCKER
- incorrect math/physics/answer;
- wrong target/evidence;
- missing required current content;
- genuinely broken required dependency;
- security exposure;
- unusable representation;
- mandatory validator failure;
- output/delivery contract failure.

REPAIR
- current artifact violates the current build contract but remains understandable;
- incomplete/false metadata;
- materially weak duplication/variety;
- meaningful layout/figure/path inconsistency.

IMPROVEMENT
- useful enhancement above the good-enough floor.

Default:
- fix BLOCKER;
- fix REPAIR;
- do not churn stable content for IMPROVEMENT unless the requested focus asks for it.

GOOD ENOUGH = CORRECT + ALIGNED + COMPLETE + USABLE + VARIED ENOUGH + TRACEABLE + DOWNSTREAM/DELIVERY READY.

============================================================================
6. AUDIT PASSES
============================================================================

PASS 1 — CORRECTNESS + EVIDENCE ALIGNMENT
Check, as applicable:
- exact targets/I-Cans/goals;
- evidence_job and student_action;
- Question Structure semantic fit;
- response mode;
- math/physics correctness;
- prompt/data/visual consistency;
- answer/key/solution correctness;
- constructed response actually elicits claimed evidence;
- selected-response choices are unique and plausible.

PASS 2 — COMPLETENESS + METADATA + TRACEABILITY
Check:
- required files/sections/cards/forms/counts;
- unique IDs;
- source/design/family provenance;
- exact section/Unit metadata;
- truthful difficulty/representation/security metadata;
- no placeholder/TODO/TBD content;
- no stale routes that are actually active.

PASS 3 — REPRESENTATIONS
For every evidence-bearing graph/table/image/diagram/model:
- accurate;
- relevant;
- legible;
- correctly routed;
- aspect preserved;
- not clipped/distorted;
- no answer leakage;
- registered graph/tool route used when required;
- student-constructed surfaces remain answer-neutral;
- semantic tables used when required.

PASS 4 — VARIETY + RIGOR + QUESTION QUALITY
Check:
- obvious near duplicates;
- number-only cloning where semantic variation is required;
- fake/noun-only variety;
- balanced required coverage;
- appropriate difficulty intent;
- meaningful context/stimulus/representation variety;
- secure-form independence;
- no exposed finished prompt reused in secure assessment.

PASS 5 — USABILITY + LAYOUT + SHELL
Check only what the selected build PM requires:
- canonical CSS/shell/classes;
- readable hierarchy;
- no clipping/collision;
- usable response areas;
- figure containment;
- print/page-break rules when required;
- MathJax behavior when required;
- teacher-only content remains teacher-only.

Do not invent browser/PDF QA when the build PM does not require it.

PASS 6 — SECURITY + DOWNSTREAM INTEGRITY
Check:
- no answer/key leakage;
- secure prompt freshness;
- form/blueprint counts;
- canonical paths/IDs still satisfy downstream consumers;
- upstream ownership remains intact.

PASS 7 — ARTIFACT-SPECIFIC QA + DELIVERY
- run every mandatory validator/tool required by the CURRENT selected build PM;
- verify tool/schema applicability before invoking;
- do not force legacy validators onto incompatible current schemas;
- verify exact output paths/file count/assets/ZIP inventory;
- run the universal finalization contract from SYSTEM_MANIFEST.json;
- require FINALIZATION_QA: PASS before completion.

============================================================================
8. PATCH VS CONTROLLED REBUILD
============================================================================

Choose the smallest reliable correction.

PATCH IN PLACE when:
- artifact identity/content is fundamentally correct;
- defects are localized;
- patching will not create hidden inconsistency.

CONTROLLED REBUILD only when an ACTUAL current-contract mismatch makes patching unreliable, for example:
- structurally wrong shell/DOM;
- wrong current source routing;
- widespread/repetitive current-contract failures;
- deterministic structure cannot be restored safely in place.

A different historical generation version or commit is not enough by itself.

If existing content is correct and authoritative:
  PRESERVE IT.

============================================================================
9. REPAIR ORDER
============================================================================

1. required authority/source/path defects
2. correctness/answer defects
3. evidence/response alignment
4. missing required content/counts
5. metadata/traceability
6. representation correctness
7. security
8. variety/rigor below good-enough floor
9. shell/layout/usability
10. explicitly requested cosmetic improvement

============================================================================
10. POST-REPAIR RE-AUDIT — HARD
============================================================================

After repairs:
- rerun every pass that produced BLOCKER or REPAIR;
- rerun dependent passes affected by the change;
- rerun mandatory artifact QA;
- rerun finalization and delivery/package integrity.

STOP when:
- no BLOCKER remains;
- no REPAIR remains;
- mandatory current-PM QA passes;
- artifact is GOOD ENOUGH.

Do not recursively polish forever.
