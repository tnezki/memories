SYSTEM RUNTIME — SHARED PRINT/LAYOUT AMENDMENT
==============================================

STATUS: CURRENT / AUTHORITATIVE RUNTIME AMENDMENT
REVISION: 2026-09-30
SCOPE: Owner-local print/layout runtime behavior

RUNTIME OWNER
-------------
The shared Print/Layout Controller is the runtime owner for adjustable print geometry in supported curriculum tools.

Canonical question DOM contract:
  .plc-question
    > .plc-question-content
    > .plc-figure
    > .plc-workspace

Canonical controller responsibilities:
- whole artifact -> selected entity/student/form -> individual question inheritance
- workspace sizing
- figure sizing
- question reordering
- one page-fit calculation
- fixed-page and dynamic-page question packing
- overflow reporting
- Work View / 2-Page View

Artifact code may create page shells and fixed non-question elements. It MUST NOT own a competing pagination or layout-measurement implementation.

FIXED-PAGE MODE
---------------
Checkpoint and personalized Summative Answer/FRQ sheets use fixed two-page student segments. The shared paginator removes/reinserts only canonical question nodes, preserves fixed page content, and fills Page 1 then Page 2 using the shared fit rule. Overflow is reported only when the packed content truly exceeds the second page.

DYNAMIC-PAGE MODE
-----------------
Reusable Summative MC forms use dynamic page shells. The shared paginator packs canonical question cards into each page until the next card does not fit, creates another page, and continues. Each form is padded to an even physical page count for duplex handling. No one-page limit applies.

CONTROL COMMIT MODEL
--------------------
Slider input may preview size changes immediately. Repagination occurs on the committed value (slider release/change, numeric commit, +/- button, reset, or reorder) so the page tree does not fight the active drag gesture.

LOCAL SOURCE SNAPSHOT RULE — REQUIRED
-------------------------------------
Before changing owner-local runtime architecture, determine whether the assistant has the exact live source currently running on the teacher's machine.

Request a live local snapshot when ANY of these are true:
- the target lives outside a canonical Git repository;
- several transfer revisions have changed the same local files in the current debugging sequence;
- screenshots contradict the source the assistant is inspecting;
- transfer SHA mismatches show that the local file is newer/different than the assumed baseline;
- generated/live HTML may be surviving or being regenerated by a different layer than expected.

In those cases, ask for the current local owner folder or smallest relevant live source folder before another structural patch. Do not infer the current application by replaying or diffing a long transfer history unless no live snapshot is available.

TRANSFER SAFETY
---------------
Curriculum Transfer replacement entries for owner-local files must use SHA-256 values computed from the supplied live snapshot when that snapshot is the current authority. Repository SHA values or older transfer baselines must not be substituted for the live local baseline.

STABILIZATION RULE
------------------
After a shared owner behavior is proven, update the canonical Philosophy/runtime amendment rather than allowing separate artifact-specific copies to become the new source of truth.

END — SHARED PRINT/LAYOUT RUNTIME AMENDMENT
